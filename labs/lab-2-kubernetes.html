Lab 2 — Running a React app on a 3-node Kubernetes cluster

Duration: 2 hours 30 minutes. Working mode: solo. Everyone types every command on their own laptop.

The app is a small React page called hello-app. It shows the name of the Pod that answered, once a second. You won't write app code today. You will run it on Kubernetes twice: first with kubectl commands, then with a manifest file. At the end you open it in your browser through a LoadBalancer Service.

Before you start

Do this the night before, not in the lab.

  1. Create a free account at hub.docker.com. Your Docker Hub username is part of your image name today.
  2. Log in from the terminal and pre-pull the base images: 
    docker login
docker pull node:20-alpine
docker pull nginx:alpine
  3. Check that your cluster is running with three nodes: 
    kubectl config current-context    # docker-desktop
kubectl get nodes                 # 3 nodes, all Ready

0:10–0:30 Build the image and get it to the cluster

Open the Dockerfile and nginx.conf and read them. The Dockerfile is the two-stage frontend build from Lab 1: Node builds the React app, then nginx serves the files on port 80. nginx.conf adds one extra address, /whoami, which replies with the container's hostname. Inside Kubernetes, a Pod's hostname is its Pod name.

Build the image and test it in plain Docker:

docker build -t hello-app:v1 .
docker run --rm -p 8080:80 hello-app:v1

Open http://localhost:8080. The page shows a container ID, because there is no Pod yet. Stop the container with Ctrl+C.

Now try to run that image on the cluster:

kubectl create deployment hello-app --image=hello-app:v1 --replicas=3
kubectl get pods

Predict first: the image is on your laptop. Will the Pods start?

Trap 1 — the local image. The Pods sit in ErrImagePull or ImagePullBackOff. Run kubectl describe pod <one-pod-name> and read the Events at the bottom. Your cluster's nodes are separate machines, each with its own image storage. They can't see the images in your laptop's Docker. When a node doesn't have an image, it pulls it from a registry. hello-app:v1 with no username means "the official image hello-app on Docker Hub", which doesn't exist.

Delete the broken Deployment, then tag the image with your Docker Hub username and push it:

kubectl delete deployment hello-app

docker tag hello-app:v1 <your-dockerhub-username>/hello-app:v1
docker push <your-dockerhub-username>/hello-app:v1

From here on, wherever this sheet says <user>, use your Docker Hub username.

Checkpoint: you can see hello-app with tag v1 on your Docker Hub page, and kubectl get all shows only service/kubernetes.

0:30–1:10 Part 1: run it with commands

  1. Create the Deployment again, this time from Docker Hub: 
    kubectl create deployment hello-app --image=<user>/hello-app:v1 --replicas=3 --port=80
kubectl rollout status deployment/hello-app
  2. See where the Pods landed: 
    kubectl get pods -o wide
    Look at the NODE column. The scheduler spread your three Pods across desktop-worker and desktop-worker2. None run on desktop-control-plane, because the control-plane node is reserved for the cluster's own components. Each worker pulled your image from Docker Hub on its own.
  3. Delete one Pod and watch what happens: 
    kubectl delete pod <one-pod-name>
kubectl get pods -o wide
    A new Pod with a new name appears, possibly on a different node. The Deployment wants 3 replicas, saw 2, and created one more.
  4. Scale up, then back down: 
    kubectl scale deployment hello-app --replicas=5
kubectl get pods -o wide
kubectl scale deployment hello-app --replicas=3
kubectl get pods
  5. Expose the Deployment through a LoadBalancer Service. Port 8080 is what your browser uses; 80 is where nginx listens inside each Pod: 
    kubectl expose deployment hello-app --type=LoadBalancer --port=8080 --target-port=80
kubectl get service hello-app
Trap 4 — the EXTERNAL-IP address. The EXTERNAL-IP column shows an address such as 172.21.0.8. Paste http://172.21.0.8:8080 into your browser and it never loads. That address is inside Docker Desktop's private network, and your laptop can't reach it. Docker Desktop also publishes every LoadBalancer port on localhost, so you use http://localhost:8080. On a cloud provider, the EXTERNAL-IP would be a real public address and you would use it directly.
  1. Open http://localhost:8080. Watch the Answers so far table for 30 seconds. Every Pod name in it matches a name in kubectl get pods. Each request opens a new connection, and the Service sends each connection to one of its Pods.
  2. Delete what you made. A Service doesn't belong to a Deployment, so you delete both: 
    kubectl delete service,deployment hello-app
kubectl get all
Checkpoint: you saw at least two different Pod names on the page, and kubectl get all is back to only service/kubernetes.

1:20–2:00 Part 2: run it from a manifest

Commands are quick, but nothing records what you ran. Next, you'll write the same Deployment and Service into one file, hello-app.yaml, in the root of your repository. Write it by hand, from this outline:

  • A Deployment named hello-app: 3 replicas, a selector app: hello-app, a Pod template with the label app: hello-app, and one container named hello-app running <user>/hello-app:v1 with containerPort: 80.
  • A line with only ---.
  • A Service named hello-app: type: LoadBalancer, selector app: hello-app, one port with port: 8080 and targetPort: 80.

Use lesson 11 if you need to check a field. Write it yourself before you open the hint below.

Hint: the complete file 
apiVersion: apps/v1
kind: Deployment
metadata:
  name: hello-app
spec:
  replicas: 3
  selector:
    matchLabels:
      app: hello-app
  template:
    metadata:
      labels:
        app: hello-app
    spec:
      containers:
        - name: hello-app
          image: <user>/hello-app:v1
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: hello-app
spec:
  type: LoadBalancer
  selector:
    app: hello-app
  ports:
    - port: 8080
      targetPort: 80
  1. Apply it and check the result: 
    kubectl apply -f hello-app.yaml
kubectl rollout status deployment/hello-app
kubectl get pods -o wide
kubectl get service hello-app
kubectl get endpointslices -l kubernetes.io/service-name=hello-app
    The EndpointSlice lists the IP address of every Pod the Service has selected, with port 80. Open http://localhost:8080 again.
  2. Change replicas: 3 to replicas: 4 in the file, then apply again: 
    kubectl apply -f hello-app.yaml
kubectl get pods
    Predict first: what will apply print for the Deployment, and for the Service? In the browser, a fourth Pod name joins the table.
  3. Compare your file with what kubectl would generate. --dry-run=client -o yaml prints the object instead of creating it: 
    kubectl create deployment hello-app --image=<user>/hello-app:v1 --replicas=3 --port=80 --dry-run=client -o yaml
kubectl create service loadbalancer hello-app --tcp=8080:80 --dry-run=client -o yaml
    The core fields match yours. The generated YAML has extra fields, such as creationTimestamp, strategy, resources and status, which are empty or defaults. Note two of them for your README.
Checkpoint: hello-app.yaml creates both objects with one command, and the browser shows four Pod names.

2:00–2:20 Break it on purpose

Keep the browser tab open on http://localhost:8080 during both traps. The page keeps asking every second, so you will see the moment it breaks.

Trap 2 — the selector typo. In the Service part of the file, change the selector to app: helo-app (one l). Apply, then run: 
kubectl get service hello-app
kubectl get endpointslices -l kubernetes.io/service-name=hello-app
The Service still exists, and so do the Pods. But the EndpointSlice is now empty: no Pod has the label app: helo-app, so the Service has nowhere to send traffic. The page shows an error. Fix the typo, apply, and the page recovers.
Trap 3 — the wrong targetPort. Change targetPort: 80 to targetPort: 8080. Apply, then check the EndpointSlice again. This time it lists your Pods, now with port 8080. The Service found the Pods, but it sends traffic to port 8080 and nothing in the Pod listens there. nginx listens on 80. The page shows an error again. Change it back to 80, apply, and the page recovers.

In your README, write what you saw for each trap and why. The EndpointSlice is what tells the two traps apart: empty means the selector is wrong; Pods listed on the wrong port means the targetPort is wrong.

Before you leave, you should be able to answer these without looking:

1. You built an image on your laptop, but the Pods using it are stuck in ImagePullBackOff. Why?

Model answer

The Pods run on the cluster's nodes, and each node has its own image storage. A node can't see the images in your laptop's Docker, so it tries to pull the image from a registry. If the image isn't in a registry the node can reach, the pull fails. Pushing the image to Docker Hub and using that name fixes it.

2. A Service exists but your browser can't reach the app. Its EndpointSlice is empty. What do you check first?

Model answer

The Service's selector against the Pods' labels. An empty EndpointSlice means no running Pod carries the labels the selector asks for. Compare spec.selector in the Service with the labels shown by kubectl get pods --show-labels.

3. In the Service, what is the difference between port: 8080 and targetPort: 80?

Model answer

port is where clients connect to the Service; today that was 8080 from the browser. targetPort is the port inside each selected Pod the traffic goes to. It must be where the app really listens, which is 80 for nginx here.

4. You deleted a Pod and a new one appeared. Which object created it, and why?

Model answer

The Deployment, through its ReplicaSet. It keeps comparing the number of running Pods with replicas. It saw two instead of three and created one more from the Pod template.

Common mistakes

  • Using hello-app:v1 in the manifest instead of <user>/hello-app:v1
  • Opening the EXTERNAL-IP instead of localhost:8080
  • Leaving the docker run test container or a Lab 1 container on port 8080
  • Indenting YAML with tabs, or putting containers: at the wrong level
  • Deleting the Deployment but forgetting the Service in Part 1
