Lab 3 — Running hello-app on Kubernetes with Terraform

Duration: 2 hours 30 minutes, plus an optional take-home on AWS. Working mode: solo. Everyone types every command on their own laptop.

In Lab 2 you ran hello-app on your 3-node cluster with kubectl. In this lab you describe the same Deployment and Service in Terraform files, and Terraform creates them. Then you update the app, catch changes made by hand, build a dev and a prod copy from one module, and break it on purpose. Everything runs on your laptop. The take-home at the end moves your state to AWS.

Before you start

Do this the night before, not in the lab.

  1. Install Terraform if you skipped it in lesson 16: on macOS brew install hashicorp/tap/terraform, on Windows winget install Hashicorp.Terraform. Check it: 
    terraform version
  2. Check that your cluster is running with three nodes: 
    kubectl config current-context    # docker-desktop
kubectl get nodes                 # 3 nodes, all Ready

You don't build an image in this lab. You use shripada/hello-app:v1 and shripada/hello-app:v2 from Docker Hub. v1 is the page from Lab 2. v2 says "v2" in the heading and highlights in green.

0:00–0:15 Set up your repository

  1. Open github.com/shripada/ms-cloud-devops-lab3, click Use this template → Create a new repository, name it ms-cloud-devops-lab3, and make it public.
  2. Clone your copy and move into it: 
    git clone https://github.com/<your-github-username>/ms-cloud-devops-lab3
cd ms-cloud-devops-lab3
  3. Open .gitignore and read it. It keeps .terraform/ and every terraform.tfstate file out of Git. You saw why in lesson 16: the state holds every setting in plain text.
  4. Clear anything left over from Lab 2: 
    kubectl get all
    If you see deployment.apps/hello-app or service/hello-app, delete them with kubectl delete service,deployment hello-app. Your Service needs port 8080, and later your prod copy needs 8090.
Checkpoint: terraform version works, three Ready nodes, your repository cloned, and no hello-app left in kubectl get all.

0:15–0:50 Part 1: write it in Terraform

Create main.tf in the root of your repository. Start with the provider and the variables:

terraform {
  required_providers {
    kubernetes = {
      source  = "hashicorp/kubernetes"
      version = "~> 3.4"
    }
  }
}

provider "kubernetes" {
  config_path    = "~/.kube/config"
  config_context = "docker-desktop"
}

variable "image_tag" {
  type    = string
  default = "v1"
}

variable "replicas" {
  type    = number
  default = 3
}

variable "port" {
  type    = number
  default = 8080
}

The provider block tells the Kubernetes plugin which cluster to talk to. It reads the same file kubectl uses, ~/.kube/config, and picks the docker-desktop context, so Terraform reaches the same cluster as kubectl.

Now add two resources. They hold the same settings as your hello-app.yaml from Lab 2, written in Terraform's language. Two differences in how you write them:

  • A list item in YAML (- name: hello-app under containers:) becomes a block: container { ... }. Two ports would be two port { ... } blocks.
  • Field names use underscores: containerPort becomes container_port, matchLabels becomes match_labels, targetPort becomes target_port.

Write them from this outline:

  • A kubernetes_deployment_v1 named hello. In metadata, the name hello-app. In spec: replicas = var.replicas, a selector with match_labels app = "hello-app", and a template with the same label and one container named hello-app, running "shripada/hello-app:${var.image_tag}", with container_port = 80.
  • A kubernetes_service_v1 named hello. In metadata, the name hello-app. In spec: type = "LoadBalancer", selector app = "hello-app", and one port with port = var.port and target_port = 80.
  • An output named url with the value "http://localhost:${var.port}".

Write it yourself before you open the hint below.

Hint: the rest of the file 
resource "kubernetes_deployment_v1" "hello" {
  metadata {
    name = "hello-app"
  }
  spec {
    replicas = var.replicas
    selector {
      match_labels = {
        app = "hello-app"
      }
    }
    template {
      metadata {
        labels = {
          app = "hello-app"
        }
      }
      spec {
        container {
          name  = "hello-app"
          image = "shripada/hello-app:${var.image_tag}"
          port {
            container_port = 80
          }
        }
      }
    }
  }
}

resource "kubernetes_service_v1" "hello" {
  metadata {
    name = "hello-app"
  }
  spec {
    type = "LoadBalancer"
    selector = {
      app = "hello-app"
    }
    port {
      port        = var.port
      target_port = 80
    }
  }
}

output "url" {
  value = "http://localhost:${var.port}"
}
  1. Download the provider, then let Terraform tidy your spacing and check the file: 
    terraform init
terraform fmt
terraform validate
    fmt lines up the = signs. validate catches typos such as containerPort before you go near the cluster.
  2. Predict first: how many resources will the plan create? Then: 
    terraform plan
    Find the Plan: line. Scroll up and find namespace = "default": you didn't write a namespace, so Terraform uses default, just as kubectl did. Paste the Plan: line into your README.
  3. Create it: 
    terraform apply
kubectl get pods -o wide
terraform output -raw url
    Type yes. Apply waits until all three Pods are ready before it says Apply complete!, so the first run can take half a minute while the nodes pull the image. Paste the output value into your README.
  4. Open http://localhost:8080. The table fills with three Pod names, the same names kubectl get pods shows.
  5. Predict first: what happens if you run terraform apply again without changing anything? Run it and check.
Checkpoint: the page shows three Pod names, and a second terraform apply says No changes.

0:50–1:05 Part 2: update the image

Keep the browser tab open on http://localhost:8080.

  1. In main.tf, change the default of image_tag from "v1" to "v2".
  2. Predict first: in lesson 16, changing the container's port made Terraform delete the container and create a new one. Will changing the image do the same here? 
    terraform plan
    Look for ~ update in-place, the line image = "shripada/hello-app:v1" -> "shripada/hello-app:v2", and Plan: 0 to add, 1 to change, 0 to destroy. Docker couldn't change a running container, so Terraform had to replace it. A Kubernetes Deployment can change its Pod template while it runs, so Terraform only updates it. Paste these lines into your README.
  3. Apply it, and watch the browser while it runs: 
    terraform apply
kubectl get rs
    New Pod names join the table one by one as the Deployment rolls out the new Pods and removes the old ones. The page you have open is still the old one, so refresh it: the heading now ends in v2 and the highlights are green. kubectl get rs shows the old ReplicaSet with 0 Pods and the new one with 3. It is the same rolling update you saw in lesson 13, started from a file.
Checkpoint: after a refresh, the page says v2, and terraform apply says No changes.

1:15–1:35 Part 3: catch changes made by hand

Once Terraform manages the app, every change should go through the code. But nothing stops anyone from running kubectl by hand, and in real teams someone always does. Your teammate needs more Pods for a demo and runs one quick command instead of changing the code. Play the teammate.

  1. Make the change by hand: 
    kubectl scale deployment hello-app --replicas=5
kubectl get pods
    Five Pod names appear in the browser.
  2. Predict first: main.tf didn't change. What will the plan show? 
    terraform plan
    ~ replicas = "5" -> "3" and 1 to change. Terraform read the real Deployment, compared it with the code, and found the difference. This is drift. Paste the plan into your README.
  3. Put it back with terraform apply. Two Pod names stop getting new answers in the browser.
  4. Now someone deletes the Service: 
    kubectl delete service hello-app
terraform plan
    The page shows an error. The plan says kubernetes_service_v1.hello will be created. Run terraform apply, and the page recovers.

The code is the record of what should exist. Once Terraform manages an object, changes go into main.tf. A kubectl change by hand lasts only until the next terraform apply.

Checkpoint: three Pods, the page works, and terraform plan says No changes.

1:35–2:05 Part 4: dev and prod from one module

The team wants two copies of hello-app: dev on port 8080 for testing, and prod on 8090. Each copy gets its own namespace. You will turn main.tf into a module, as in lesson 16, and call it from one folder per environment.

  1. Remove the single-folder copy so port 8080 is free, then make the folders and move the file: 
    terraform destroy
rm -rf .terraform .terraform.lock.hcl terraform.tfstate*
mkdir -p modules/hello-app envs/dev envs/prod
mv main.tf modules/hello-app/
  2. In modules/hello-app/main.tf, add a variable with no default, so every environment must choose its own namespace: 
    variable "namespace" {
  type = string
}
  3. Add a namespace resource, above the Deployment: 
    resource "kubernetes_namespace_v1" "env" {
  metadata {
    name = var.namespace
  }
}
  4. In the metadata of the Deployment and of the Service, add a namespace line under the name: 
      metadata {
    name      = "hello-app"
    namespace = kubernetes_namespace_v1.env.metadata[0].name
  }
    The Deployment and Service now refer to the namespace resource, so Terraform creates the namespace first.
  5. Write envs/dev/main.tf: 
    module "hello" {
  source    = "../../modules/hello-app"
  namespace = "dev"
  port      = 8080
}
    Write envs/prod/main.tf the same way, with "prod" and 8090. Your folders now look like this: 
    ms-cloud-devops-lab3/
├── modules/hello-app/
│   └── main.tf       # the code you wrote in Part 1, plus the namespace
└── envs/
    ├── dev/main.tf
    └── prod/main.tf
  6. Each environment folder is its own Terraform folder, so each needs its own init: 
    cd envs/dev  && terraform init && terraform apply
cd ../prod   && terraform init && terraform apply
kubectl get svc -A
    Two hello-app Services, one in dev on 8080 and one in prod on 8090. Open localhost:8080 and localhost:8090 side by side: different Pod names, because they are different Pods. Paste the kubectl get svc -A output into your README.
  7. Predict first: in envs/dev/main.tf, change "dev" to "development". What will happen to the running Pods? 
    cd ../dev
terraform plan
    Every resource says # forces replacement, and the plan is 3 to add, 0 to change, 3 to destroy. An object can't move to another namespace, so Terraform must delete it and create a new one. Don't apply it. Change the name back to "dev". Reading the plan before you type yes is what saves prod.
Checkpoint: both pages work, and terraform plan says No changes in both envs/dev and envs/prod.

2:05–2:20 Break it on purpose

Work in envs/dev. Keep both browser tabs open.

Trap 1 — the lost state file. Your laptop's disk "fails", and only the state file is lost. In envs/dev: 
rm terraform.tfstate
terraform plan
Predict first: the dev Pods are still running. What does the plan say? It says 3 to add: with no state, Terraform has no record that it ever made anything. Now run terraform apply and type yes. It fails with namespaces "dev" already exists. The state file is Terraform's only memory, and it links each resource in your code to a real object. (The terraform.tfstate.backup file is one step behind; don't rely on it.) Paste the error into your README.

To recover, delete what Terraform has forgotten, then apply again. Deleting a namespace deletes everything inside it:

kubectl delete namespace dev
terraform apply
On a laptop that's fine. On a real prod system you can't delete and recreate everything. That's why teams keep state in a remote backend. The take-home does exactly that.
Trap 2 — the wrong selector. In modules/hello-app/main.tf, in the Service, change the selector to app = "helo-app" (one l). From envs/dev: 
terraform apply
The plan shows "app" = "hello-app" -> "helo-app", and apply completes with no error. Now look at the dev page: it shows an error. The prod page still works, because you only applied in envs/dev. Find the cause: 
kubectl get endpointslices -n dev -l kubernetes.io/service-name=hello-app
The EndpointSlice is empty, the same as Lab 2's trap 2. Terraform checks that the cluster matches your code. It doesn't check that your code is right. Fix the typo, run terraform apply, and the page recovers. Write what you saw in your README.

  1. Fill in every section of README.md, and save a browser screenshot of the dev and prod pages as screenshot.png in the repository root.
  2. From the repository root, stage everything and check what Git will commit: 
    git add .
git status
    You should see the three main.tf files, the two .terraform.lock.hcl files, README.md and screenshot.png. If any terraform.tfstate file is listed, stop: your .gitignore is missing or broken.
  3. Commit and push, then check the files on GitHub: 
    git commit -m "Lab 3 submission"
git push
  4. Delete both environments: 
    cd envs/prod && terraform destroy
cd ../dev    && terraform destroy
kubectl get ns
    No dev or prod namespace is left. Skip this step if you are going to do the take-home tonight: it needs envs/dev running.

Before you leave, you should be able to answer these without looking:

1. You run terraform apply twice without changing anything. The second run says "No changes". What did Terraform do to decide that?

Model answer

It read the real Deployment and Service from the cluster, using the IDs saved in the state file, and compared their settings with the code. They already matched, so there was nothing to create, change or destroy.

2. Changing the image tag gave update in-place. Changing the namespace gave forces replacement. Why the difference?

Model answer

A Deployment can change its Pod template while it runs: Kubernetes rolls out new Pods with the new image, so Terraform only updates it. An object can't move to another namespace, so the only way is to delete it and create a new one. That means the running Pods go away, which is why you read the plan before typing yes.

3. Someone ran kubectl scale deployment hello-app --replicas=5. The code says 3. What does the next terraform plan show, and what does apply do?

Model answer

The plan shows drift: replicas = "5" -> "3", 1 to change. Apply sets the Deployment back to 3 replicas, so the hand change is lost. If 5 is really needed, the change goes into the code.

4. After you deleted terraform.tfstate, apply failed with "already exists". Why? Where should the state live in a team?

Model answer

The state file links each resource in the code to a real object. Without it, Terraform thought nothing existed and tried to create everything, and Kubernetes refused because the objects were still there. In a team, the state goes in a remote backend, such as an encrypted, versioned S3 bucket with locking, not on one laptop and not in Git.

5. terraform apply finished with no errors, but the page doesn't load. What does that tell you, and what do you check?

Model answer

It tells you the cluster now matches the code. It says nothing about whether the code is right. Check the Service's EndpointSlice: if it's empty, the selector doesn't match the Pods' labels. If it lists Pods on the wrong port, the target_port is wrong.

Common mistakes

  • Running Terraform in the wrong folder. The folder you are in is the environment you change: check with pwd before apply.
  • Forgetting terraform init in a new folder: you get Module not installed or Missing required provider.
  • Writing YAML names in Terraform: containerPort instead of container_port, or containers instead of container.
  • Leaving Lab 2's Service on port 8080, so the new Service's port clashes with it.
  • Changing an object with kubectl and being surprised when the next apply undoes it.
  • Committing a terraform.tfstate file. Always run git status before you commit.

Take-home Optional: move your state to AWS

In Trap 1, losing one file meant deleting and recreating dev. Here you create an S3 bucket with Terraform, catch a change someone makes in the AWS console, and then move envs/dev's state into that bucket, with locking.

Money first. This uses your own AWS account. One small S3 bucket costs a few paise at most, but a bill reaches you only if you forget something. Finish with the clean-up steps at the end, and check the Billing page in the console afterwards.
  1. Set up access. In the AWS console, create an IAM user for yourself (not the root user) with an access key. Then: 
    aws configure                 # region: ap-south-1
aws sts get-caller-identity   # shows your account and user
  2. Make sure envs/dev is running (terraform apply there, if you destroyed it).
  3. Create a folder aws in your repository with this main.tf. Bucket names are shared by every AWS account in the world, so put your GitHub username in yours (lowercase, no spaces): 
    terraform {
  required_providers {
    aws = {
      source  = "hashicorp/aws"
      version = "~> 6.0"
    }
  }
}

provider "aws" {
  region = "ap-south-1"
}

variable "bucket_name" {
  type    = string
  default = "<your-github-username>-lab3-state"
}

resource "aws_s3_bucket" "state" {
  bucket        = var.bucket_name
  force_destroy = true
}

resource "aws_s3_bucket_versioning" "state" {
  bucket = aws_s3_bucket.state.id
  versioning_configuration {
    status = "Enabled"
  }
}

resource "aws_s3_bucket_public_access_block" "state" {
  bucket                  = aws_s3_bucket.state.id
  block_public_acls       = true
  block_public_policy     = true
  ignore_public_acls      = true
  restrict_public_buckets = true
}

output "bucket" {
  value = aws_s3_bucket.state.bucket
}
    Versioning keeps every old copy of the state, so a bad write can be undone. The public access block makes sure nobody can make the bucket public. force_destroy = true lets terraform destroy delete the bucket even with files in it. It's there so you can clean up the lab; leave it out on a real state bucket.
  4. Create it, from the aws folder: 
    cd aws
terraform init
terraform apply
terraform output -raw bucket
  5. Drift on a real cloud. In the AWS console, open S3 → your bucket → Properties → Bucket Versioning → Edit → Suspend → Save changes. Then: 
    terraform plan
    ~ status = "Suspended" -> "Enabled". Run terraform apply and check the console again: versioning is back on. This is the drift from Part 3, on AWS.
  6. Move dev's state into the bucket. Create envs/dev/backend.tf, with your bucket name: 
    terraform {
  backend "s3" {
    bucket       = "<your-github-username>-lab3-state"
    key          = "dev/terraform.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true
  }
}
    Then, from envs/dev: 
    terraform init -migrate-state
    Terraform asks whether to copy the existing state to the new backend. Type yes. In the console, your bucket now has dev/terraform.tfstate.
  7. Repeat Trap 1. Delete the local state file, if it is still there, and plan: 
    rm -f terraform.tfstate terraform.tfstate.backup
terraform plan
    No changes. The laptop's copy is gone, but the state lives in S3, so Terraform still knows about everything it created.
  8. See the lock. Open a second terminal in envs/dev. In the first, run terraform apply and leave it waiting at the yes prompt. In the second, run terraform plan. It fails with Error acquiring the state lock, because the first terminal is holding the lock. Answer no in the first terminal, and the lock is released.

Add a section to your README with the drift plan and the lock error, then commit aws/main.tf, its .terraform.lock.hcl and envs/dev/backend.tf.

Go further: a registry. Add an aws_ecr_repository named hello to aws/main.tf, with name = "hello-app" and force_delete = true, plus an output registry_url with the value aws_ecr_repository.hello.repository_url. Apply. Then push the v2 image there, reading the address from the output instead of copying it: aws ecr get-login-password --region ap-south-1 | docker login --username AWS --password-stdin $(terraform output -raw registry_url | cut -d/ -f1), then docker pull shripada/hello-app:v2, docker tag shripada/hello-app:v2 $(terraform output -raw registry_url):v2 and docker push $(terraform output -raw registry_url):v2. The image now shows up under ECR in the console.

Clean up, in this order:

  1. Delete dev. Its state is in S3, so run this from envs/dev while the bucket still exists: 
    terraform destroy
  2. Delete the bucket (and the registry, if you made one), from aws: 
    terraform destroy
  3. Delete envs/dev/backend.tf and commit, because the bucket it points to no longer exists. In the console, check that S3 and ECR are empty, then check Billing.
