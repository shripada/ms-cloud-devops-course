Services

Why this matters for DevOps

In lesson 9 you saw that a replaced Pod gets a new name and a new IP. Now think about the app you will deploy in this module: a React frontend that calls an Express backend, which talks to PostgreSQL. The backend runs as three Pods, and any of them can be replaced at any moment. Which IP should the frontend call? One Pod's IP might be gone in five minutes. A list of all three keeps changing.

You have seen the answer before. In lesson 5, Compose let containers reach each other by service name, like backend:3000, without knowing any IP. Kubernetes has the same idea, built for a cluster where Pods keep moving: the Service. Every real Kubernetes app uses Services, and “how does traffic reach a Pod?” is a standard interview question. [Kubernetes docs: Service]

Three ideas, no more

Service: a fixed name and a fixed virtual IP (the ClusterIP) in front of a group of Pods. The Service doesn't list Pods by name. It has a selector, such as app=who, and it sends traffic to whichever Pods carry that label right now. A controller keeps a live list of those Pods' IPs, called an EndpointSlice. When a Pod is replaced, the list updates in seconds, while the Service's own name and IP never change. [Kubernetes docs: EndpointSlices]

DNS: the cluster runs its own DNS server, CoreDNS (you saw its Pods in kube-system in lesson 9). Every Service gets a DNS name. From a Pod in the same namespace, the short name who is enough. The full name is who.default.svc.cluster.local: Service name, namespace, then the cluster's suffix. [Kubernetes docs: DNS for Services and Pods]

kube-proxy: the ClusterIP is not a real machine, and no process listens on it. kube-proxy, the Pod you saw once on every node, writes network rules into each node's Linux kernel. Those rules catch any packet sent to the ClusterIP and redirect it to one of the Pods in the EndpointSlice. That is how one Service shares requests between several Pods. [Kubernetes docs: Virtual IPs and service proxies]

Think of your college office's landline number. The staff at the desk change every shift, but students always dial the same number, and whoever is on duty picks up. The landline number is the Service. The staff on duty today are the Pods. The office's duty roster, updated every shift, is the EndpointSlice.

Three types of Service

TypeReachable fromUsed for
ClusterIP (default)Only inside the clusterPod-to-Pod traffic, for example frontend to backend, or backend to database
NodePortA port between 30000 and 32767 on every node's IPRarely used directly. It's the building block for LoadBalancer.
LoadBalancerOutside the cluster, through an external load balancerLetting users in. On AWS, this creates a real AWS load balancer.

Before you start

You need the three-node cluster from lesson 9, and an empty default namespace. Check that your commands go to the right cluster first:

kubectl config current-context
kubectl get nodes

You should see docker-desktop (option 1) or minikube (option 2), and three Ready nodes.

Do it

  1. Start an app that tells you which Pod answered. The nginx page looks the same from every Pod, so we use traefik/whoami, a tiny web server that replies with its own Pod name: 
    kubectl create deployment who --image=traefik/whoami --replicas=3
kubectl rollout status deployment/who
kubectl get pods -l app=who -o wide
    Note the three Pod IPs. Pods on the same node share a range, for example 10.244.1.x on one worker and 10.244.2.x on the other.
  2. Create a Service in front of them: 
    kubectl expose deployment who --port=80
kubectl get service who -o wide
kubectl get endpointslices -l kubernetes.io/service-name=who
    expose copies the Deployment's selector, app=who, into the Service. The ClusterIP looks like 10.96.x.x, a different range from the Pods. It's a virtual address that only Services use. The ENDPOINTS column lists exactly the three Pod IPs from step 1.
  3. Before looking at the Service, look at the Deployment it points to. Kubernetes stores every object as structured data, and -o yaml prints it in a format called YAML: 
    kubectl get deployment who -o yaml
    The output is long, because Kubernetes adds many fields of its own. Trimmed to the parts that matter, it looks like this: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: who
spec:
  replicas: 3
  selector:
    matchLabels:
      app: who
  template:
    metadata:
      labels:
        app: who
    spec:
      containers:
        - name: whoami
          image: traefik/whoami
    Indentation shows what belongs to what: replicas, selector and template are all inside spec. A line starting with - is one item in a list. containers is a list because one Pod can run several containers. You'll recognise the --replicas=3 and --image you typed in step 1. template is the blueprint for each Pod, and its labels give every Pod the label app=who. Remember that label: the Service is about to use it.
  4. Now see what expose created, in the same way: 
    kubectl get service who -o yaml
    Trimmed: 
    apiVersion: v1
kind: Service
metadata:
  name: who
spec:
  type: ClusterIP
  clusterIP: 10.96.143.20
  selector:
    app: who
  ports:
    - port: 80
      protocol: TCP
      targetPort: 80
    ports is a list because one Service can open several ports. Now read spec:
    • type: ClusterIP: the default type, reachable only inside the cluster.
    • selector: app: who: send traffic to Pods with the label app=who, the label from the Deployment's template in step 3.
    • port: 80: the port the Service listens on. Clients call who:80, and http://who means port 80.
    • targetPort: 80: the port inside the container that traffic is forwarded to. Here they happen to be the same. Step 8 makes them different.
    kubectl expose is just a quick way of writing this object for you. In lesson 11 you will write files like this yourself.
  5. A ClusterIP Service is only reachable from inside the cluster, so start a throwaway Pod to act as a client. -it gives you a shell inside it, and --rm deletes the Pod when you exit: 
    kubectl run tmp --rm -it --image=busybox:1.36 -- sh
    At the / # prompt, call the Service by name a few times: 
    wget -qO- http://who | grep Hostname
wget -qO- http://who | grep Hostname
wget -qO- http://who | grep Hostname
wget -qO- http://who | grep Hostname
    The Hostname changes between Pod names: kube-proxy is sharing your requests between the three Pods. Now try the full DNS name, and then try to ping the Service: 
    wget -qO- http://who.default.svc.cluster.local | grep Hostname
ping -c 2 who
    DNS resolves who to the ClusterIP, but the ping gets no reply. That's expected. The ClusterIP is not a machine, and kube-proxy's rules only forward the Service's port (80, over TCP). Ping uses a different protocol, so nothing answers it. Type exit to leave; the Pod is deleted.
  6. Now replace every Pod and check what changes: 
    kubectl delete pods -l app=who
kubectl rollout status deployment/who
kubectl get service who
kubectl get endpointslices -l kubernetes.io/service-name=who
    The Service's ClusterIP is exactly the same. The EndpointSlice shows three new Pod IPs. A client calling http://who never notices the change. This is the whole point of a Service.
  7. Break it on purpose. Scale to zero and look again: 
    kubectl scale deployment/who --replicas=0
kubectl get endpointslices -l kubernetes.io/service-name=who
kubectl run tmp --rm -it --image=busybox:1.36 -- wget -qO- -T 3 http://who
    The endpoints show <unset>, and wget fails with Connection refused. The Service still exists and DNS still works, but there is no Pod behind it. Remember this pattern: when a Service “doesn't work”, check its endpoints first. Empty endpoints mean no running, ready Pod matches the selector. Bring the Pods back: 
    kubectl scale deployment/who --replicas=3
  8. Open the app to your laptop with a LoadBalancer Service. --port is the port the Service listens on. --target-port is the port the container listens on: 
    kubectl expose deployment who --name=who-lb --type=LoadBalancer --port=8099 --target-port=80
kubectl get service who-lb
    Option 1 (Docker Desktop): the EXTERNAL-IP fills in within a few seconds, and Docker Desktop also forwards the port to your laptop. Open http://localhost:8099 and refresh a few times. The Hostname line changes as different Pods answer.
    Option 2 (minikube): in a separate terminal, run minikube tunnel and leave it running (it may ask for your password). Then open http://localhost:8099.
    Look at the PORT(S) column: something like 8099:31233/TCP. The second number is a NodePort. A LoadBalancer Service is built on top of a NodePort: the external load balancer sends traffic to that port on the nodes, and kube-proxy takes it from there. On AWS the load balancer is a real AWS one. On your laptop, Docker Desktop plays that role. You can't open the NodePort yourself on this setup, because the nodes live inside Docker Desktop's virtual machine.
    Print this Service as YAML too, with kubectl get service who-lb -o yaml. Its spec, trimmed: 
    spec:
  type: LoadBalancer
  selector:
    app: who
  ports:
    - nodePort: 31233
      port: 8099
      protocol: TCP
      targetPort: 80
    Kubernetes prints fields in alphabetical order, so nodePort comes first. Three different ports, three different jobs: port (8099) is where the Service listens, targetPort (80) is where the container listens, and nodePort (31233) is the port opened on every node. You didn't ask for a nodePort, so Kubernetes picked a free one between 30000 and 32767. In a YAML file you can choose it yourself, for example nodePort: 30090.
  9. Clean up. The Services don't belong to the Deployment, so delete them separately: 
    kubectl delete deployment who
kubectl delete service who who-lb
kubectl get all
    Only the built-in kubernetes Service should remain. It's how Pods inside the cluster reach the API server.
Stretch: the most common Service bug at work is a selector that matches no Pods, often from a typo in a label. Create the who Deployment again, then make a Service by hand: kubectl create service clusterip broken --tcp=80:80. Run kubectl describe service broken, then answer: what is its selector, why are its endpoints empty, and how would you fix it? (Hint: compare with kubectl get pods --show-labels.)

Practice questions

5 marks · 9 minutes

A college fest website has a React frontend that must be reachable from the internet, a Django API used by the frontend, and a MySQL database used only by the API.

  1. [1]Analyze the Service types ClusterIP, NodePort and LoadBalancer.
  2. [3]Choose one for each of the three components, and justify each choice.
  3. [1]Explain how the API Pod reaches the database using the name mysql.fest.svc.cluster.local.
Model answer and marking
  • The three types: ClusterIP (the default) gives a fixed name and IP that work only inside the cluster. NodePort also opens a port between 30000 and 32767 on every node. LoadBalancer also puts an external load balancer in front, so users outside the cluster can reach it.
  • Frontend: LoadBalancer. It's the only part users must reach from the internet. On AWS this creates a real load balancer with one public address.
  • Django API: ClusterIP. Only the frontend calls it, from inside the cluster, so there's no reason to open it to the outside.
  • MySQL: ClusterIP. Only the API uses it. A database open to the internet invites attacks and data theft.
  • How the name works: CoreDNS, the cluster's own DNS server, turns mysql.fest.svc.cluster.local (Service mysql, namespace fest, then the cluster suffix) into the Service's ClusterIP. The API connects to that IP on port 3306, and kube-proxy's rules send the connection on to a MySQL Pod. If the MySQL Pod is replaced, the name and the ClusterIP stay the same. From inside the fest namespace, just mysql works.

Marking (5): three Service types 1; choice and justification for each component 3 (1 each); how the name resolves 1.

5 marks · 9 minutes

The frontend of an exam-results website runs as three replicas behind a NodePort Service on node port 31000.

  1. [3]With a diagram, analyze the path a browser request takes from the node's port through kube-proxy and the Service to one of the Pods.
  2. [2]Examine what happens to requests if the node running one of the Pods fails.
Model answer and marking 
Browser ──► http://<any node IP>:31000
               │
        ┌──────▼───────── Node A ──────────────┐
        │ kube-proxy's rules catch port 31000  │
        │ and pick one Pod from the Service's  │
        │ EndpointSlice                        │
        └──────┬──────────────┬──────────────┬─┘
               ▼              ▼              ▼
         Pod 10.244.1.5  Pod 10.244.1.6  Pod 10.244.2.8 (on Node B)
           :8080           :8080           :8080   (targetPort)
  • Path: the browser connects to port 31000 on any node's IP. Every node opens this port, even a node with no frontend Pod on it. kube-proxy has written rules on each node that catch traffic to port 31000 and pick one of the Pods in the Service's EndpointSlice. The request goes to that Pod's IP on the targetPort, 8080, even if the Pod is on another node. The reply comes back the same way. Because a different Pod can be picked for each request, the three replicas share the load.
  • A node running one Pod fails: if the browser was using that node's IP, its requests fail, because nothing answers there. That's why real setups put a load balancer in front, which sends traffic only to working nodes. Requests through the other nodes keep working. For a short time some may still be sent to the dead Pod, until Kubernetes notices the node is down and removes that Pod from the EndpointSlice. Then all traffic goes to the two remaining Pods. As in lesson 9, the Deployment creates a replacement Pod on a healthy node, and it joins the EndpointSlice once it's running.

Marking (5): traffic path with diagram 3; node failure analysis 2.

Compare with a model answer

Pods are disposable, and each replacement gets a new IP, so clients can't rely on Pod IPs. A Service gives a group of Pods one stable DNS name and one virtual IP, the ClusterIP. It picks its Pods with a label selector, and a controller keeps an EndpointSlice listing the IPs of the ready Pods that match. When a client calls the Service by name, CoreDNS resolves the name to the ClusterIP. kube-proxy, which runs on every node, has written kernel rules that catch traffic to that ClusterIP and forward it to one of the Pods in the EndpointSlice, which spreads the load. ClusterIP is the default and only works inside the cluster. NodePort opens a port on every node, and LoadBalancer puts a cloud load balancer in front of that to let outside traffic in.
