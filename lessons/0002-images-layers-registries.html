Images, layers & registries

Today's goal: read an image's full name, see the layers inside it, and prove that two images share storage. About 20 minutes.

Why this matters for DevOps

Every deployment finally comes down to one question: “Which image, exactly?” Using the wrong tag, shipping a 1 GB image, or pulling from the wrong registry are everyday problems in real projects. If you understand how an image is named and stored, you can find and fix these problems quickly.

Three ideas, no more

An image name has parts. In lesson 1 you typed only nginx. Docker expanded it to docker.io/library/nginx:latest, which is registry / repository : tag. Docker Hub (docker.io) is the default registry and latest is the default tag. It is like a full postal address: if you skip the city and PIN code, Docker fills in the defaults. [Docker docs]

Tags can move. Digests cannot. A tag like nginx:1.27 is just a label. The publisher can point it to a newer build tomorrow. A digest (sha256:…) is a hash of the image content, so it always means exactly those bytes. Think of a tag as a class name like “CSE-A”, which gets new students every year, and the digest as one student's roll number, which never changes. Production pipelines often use the digest for this reason. [Docker docs]

An image is a stack of read-only layers. Each layer is a set of file changes. Images built on the same base share the same layers on disk, and Docker only downloads the layers you don't already have. When a container runs, Docker adds one thin writable layer on top. [Docker docs]

A common confusion: latest gives you whatever latest points to on the day you pull. It does not mean “newest version on your machine”, and your copy does not update by itself.

Do it

  1. Pull a second variant of nginx and compare the sizes: 
    docker pull nginx:alpine
docker images nginx
    The alpine variant is built on Alpine Linux, which is very small. So it should be several times smaller than latest.
  2. Look inside the layers. Each row is one build step. Some rows add files and some only change settings (these show 0B): 
    docker image history nginx:alpine
  3. Find the layer hashes and the digest: 
    docker image inspect nginx:alpine --format '{{json .RootFS.Layers}}'
docker images --digests nginx
  4. Pull the base image separately and watch what happens: 
    docker pull alpine
    Now compare the first layer of both images: 
    docker image inspect alpine --format '{{index .RootFS.Layers 0}}'
docker image inspect nginx:alpine --format '{{index .RootFS.Layers 0}}'
    If the two hashes match, nginx:alpine is built on the same Alpine base, and that layer is stored only once on your disk. If they don't match, the two tags were built from different Alpine releases. That is a live example of “tags move”.
  5. Give an image a second name. docker tag only adds a label. It copies no data: 
    docker tag nginx:alpine my-nginx:v1
docker images
    Both rows show the same IMAGE ID. It is one image with two names, like one person with a real name and a hostel nickname.
  6. Check how much disk space Docker is using: 
    docker system df
  7. Clean up. Removing a tag only removes that name. The image data is deleted only when its last name is removed: 
    docker rmi my-nginx:v1
docker rmi nginx:latest
Stretch (needs a free Docker Hub account): run docker login, then docker tag nginx:alpine YOUR-USER/my-nginx:v1 and docker push YOUR-USER/my-nginx:v1. Read the output: most layers say Mounted from library/nginx or Layer already exists. The registry also skips layers it already has.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. What is the full name Docker uses for redis?

2. Your deployment must run exactly the same bytes every time, even months from now. What do you use?

3. You already have alpine. Why does pulling nginx:alpine skip one layer?

4. After docker tag nginx:alpine my-nginx:v1, how much extra disk space is used?

5. Interview practice (say it out loud or type it): “What are image layers, and why do they make Docker efficient?”

Compare with a model answer

An image is a stack of read-only layers. Each layer is a set of file changes from one build step, identified by a hash of its content. Because of this, images built on the same base share those layers on disk and in registries, so a pull or push only transfers what is missing. A container adds a thin writable layer on top, which is why many containers can start from one image cheaply.
