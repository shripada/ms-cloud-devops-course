Infrastructure as code with Terraform

Why this matters for DevOps

So far someone had to create the cluster before you could use it. In a company that means a network (VPC), a Kubernetes cluster, worker nodes, a registry, DNS records, all in the cloud. Clicking these together in the AWS console works once. Then a new teammate asks “how was prod set up?” and nobody remembers. Dev and prod slowly become different. Someone changes a setting at 2 a.m. and it's never written down. Infrastructure as code (IaC) fixes this the same way Git fixed source code: the setup lives in files, changes go through a pull request, and anyone can rebuild it from scratch.

Three ideas, no more

Declarative code, providers: you write what should exist (“one container called web-dev, port 8081”), not the steps to create it. Like a Kubernetes manifest, but for cloud resources. Terraform itself knows nothing about AWS or Docker. A provider is a plugin that talks to one API: the aws provider, the cloudflare provider, the docker provider. One tool and one language, many providers. [Terraform docs: Providers]

The workflow: init, plan, apply, destroy: init downloads the providers. plan compares your code with what really exists and prints what it would do: + create, ~ change, - destroy, -/+ replace. Nothing changes yet. apply does it. destroy deletes everything the code manages. The plan is what reviewers read in a pull request. [Terraform docs: Core workflow]

State: Terraform keeps a file, terraform.tfstate, that maps each resource in your code to the real thing it created (“docker_container.web is container 93c6…”). That's how plan knows what to compare. In a team the state can't live on one laptop: it goes in a remote backend (an S3 bucket on AWS), with a lock so two engineers running apply at the same moment can't corrupt it. [Terraform docs: State]

Think of a building plan approved by the municipal office. The drawing (code) says what the house should look like. The site register (state) records what has actually been built and where. Before any work, the engineer compares drawing with site and lists the changes (plan). Only one contractor holds the register at a time (lock). If someone adds a room without approval, the next inspection finds it (drift).

Before you start

Docker Desktop running. Install Terraform: on macOS brew install hashicorp/tap/terraform, on Windows winget install Hashicorp.Terraform. Check with terraform version. Make a new folder, iac-demo, and open it in your editor.

One macOS trap first. The Docker provider looks for Docker at /var/run/docker.sock, and Docker Desktop on macOS doesn't create that file unless you turn on a setting. Point the provider at the right place, in every terminal you use today:

export DOCKER_HOST=$(docker context inspect -f '{{.Endpoints.docker.Host}}')
echo $DOCKER_HOST

Without this, apply fails with Cannot connect to the Docker daemon at unix:///var/run/docker.sock. Windows users can skip this step.

Do it: plan, apply, destroy

  1. Create main.tf: 
    terraform {
  required_providers {
    docker = {
      source  = "kreuzwerker/docker"
      version = "~> 3.6"
    }
  }
}

provider "docker" {}

variable "env" {
  type    = string
  default = "dev"
}

variable "port" {
  type    = number
  default = 8081
}

resource "docker_image" "web" {
  name         = "nginx:1.27-alpine"
  keep_locally = true
}

resource "docker_container" "web" {
  name  = "web-${var.env}"
  image = docker_image.web.image_id
  ports {
    internal = 80
    external = var.port
  }
}

output "url" {
  value = "http://localhost:${var.port}"
}
    Read it top to bottom. required_providers says which plugin and which version. Two variables with defaults. Two resources: each has a type (docker_container) and a name you choose (web). docker_image.web.image_id refers to the image resource, so Terraform knows to create the image first. keep_locally = true stops destroy from deleting the nginx image from your laptop. The output prints a value after apply.
  2. Download the provider: 
    terraform init
ls -a
    You get a .terraform/ folder (the plugin) and .terraform.lock.hcl (the exact provider version, like package-lock.json). Commit the lock file; never commit .terraform/.
  3. Predict first: how many resources will the plan create? Then: 
    terraform plan
    Plan: 2 to add, 0 to change, 0 to destroy. Each + line is a setting that will be created. Values marked (known after apply), like the container ID, only exist once Docker makes them. Nothing has been created yet: docker ps shows no web-dev.
  4. Create it: 
    terraform apply
curl -s localhost:8081 | grep title
terraform state list
terraform output -raw url
    apply shows the plan again and waits for you to type yes. Then nginx answers on 8081. state list shows the two resources Terraform now tracks. output -raw prints just the value, with no quotes, which is how a CI pipeline reads it. On AWS the output would be the registry URL or the cluster endpoint, so nobody copies it by hand.
  5. Predict first: what happens if you run terraform apply again without changing anything? 
    terraform apply
    No changes. Your infrastructure matches the configuration. A shell script with docker run would fail the second time (“name already in use”). Terraform compares first, then changes only the difference. This is called idempotent: running it once or ten times gives the same result.
  6. Change the code. Set the port default to 8082 and plan: 
    terraform plan
    Look for external = 8081 -> 8082 # forces replacement and Plan: 1 to add, 0 to change, 1 to destroy. Docker can't change a running container's port, so Terraform must delete it and make a new one. The plan warns you before anything happens. On AWS, the same forces replacement on a database means you lose its data, so reviewers look for that line. Set the port back to 8081.

Do it: drift, state and environments

  1. Someone “just fixes something quickly” by hand, outside Terraform: 
    docker update --restart=always web-dev
terraform plan
    Terraform reads the real container, compares it with the code, and shows ~ restart = "always" -> "no", 1 to change. This is drift: the real thing no longer matches the code. terraform apply puts it back. Now delete it by hand and plan again: 
    docker rm -f web-dev
terraform plan
    docker_container.web will be created. Terraform noticed it's gone and will recreate it. Run terraform apply. The same happens on AWS when someone turns off versioning on an S3 bucket in the console: the next plan shows it, and apply turns it back on. Many teams run terraform plan on a schedule in CI just to catch drift.
  2. Look inside the state: 
    terraform state show docker_container.web | head -15
grep -c '"type"' terraform.tfstate
    It holds every setting of every resource, in plain text. On AWS that includes database passwords. So: never commit terraform.tfstate to Git (add it to .gitignore), and in a team keep it in a remote backend: 
    terraform {
  backend "s3" {
    bucket       = "shop-terraform-state"
    key          = "prod/terraform.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true
  }
}
    The bucket is encrypted and only the team and the CI pipeline can read it. use_lockfile makes Terraform write a lock object next to the state during plan and apply. If Priya is applying and Arjun runs apply too, Arjun gets Error acquiring the state lock and waits, instead of both writing the state at once and corrupting it. (Older setups use a DynamoDB table for the lock; you'll see both.) We don't run this today: it needs an AWS account.
  3. Same code, second environment. A workspace gives the same code a separate state: 
    terraform workspace new prod
terraform apply -var env=prod -var port=8090
docker ps --format '{{.Names}} {{.Ports}}'
terraform workspace list
    Two containers, web-dev on 8081 and web-prod on 8090, from one main.tf. Each has its own state (look in terraform.tfstate.d/prod/). In real projects the values usually live in small files, dev.tfvars and prod.tfvars, used with -var-file=prod.tfvars, and prod gets bigger nodes and more of them. Same code, so dev really does match prod except for those values.
  4. Clean up both environments: 
    terraform destroy -var env=prod -var port=8090
terraform workspace select default
terraform destroy
docker ps -a | grep web
    Nothing left. On AWS, destroy at the end of a practice session is what keeps your bill at zero.

What the AWS version looks like

You won't run this today, but read it: it's the same shape. A provider, variables, and resources that refer to each other. (Real EKS code usually uses the community terraform-aws-modules/eks module rather than writing every resource.)

provider "aws" { region = "ap-south-1" }

variable "node_count"    { type = number }
variable "instance_type" { type = string }

module "eks" {
  source          = "terraform-aws-modules/eks/aws"
  cluster_name    = "shop-${terraform.workspace}"
  # ... VPC and subnets ...
  eks_managed_node_groups = {
    default = {
      instance_types = [var.instance_type]
      desired_size   = var.node_count
    }
  }
}

resource "aws_ecr_repository" "api" { name = "shop/api" }

output "registry_url" { value = aws_ecr_repository.api.repository_url }

A pull request changes node_count in prod.tfvars from 3 to 5. CI runs terraform plan and posts the result on the pull request: 1 to change. A teammate reviews it, merges, and the pipeline runs apply against the remote state. No one clicks in the console.

Drill: spot the problems. A team describes how they use Terraform for their AWS setup. Find four practices that will cause trouble, and say what to do instead. 
1. terraform.tfstate is committed to the Git repo so everyone has a copy.
2. Each engineer runs terraform apply from their own laptop whenever they need to.
3. The database password is written in main.tf: password = "Shop@123".
4. When a change is urgent, they make it in the AWS console and "update the
   code later".
Show the answer

1. State in Git: it holds secrets in plain text, and two people's copies get out of sync, so plans are wrong. Use a remote backend (S3, encrypted) and add *.tfstate to .gitignore. 2. No locking, no review: two applies at once can corrupt the state, and changes skip review. Turn on state locking, and run plan and apply from CI after a pull request is approved. 3. Password in code: it's in Git history forever. Pass it as a sensitive variable from a secrets store (AWS Secrets Manager, or a CI secret), or let AWS generate and manage it. 4. Console changes: this is drift. The next apply undoes the urgent fix, or the code never gets updated. Make the change in code, even when urgent; scheduled plan runs catch anything that slips through.

Practice questions

5 marks · 9 minutes

A college's placement portal is moving to AWS. Its VPC, EKS cluster, worker node group and private registry are created by clicking in the console. The test environment no longer matches production, and nobody can tell who changed what. DNS is hosted with Cloudflare. The team needs:

  • every resource, including the Cloudflare DNS records, described in files kept in Git
  • a preview of every change before it is made
  • an identical copy of the environment on demand, removed completely when the work is done
  1. [1]Choose a suitable tool and justify the choice.
  2. [1]Show how this environment, including the Cloudflare records, is described in files.
  3. [1]Apply the tool: show how a change travels from a file in Git to the AWS account.
  4. [1]Explain how the tool keeps track of the resources it has created here.
  5. [1]Use this to show how the team previews changes and removes the whole environment.
Model answer and marking
  • Tool: Terraform (or OpenTofu). Declarative files kept in Git; plan previews every change; apply and destroy create and remove everything; and through providers one tool manages both AWS (the aws provider) and Cloudflare (the cloudflare provider). CloudFormation or CDK can't manage the Cloudflare records; console clicks and CLI scripts give no preview and no record.
  • From Git to AWS: the VPC, cluster, node group, registry and DNS records are declared in .tf files. A change is made in a branch and opened as a pull request; CI runs terraform plan and posts the output; a reviewer approves; after merge, the pipeline runs terraform apply, which calls the AWS and Cloudflare APIs to make the real resources match.
  • Keeping track: the state file maps each resource in the code to the real resource's ID. It's kept in a remote backend (an encrypted S3 bucket, with locking), not on a laptop or in Git.
  • Preview and remove: plan reads the current settings of the resources in the state, compares them with the code, and lists what will be created, changed, replaced or destroyed, before anything happens. An identical copy is the same code applied with a separate state (a workspace or another state key) and its own variables. destroy deletes everything recorded in that state, so nothing is left behind or forgotten.

Marking (5): tool choice with justification covering Git, preview, repeatability and both providers 1; environment described as files with providers 1; Git-to-AWS workflow with plan and apply 1; role of the state file 1; how state enables preview and destroy 1. Exact syntax isn't required.

5 marks · 9 minutes

An ed-tech start-up needs the same AWS platform (VPC, EKS cluster, worker node group) in staging and prod, differing only in the node instance type and number of nodes. Recently, three engineers' changes have overwritten each other. The team needs:

  • every change reviewed as code
  • a preview before anything is changed
  • a shared record of what exists in each environment that only one person can change at a time
  1. [1]Choose a suitable tool and justify the choice.
  2. [1]Show how one set of files creates both environments.
  3. [2]Show where the record of what exists should be kept, and why.
  4. [1]Apply it: show how this stops the engineers' changes from overwriting each other.
Model answer and marking
  • Tool: Terraform (or OpenTofu): code reviewed in Git, plan as a preview, and a remote state with locking. (CloudFormation, with change sets and stack-level locking, can be justified too.)
  • One set of files, two environments: the VPC, cluster and node group are written once, with input variables such as instance_type and node_count. Each environment has a small values file, staging.tfvars (for example 2 × t3.medium) and prod.tfvars (5 × m5.large), and its own state (a workspace or a separate state key). The environments differ only where the values differ.
  • Where the record lives: the state file maps every resource to what really exists. It goes in a remote backend, an S3 bucket with encryption and versioning and restricted access, with one state per environment. Not on a laptop, where others can't see it and it gets out of date, and not in Git, because it holds secrets in plain text and two copies drift apart.
  • No overwriting: state locking (use_lockfile in S3, or a DynamoDB table). While one engineer's plan or apply runs, the state is locked; a second engineer gets “Error acquiring the state lock” and waits. Because every plan starts from the latest shared state, nobody applies over someone else's change from an old copy. Running apply only from CI after review makes this stronger.

Marking (5): tool choice and justification 1; one set of files with variables per environment 1; remote state, where and why 2; locking prevents overwrites 1. Exact syntax isn't required.

5 marks · 9 minutes

A food-delivery company's AWS account needs a private container registry, an S3 bucket for invoice PDFs with public access blocked, and an IAM role for the EKS worker nodes. Someone turned off “Block public access” in the console, and nobody noticed for a week. The team needs:

  • these resources written as code
  • a way to find out when the real account no longer matches the code, and put it back
  • the bucket name passed automatically to the CI pipeline that uploads invoices
  1. [1]Choose a suitable tool and justify the choice.
  2. [2]Show how the tool finds the change made in the console.
  3. [1]Show how it puts the bucket back.
  4. [1]Show how the bucket name is handed to the CI pipeline.
Model answer and marking
  • Tool: Terraform (or OpenTofu): plan compares the real account with the code and shows any difference, apply puts it back, and output values pass results to other tools. (CloudFormation's drift detection finds the change, but a stack update won't undo a console change to a resource whose template hasn't changed, so it needs extra steps.)
  • Finding the change: Terraform keeps a state file of the resources it manages. On every plan it reads the current settings of each one from the AWS API and compares them with the code. The bucket shows as a change, for example block_public_acls: false -> true. Running terraform plan on a schedule in CI (say every night) and alerting when it isn't empty would have caught this the same day, not a week later.
  • Putting it back: terraform apply sets the bucket back to what the code says. Then the team finds out who made the console change and why, and either adds it to the code properly or limits console write access.
  • Bucket name to CI: the code declares output "invoice_bucket" { value = aws_s3_bucket.invoices.bucket }. After apply, the pipeline reads it with terraform output -raw invoice_bucket, or Terraform writes it to a shared parameter store (SSM Parameter Store) that CI reads. Nobody copies it by hand.

Marking (5): tool choice and justification 1; how the console change is found 2; how the bucket is put back 1; how the bucket name reaches CI 1. Exact syntax isn't required.

Check yourself

Answer before clicking.

1. What does terraform plan change in your cloud account?

2. Two engineers run terraform apply on prod at the same moment. The state is in S3 with locking on. What happens?

3. Someone turned off versioning on an S3 bucket in the console. Terraform manages that bucket. What does the next terraform plan show?

4. One team needs to manage both AWS resources and Cloudflare DNS records. Why does Terraform fit?

5. Exit question: “Your team creates dev and prod EKS clusters by clicking in the AWS console. Convince them to use Terraform. Explain how it would work from Git to AWS, and how two engineers avoid overwriting each other.”

Compare with a model answer

With console clicks, nobody can see how prod was built, dev and prod drift apart, and rebuilding after a mistake means remembering every click. With Terraform the VPC, cluster, node group and registry are declared in .tf files in Git, using the AWS provider. Dev and prod use the same code with different variable files, for example 2 small nodes in dev and 5 larger ones in prod, so they differ only where we choose. A change starts in a branch; CI runs terraform plan and posts it on the pull request, so reviewers see exactly what will be created, changed or replaced before anything happens. After approval, the pipeline runs apply. Terraform records what exists in a state file, which we keep in an encrypted S3 bucket, not in Git, because it contains secrets. State locking means only one apply runs at a time: if two engineers try at once, the second gets a lock error and waits, so the state can't be corrupted. Running plan on a schedule also catches drift from anyone who changes things in the console, and apply puts it back.
