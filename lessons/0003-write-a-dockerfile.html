Write a Dockerfile

Today's goal: package your own Python app and a Node.js app as images, run them, and make rebuilds fast. About 35 minutes.

Why this matters for DevOps

So far you have only used images that other people built. In a real job, you write the image for your team's app. In placement interviews, one of the most common tasks is “write a Dockerfile for this app”. Interviewers then ask why you ordered the lines the way you did. By the end of this lesson you can answer both.

Three ideas, no more

A Dockerfile is a recipe. It is a plain text file with step-by-step instructions: start from this base image, copy these files, run this command. docker build follows the recipe and produces an image. If you have written a Makefile or a build script in college, it is the same idea. [Dockerfile reference]

Each instruction becomes a layer, and layers are cached. You saw layers in lesson 2. When you rebuild, Docker reuses a layer if its instruction and its input files have not changed. The moment one layer changes, every layer after it is rebuilt. So you put things that change rarely (dependencies) at the top and things that change often (your code) at the bottom. [Docker docs: build cache]

RUN happens at build time. CMD happens at run time. RUN pip install … executes once, while the image is being built, and the result is saved in a layer. CMD only records the command to start when someone does docker run. Think of it like compile time versus run time in C.

Tiffin analogy: RUN is cooking the food at home in the morning. CMD is the note on the box saying “open and eat at 1 pm”. The cooking is already done before the box leaves the house.

Do it

  1. Make a new folder anywhere and go inside it: 
    mkdir hello-docker && cd hello-docker
  2. Create app.py, a tiny Flask web app: 
    from flask import Flask

app = Flask(__name__)

@app.route("/")
def home():
    return "Hello from my own image!\n"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
    host="0.0.0.0" is important. By default Flask listens only on 127.0.0.1, which means “inside this container only”, so requests from your Mac would never reach it.
  3. Create requirements.txt with one line: 
    flask==3.1.*
    You don't need Python or Flask installed on your Mac. Everything gets installed inside the image.
  4. Create a file named exactly Dockerfile (no extension): 
    FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000
CMD ["python", "app.py"]
    Line by line:
    • FROM: start from the official slim Python image.
    • WORKDIR: create /app and cd into it for all the lines after it.
    • COPY requirements.txt . and RUN pip install: install dependencies before copying the code. This is the caching trick from idea 2.
    • COPY . .: copy the rest of your folder into /app.
    • EXPOSE: only documentation. It does not publish the port. You still need -p.
    • CMD: the command to start the app. The ["…", "…"] style (called exec form) is the recommended one.
  5. Build the image. The . at the end means “use this folder as the build context”: 
    docker build -t hello-docker:v1 .
  6. Run it and test it: 
    docker run -d -p 5000:5000 --name hello hello-docker:v1
curl localhost:5000
    If port 5000 is busy on your Mac (macOS AirPlay Receiver sometimes uses it), use -p 5050:5000 and curl localhost:5050.
  7. Now see the cache working. Change the message in app.py, then rebuild: 
    docker build -t hello-docker:v2 .
    In the output, the pip install step says CACHED. Only the COPY . . step ran again, so the build finishes in a second or two.
  8. Now break it on purpose. Move COPY . . to above the RUN pip install line, change app.py again and rebuild. This time pip install runs every single time. That is the mistake interviewers look for.
  9. Put the Dockerfile back in the right order, then clean up: 
    docker rm -f hello
docker image history hello-docker:v2
    In the history, you can see one layer per instruction from your own Dockerfile, sitting on top of the Python base layers.

Do it again: a Node.js + Express app

Many companies use Node.js for backends, so let's package an Express app too. The recipe is the same as before. Only the ingredients change: the base image, the dependency file and the install command. Once you see the pattern, you can write a Dockerfile for almost any language.

  1. Make a second folder next to the first one: 
    cd ..
mkdir hello-node && cd hello-node
  2. Create package.json. This file does the same job for Node that requirements.txt did for Python: 
    {
  "name": "hello-node",
  "version": "1.0.0",
  "main": "server.js",
  "dependencies": {
    "express": "^5.1.0"
  }
}
  3. Create server.js: 
    const express = require("express");

const app = express();

app.get("/", (req, res) => {
  res.send("Hello from my Node image!\n");
});

app.listen(3000, () => {
  console.log("Listening on port 3000");
});
    When you don't pass a host to app.listen, Node listens on all network interfaces. So here you don't need the 0.0.0.0 fix that Flask needed.
  4. Create .dockerignore with this one line: 
    node_modules
    If you ever run npm install on your Mac, a large node_modules folder appears. It holds packages built for macOS, not Linux, and you don't want them copied into the image. The image installs its own copy.
  5. Create the Dockerfile. Compare it line by line with the Python one: 
    FROM node:22-slim

WORKDIR /app

COPY package*.json ./
RUN npm install --omit=dev

COPY . .

EXPOSE 3000
CMD ["node", "server.js"]
    • FROM node:22-slim: the official Node image (an LTS version) in place of Python.
    • COPY package*.json ./: copies package.json, and also package-lock.json if you have one. Same caching trick as before: dependencies first, code later.
    • RUN npm install --omit=dev: installs only the packages needed to run, skipping dev-only tools like test frameworks.
    • CMD ["node", "server.js"]: start the server directly with node.
  6. Build, run and test: 
    docker build -t hello-node:v1 .
docker run -d -p 3000:3000 --name node-app hello-node:v1
curl localhost:3000
  7. Change the message in server.js and rebuild as hello-node:v2. Just like with Python, the npm install step shows CACHED.
  8. Clean up: 
    docker rm -f node-app

In company projects, package-lock.json is always committed to Git, and the Dockerfile uses npm ci --omit=dev in place of npm install. npm ci installs exactly the versions in the lock file, so every build gets the same packages. It fails if there is no lock file, which is why we used npm install here. [npm docs]

Stretch: create a .dockerignore file containing __pycache__ and .git. It works like .gitignore: those files are never sent to the build, so the image stays clean and small. Then run docker images hello-docker and compare the size with python:3.12 (the non-slim version) if you are curious. The difference is usually hundreds of MB.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. When does RUN pip install -r requirements.txt actually execute?

2. Your friend's Dockerfile has COPY . . before RUN pip install. Every small code change takes 2 minutes to build. Why?

3. The Dockerfile says EXPOSE 5000. You run docker run -d hello-docker:v1 with no -p. Can your browser reach it?

4. The container is running and -p is correct, but curl says “connection reset”. The app listens on 127.0.0.1. What's wrong?

5. Why does the Node project put node_modules in .dockerignore?

6. Interview practice (say it out loud or type it): “Walk me through a Dockerfile for a Python app. Why do you copy requirements.txt separately?”

Compare with a model answer

I start FROM a slim official Python image and set a WORKDIR. I copy only requirements.txt first and run pip install, then copy the rest of the code, and finally set CMD to start the app. Each instruction creates a cached layer, and a change in one layer rebuilds everything after it. Dependencies change rarely and code changes often, so installing dependencies before copying code means normal code changes reuse the cached dependency layer and the build takes seconds instead of minutes.
