Networks & Compose

Today's goal: make containers talk to each other by name, then run a two-container app (a Flask web app and a Redis database) with a single command. About 40 minutes.

Why this matters for DevOps

Real apps are never one container. There is at least an app and a database, often a cache and a background worker too. Typing four long docker run commands in the right order, with the right network and volume flags, is slow and easy to get wrong. Docker Compose writes the whole setup down in one file that lives in Git next to the code. On your first day in a company, “clone the repo and run docker compose up” is very often step one. Kubernetes files in module 2 will look familiar because of today.

Three ideas, no more

Containers on the same user-defined network find each other by name. You create a network with docker network create and attach containers to it. Docker runs a small DNS server for that network, so a container called redis is reachable at the hostname redis. You never hard-code an IP address. IPs change every time a container is recreated; names don't. [Docker docs: networking]

localhost inside a container means that container only. This is the most common beginner bug. If your web container connects to localhost:6379, it is looking for Redis inside itself, and finds nothing. It must use the other container's name. It is the same idea as the 127.0.0.1 problem from lesson 3, seen from the other side.

A Compose file describes the whole app. compose.yaml lists the services (containers), their images or build folders, ports, environment variables and volumes. docker compose up creates a network for the app, puts every service on it, and starts everything. docker compose down removes it all again. [Docker docs: Compose]

College analogy: a network is a hostel's internal phone system. You dial “Room Ravi”, not a number that changes every semester. A Compose file is the hostel's allotment list: who stays in which room, and what each room needs, written down once so the warden doesn't have to remember it.

Do it: talk by name

  1. Create a network and start nginx on it, with the name canteen: 
    docker network create campus
docker run -d --name canteen --network campus nginx:alpine
  2. Start a throwaway container on the same network and fetch the page using only the name: 
    docker run --rm --network campus alpine wget -qO- http://canteen | head -4
docker run --rm --network campus alpine ping -c1 canteen
    The name canteen turns into an IP like 172.18.0.2. No -p needed: -p is only for traffic coming from your Mac. Containers on one network reach each other directly. If you get Connection refused, nginx was still starting. Wait a second and try again.
  3. Now try from a container that is not on the network: 
    docker run --rm alpine wget -qO- -T 3 http://canteen
    You get bad address 'canteen'. Outside the network, the name means nothing. This is also a basic security idea: only the containers you put on the network can reach each other.
  4. Clean up: 
    docker rm -f canteen
docker network rm campus

Do it: a two-service app with Compose

  1. Make a folder: 
    mkdir visits && cd visits
  2. Create app.py, a page that counts its visits in Redis: 
    import os
from flask import Flask
from redis import Redis

app = Flask(__name__)
redis = Redis(host=os.environ.get("REDIS_HOST", "localhost"), port=6379)

@app.route("/")
def home():
    count = redis.incr("visits")
    return f"This page has been visited {count} times.\n"

if __name__ == "__main__":
    app.run(host="0.0.0.0", port=5000)
    The Redis hostname comes from an environment variable, so the same code runs anywhere. Redis is a very fast in-memory database, often used for counters, caches and login sessions.
  3. Create requirements.txt: 
    flask==3.1.*
redis==6.*
  4. Create the Dockerfile. It is the same one you wrote in lesson 3: 
    FROM python:3.12-slim

WORKDIR /app

COPY requirements.txt .
RUN pip install --no-cache-dir -r requirements.txt

COPY . .

EXPOSE 5000
CMD ["python", "app.py"]
  5. Create compose.yaml. Indentation matters in YAML: use spaces, never tabs. 
    services:
  web:
    build: .
    ports:
      - "8000:5000"
    environment:
      REDIS_HOST: redis
    depends_on:
      - redis

  redis:
    image: redis:7-alpine
    volumes:
      - redis-data:/data

volumes:
  redis-data:
    Line by line:
    • web and redis: the two services. Each service name is also its hostname on the network.
    • build: .: build the web image from the Dockerfile in this folder. redis uses a ready-made image instead.
    • ports: the same HOST:CONTAINER rule as -p in lesson 4. Only web is published. Redis stays private.
    • environment: tells the app that Redis lives at the hostname redis.
    • depends_on: start redis before web. It only waits for the container to start, not for Redis to be fully ready.
    • volumes: a named volume, exactly like pgdata in lesson 4, so the count survives.
  6. Start everything. -d runs it in the background, --build builds the web image first: 
    docker compose up -d --build
curl localhost:8000
curl localhost:8000
    The count goes up: 1, then 2. Two containers, talking by name, from one command.
  7. Look at what Compose made for you: 
    docker compose ps
docker network ls
docker compose logs web
    You see a network called visits_default. Compose named it after the folder and put both services on it. logs shows each of your curl requests.
  8. Take the whole app down and bring it back: 
    docker compose down
docker compose up -d
curl localhost:8000
    down removed both containers and the network, but the count continues at 3. The volume kept it.
  9. Clean up everything, including the volume this time: 
    docker compose down -v
cd ..
    -v also deletes the named volumes. Never type it casually on a real database.
Stretch: change REDIS_HOST: redis to REDIS_HOST: localhost, run docker compose up -d and curl localhost:8000. You get a server error. Read docker compose logs web and find Connection refused. That is idea 2, happening for real. Change it back. For a second stretch, add a third service adminer or a second copy of web on port 8001 and check that both share the same counter.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. Your web container connects to Redis at localhost:6379 and gets “connection refused”. Redis is running in another container on the same network, named redis. The fix?

2. Why should apps use container names, not IP addresses like 172.18.0.2?

3. In the Compose file, Redis has no ports section. Can web still reach it?

4. depends_on: [redis] is set. What does Compose guarantee?

5. After docker compose down and up, the visit count continued from where it stopped. Which command would have reset it?

6. Interview practice (say it out loud or type it): “Your app and database run in separate containers. How do they find each other, and why would you use Docker Compose?”

Compare with a model answer

I put both containers on the same user-defined network. Docker provides built-in DNS on that network, so the app reaches the database by its container or service name, like db:5432, instead of a changing IP. Inside a container localhost means the container itself, so that won't work. Only the service users need, like the web app, gets a published port; the database stays private on the network. Compose describes all of this in one version-controlled compose.yaml: services, images or build contexts, ports, environment variables, volumes and start order. One docker compose up creates the network and starts everything, so every developer gets the same setup, and docker compose down cleans it up.
