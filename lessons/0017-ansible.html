Configuration management with Ansible

Why this matters for DevOps

Terraform gave you machines and a cluster. Now something has to happen on them: create a user, install a package, write a config file, deploy an app with the right settings for dev or prod. Doing it by SSH-ing into each machine works for two machines. With twenty CI runners, someone forgets one, or types a different value on one, and now “it fails only on runner 7”. Configuration management means writing the desired setup once and applying it to every machine, as many times as you like, with the same result.

Three ideas, no more

Agentless, with an inventory: Ansible runs on one control machine (your laptop, or a CI job). It connects to each target over SSH, copies a small Python program, runs it, and deletes it. Nothing has to be installed or kept running on the targets, apart from SSH and Python. (Chef and Puppet need an agent on every machine.) The inventory is a file listing the targets, in groups like runners and staging, so a playbook can target one group. [Ansible docs: Inventory]

Idempotent tasks: ok vs changed: a playbook is a list of tasks. Each task uses a module that describes a state, not a command: “user deploy exists”, not useradd deploy. The module checks first. If the machine is already right, it reports ok and does nothing. If not, it fixes it and reports changed. So you can run a playbook ten times safely, and the second run tells you whether anyone changed anything by hand. [Ansible docs: Playbooks]

Variables and Vault: one playbook, different values per group or host (max_jobs: 4 on runners, 1 on staging), kept in group_vars/ files. Secrets like a database password go in a variables file encrypted with Ansible Vault (AES-256). The encrypted file is safe to commit; the playbook decrypts it in memory when you give the vault password. [Ansible docs: Vault]

Your college's lab assistant has to set up 60 lab PCs before the practical exam. Going to each PC is slow, and PC 43 always ends up different. Instead, there's a checklist (playbook) and a list of PCs by lab (inventory: Lab A, Lab B). For each item the assistant checks first: “Python installed? Yes, tick (ok). Wallpaper wrong? Fix it (changed).” Running the checklist again an hour later should give all ticks.

TerraformAnsible
Main jobCreate and delete infrastructure: networks, clusters, VMs, bucketsConfigure what's on existing machines, and deploy apps
How it knows what existsA state fileNo state: checks each machine every run
Typical orderFirst: make the cluster and runnersThen: set up the runners, deploy to the cluster

They overlap a little (Ansible can create cloud resources, Terraform can run scripts), but this split is what most teams use.

Before you start

Docker Desktop running, with your 3-node cluster. Ansible's control machine must be macOS or Linux; on Windows, use WSL2 (Ubuntu) and run everything there. Install Ansible plus the Python library its Kubernetes module needs, in a virtual environment:

brew install uv
uv venv -p 3.13 ~/ansible-env
source ~/ansible-env/bin/activate
uv pip install ansible kubernetes
ansible --version

Run source ~/ansible-env/bin/activate in every new terminal. Make a folder, config-demo, and work in it.

We need some machines to manage. Real targets would be VMs reached by SSH. To keep it free and fast, we'll use three containers as stand-in machines, and tell Ansible to reach them with docker exec instead of SSH. Everything else works exactly as it would with real servers.

for h in runner1 runner2 stage1; do
  docker run -d --name $h python:3.13-slim sleep infinity
done

Do it: one playbook, three machines

  1. Write the inventory, inventory.ini: 
    [runners]
runner1
runner2

[staging]
stage1

[all:vars]
ansible_connection=community.docker.docker
ansible_python_interpreter=/usr/local/bin/python3
    Two groups. The last two lines apply to every host: connect through Docker, and use this Python on the target. With real servers you'd write IP addresses or host names and leave out ansible_connection, and Ansible would use SSH.
  2. Check Ansible can reach them all: 
    ansible all -i inventory.ini -m ping
    Three SUCCESS and "ping": "pong". This is an ad-hoc command: one module, run once, no playbook. Nothing was installed on the containers first. That's “agentless”.
  3. Give each group its own values. Create group_vars/runners.yml: 
    app_env: ci
max_jobs: 4
    and group_vars/staging.yml: 
    app_env: staging
max_jobs: 1
    Ansible loads these automatically for hosts in the group with the same name.
  4. Write the playbook, setup.yml: 
    - name: Prepare build machines
  hosts: all
  tasks:
    - name: Create the deploy user
      ansible.builtin.user:
        name: deploy
        shell: /bin/bash

    - name: Create the app folder
      ansible.builtin.file:
        path: /opt/app
        state: directory
        owner: deploy
        mode: "0755"

    - name: Write the app settings
      ansible.builtin.copy:
        dest: /opt/app/settings.env
        owner: deploy
        content: |
          APP_ENV={{ app_env }}
          MAX_JOBS={{ max_jobs }}
    Every task says what should be true. {{ app_env }} is filled in from the variables, per host.
  5. Predict first: on the first run, how many tasks will say changed on each host? Then: 
    ansible-playbook -i inventory.ini setup.yml
docker exec runner1 cat /opt/app/settings.env
docker exec stage1 cat /opt/app/settings.env
    The recap shows ok=4 changed=3 for each host. (The fourth task is “Gathering Facts”, where Ansible reads details about each machine.) Runners got MAX_JOBS=4, staging got 1: same playbook, different values.
  6. Run it again, unchanged: 
    ansible-playbook -i inventory.ini setup.yml
    changed=0 everywhere. Each module checked, found the machine already right, and did nothing. A shell script with useradd deploy would fail on the second run with “user already exists”.

Do it: drift, limits and a new machine

  1. Someone edits a file by hand on one runner: 
    docker exec runner2 sh -c 'echo MAX_JOBS=99 >> /opt/app/settings.env'
ansible-playbook -i inventory.ini setup.yml --check --diff
    --check is a dry run: nothing changes. --diff shows what would. You see -MAX_JOBS=99 and changed: [runner2] only. Ansible found the one machine that drifted. Run it without --check to fix it.
  2. Change only staging. Set max_jobs: 2 in group_vars/staging.yml, then: 
    ansible-playbook -i inventory.ini setup.yml --limit staging
    Only stage1 runs. The runners aren't touched, even though the playbook says hosts: all. This is how you try a change on staging before everyone else.
  3. A new runner joins. Start runner3 the same way as the others, add it under [runners] in the inventory, and run the same playbook. Only runner3 shows changed, and it ends up exactly like runner1. Adding machine number 20 is one line in the inventory.
  4. Clean up the stand-in machines: docker rm -f runner1 runner2 runner3 stage1.

Do it: deploy to Kubernetes, with a secret

Ansible doesn't need SSH for this part. The kubernetes.core.k8s module talks straight to the cluster's API, using your kubeconfig, the same way kubectl does. So the “target” is your own laptop (ansible_connection=local), and nothing is installed on the cluster. We'll pretend two namespaces are two clusters, dev and prod.

  1. Create clusters.ini: 
    [clusters]
dev   namespace=shop-dev   replicas=1  image_tag=v1.10
prod  namespace=shop-prod  replicas=3  image_tag=v1.11

[clusters:vars]
ansible_connection=local
ansible_python_interpreter="{{ ansible_playbook_python }}"
kube_context=docker-desktop
    Each “host” is an environment with its own values. With real clusters, prod would have its own kube_context, for example the one aws eks update-kubeconfig adds. The interpreter line makes the module use the Python where you installed the kubernetes library.
  2. Store the database password, encrypted. Create group_vars/clusters/vault.yml: 
    db_password: "S3cret-Prod-Pass"
    then encrypt it (choose a vault password and remember it): 
    ansible-vault encrypt group_vars/clusters/vault.yml
cat group_vars/clusters/vault.yml
    The file now starts with $ANSIBLE_VAULT;1.1;AES256 followed by numbers. This is safe to commit, unlike a Kubernetes Secret's base64 (lesson 12), which anyone can decode. The vault password itself never goes in Git: you type it, or CI reads it from its own secret store. ansible-vault edit opens it to change a value.
  3. Write deploy.yml: 
    - name: Deploy the shop API
  hosts: clusters
  gather_facts: false
  tasks:
    - name: Namespace exists
      kubernetes.core.k8s:
        context: "{{ kube_context }}"
        state: present
        definition:
          apiVersion: v1
          kind: Namespace
          metadata:
            name: "{{ namespace }}"

    - name: Database password Secret exists
      no_log: true
      kubernetes.core.k8s:
        context: "{{ kube_context }}"
        state: present
        definition:
          apiVersion: v1
          kind: Secret
          metadata:
            name: db
            namespace: "{{ namespace }}"
          stringData:
            password: "{{ db_password }}"

    - name: API Deployment has the right image and replicas
      kubernetes.core.k8s:
        context: "{{ kube_context }}"
        state: present
        definition:
          apiVersion: apps/v1
          kind: Deployment
          metadata:
            name: api
            namespace: "{{ namespace }}"
          spec:
            replicas: "{{ replicas }}"
            selector:
              matchLabels: { app: api }
            template:
              metadata:
                labels: { app: api }
              spec:
                containers:
                  - name: api
                    image: "traefik/whoami:{{ image_tag }}"
    The definition is an ordinary Kubernetes manifest with variables in it. no_log: true keeps the password out of Ansible's output.
  4. Run it, first without the vault password: 
    ansible-playbook -i clusters.ini deploy.yml
    Attempting to decrypt but no vault secrets found. Without the password, the secret can't be read. Now properly: 
    ansible-playbook -i clusters.ini deploy.yml --ask-vault-pass
kubectl get deploy -A | grep api
kubectl get secret db -n shop-prod -o jsonpath='{.data.password}' | base64 -d; echo
    changed=3 for both. shop-dev has 1 replica, shop-prod has 3. The password reached the cluster, and was never in Git in plain text.
  5. Drift in the cluster. Someone scales prod by hand, then you run the playbook again: 
    kubectl scale deploy api -n shop-prod --replicas=1
ansible-playbook -i clusters.ini deploy.yml --ask-vault-pass
    dev: changed=0, prod: changed=1. Only the Deployment that drifted was put back to 3.
  6. Release a new version to dev only, from the command line, without editing the inventory: 
    ansible-playbook -i clusters.ini deploy.yml --ask-vault-pass --limit dev -e image_tag=v1.11
    -e overrides a variable for this run. Only dev changes. Clean up: kubectl delete namespace shop-dev shop-prod.
Drill: spot the problems. A team sets up 15 CI runners with this “playbook”. Find three problems and say how to fix each. 
- hosts: all
  tasks:
    - name: Install Docker
      ansible.builtin.shell: curl -fsSL https://get.docker.com | sh
    - name: Add runner config
      ansible.builtin.shell: echo "concurrent=4" >> /etc/runner/config.toml
    - name: Set registry password
      ansible.builtin.copy:
        dest: /etc/runner/registry.env
        content: "REGISTRY_PASSWORD=Gh0st@2026"
Show the answer

1. shell instead of state-based modules: the shell commands run every time and always report changed, so you can't spot drift, and re-running the install script on every run is slow and risky. Use a package module, for example ansible.builtin.apt with state: present. 2. echo >> appends: every run adds another concurrent=4 line, so the file grows. Use ansible.builtin.lineinfile or a template, which make sure the line is there exactly once. 3. Password in plain text in the playbook: it's in Git for everyone to read. Put it in a vault-encrypted variables file and use {{ registry_password }}, with no_log: true. Also accept: hosts: all with no groups, so you can't roll out to a few runners first; use inventory groups and --limit.

Practice questions

5 marks · 9 minutes

An engineer sets up each new EKS cluster by hand: create the namespaces staging and prod, apply a standard LimitRange and NetworkPolicy in each, and deploy the ticket-booking API with three replicas in staging and eight in prod. Running the same commands again fails with “already exists”. The team needs:

  • the set-up written once and run against every new cluster from a control machine
  • no software installed on the cluster
  • safe to run repeatedly
  1. [1]Choose a suitable tool and justify the choice.
  2. [1]Show how it reaches a new cluster without any agent installed.
  3. [1]Show how the replica counts for staging and prod are supplied.
  4. [2]Apply it: show why running it a second time causes no errors.
Model answer and marking
  • Tool: Ansible, with the kubernetes.core.k8s module. It's agentless, runs from one control machine, uses idempotent modules, and takes variables per environment. (Kustomize overlays with kubectl apply cover part of this, but only if the answer explains re-runs and per-environment values. A shell script of kubectl create commands fails the re-run requirement.)
  • No agent: the playbook runs on the control machine (a laptop or CI job) with connection: local. The k8s module talks straight to the cluster's Kubernetes API using a kubeconfig, for example one created by aws eks update-kubeconfig, the same way kubectl does. Nothing is installed on the cluster or its nodes.
  • Replica counts: the replica count is a variable, replicas, set per namespace in the inventory or in variable files (staging: 3, prod: 8). The Deployment definition in the playbook uses replicas: "{{ replicas }}", so one definition serves both.
  • Safe to re-run: each task declares the desired state (state: present: “this namespace, this LimitRange, this Deployment with N replicas should exist”), not a command. The module compares it with what's in the cluster: if it already matches, it reports ok and does nothing; if it's missing or different, it creates or updates it and reports changed. A second run gives changed=0 instead of “already exists” errors, and a run after someone changed something by hand puts back only that one thing.

Marking (5): tool choice with justification 1; how it reaches the cluster without an agent 1; how per-environment replica counts are supplied 1; idempotent re-runs explained 2. Exact syntax isn't required.

5 marks · 9 minutes

Eight EC2 machines are build servers for a mobile app team. Each needs Java 21, Git, Docker, a non-root user named builder, and an SSH key that can read the team's GitHub repositories. New servers are added every month; today each is set up by hand over SSH. The tool may need nothing but SSH and Python on the machines.

  1. [1]Choose a suitable tool and justify the choice.
  2. [1]Show how the tool knows which machines to set up, and how a new server is added.
  3. [1]Show how the set-up is run on only the three servers used by the Android team.
  4. [2]Explain why running it again on an already configured machine changes nothing.
Model answer and marking
  • Tool: Ansible. It's agentless (it needs only SSH and Python on the targets), keeps machines in an inventory with groups, and uses idempotent modules. Chef and Puppet need an agent installed and running on every machine, which the scenario rules out.
  • Which machines: an inventory file lists the servers' host names or IP addresses in groups, for example [builders] with all eight and [android] with three of them. The playbook says hosts: builders. (A dynamic inventory can also list EC2 machines by their tags.)
  • New server: add its address to the inventory under [builders] and run the same playbook. It ends up exactly like the others, and the existing servers report ok.
  • Only the Android servers: ansible-playbook -i inventory.ini builders.yml --limit android. The playbook runs only on that group, even though it targets all builders.
  • Re-running changes nothing: tasks use state-based modules: apt with state: present for Java, Git and Docker; user for builder; copy for the SSH key with the right owner and mode. Each module checks first; if the machine already matches, it reports ok and does nothing. So a second run shows changed=0, and any server that drifted is put back and shows changed. The SSH private key is kept in an Ansible Vault-encrypted file, not in plain text.

Marking (5): tool choice and justification 1; inventory and adding a server 1; running on the Android servers only 1; idempotency 2. Exact syntax isn't required.

5 marks · 9 minutes

The payments API must be rolled out the same way to four EKS clusters (dev, qa, staging and prod) that differ only in the image tag and replica count. For each cluster: connect, create the payments namespace, create a Secret holding the payment gateway's API key, and apply the Deployment and Service. The team needs:

  • everything run from one control machine, with nothing installed on the targets
  • the API key stored encrypted inside the Git repository
  1. [1]Choose a suitable tool and justify the choice.
  2. [1]Show how the per-cluster values are supplied.
  3. [2]Show how the API key stays encrypted in Git but is usable during the run.
  4. [1]Show how the output tells which steps changed something and which found the cluster already correct.
Model answer and marking
  • Tool: Ansible with the kubernetes.core.k8s module and Ansible Vault: agentless, runs from one control machine, per-cluster variables in the inventory, idempotent tasks, and ok or changed reported for every task. Helm or Kustomize alone don't cover connecting to each cluster or encrypting the key in Git.
  • Per-cluster values: the inventory lists the four clusters as hosts, each with its own variables: kubeconfig context, image_tag and replicas (or one variables file per cluster in host_vars/). The same playbook runs for each and puts these values into the Deployment by templating.
  • Encrypted in Git, usable in the run: the API key is in a variables file encrypted with ansible-vault encrypt (AES-256), so the file in Git shows only $ANSIBLE_VAULT;1.1;AES256 and random-looking text. At run time the vault password is given with --ask-vault-pass, or in CI from the pipeline's secret store via --vault-password-file. Ansible decrypts the file in memory, creates the Kubernetes Secret, and no_log: true keeps the key out of the output. The vault password itself is never in Git.
  • ok vs changed: each task reports ok (the cluster already matched) or changed (it created or updated something), and the PLAY RECAP gives counts per cluster, for example prod: ok=4 changed=1. On a second run with nothing new, every task is ok; after changing prod's image tag, only prod's Deployment task shows changed. --check --diff shows what would change without changing it.

Marking (5): tool choice and justification 1; per-cluster values 1; encrypted key in Git and its use at run time 2; ok versus changed output 1. Exact syntax isn't required.

Check yourself

Answer before clicking.

1. What must be installed on a Linux server before Ansible can manage it?

2. You run a playbook a second time and the recap says changed=0 on every host. What does that tell you?

3. You want to try a config change on the staging group before the other runners. How?

4. Why can a vault-encrypted variables file be committed to Git, but a Kubernetes Secret manifest can't?

5. Exit question: “You must deploy the same app to three Kubernetes clusters, each with a different replica count and image tag, and a database password that must not be readable in Git. Re-running must be safe. Which tool, and how?”

Compare with a model answer

Ansible, with the kubernetes.core.k8s module and Ansible Vault. It's agentless: it runs from one control machine, a laptop or a CI job, and talks to each cluster's API through a kubeconfig context, so nothing is installed on the clusters. The inventory lists the three clusters, each with its own variables (context, replica count, image tag); one playbook inserts those values into the Deployment manifest by templating, so all three use the same definition. The password is in a variables file encrypted with Ansible Vault (AES-256), so it can be committed; the playbook decrypts it at run time when given the vault password, which comes from the CI secret store, and creates a Kubernetes Secret with no_log so it isn't printed. Re-running is safe because each task declares the desired state: the module compares it with the cluster and reports ok if it already matches or changed if it fixed something, so a second run changes nothing, and a run after someone scaled a Deployment by hand puts back only that one.
