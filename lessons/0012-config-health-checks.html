Config & health checks

Why this matters for DevOps

Your college fest app runs in three places: your laptop, a staging cluster and production. The code is the same everywhere, but the database password, the payment gateway URL and the log level are different. If you bake those into the image, you need three images, and the production password ends up inside every copy of the image on Docker Hub. The rule at work: build one image, and give it its settings from outside.

The second problem: Kubernetes only knows that your container's process is running. It doesn't know if the app inside is stuck, or still loading, or ready for users. Probes are how you tell it. Without them, a rolling update (next lesson) sends users to Pods that can't answer yet.

Three ideas, no more

ConfigMap vs Secret: both are small key–value objects that a Pod reads as environment variables or as files. Use a ConfigMap for normal settings anyone on the team may see: LOG_LEVEL, a payment gateway URL, a feature flag. Use a Secret for anything that would hurt if it leaked: passwords, API keys, tokens. [Kubernetes docs: ConfigMaps] [Secrets]

base64 is not encryption: a Secret's values are stored as base64, which is just a way to write any bytes as plain letters. Anyone can decode it with one command, no key needed. What actually protects a Secret is who is allowed to read it (RBAC rules on the API server), encrypting etcd on disk, and never committing the plain value to Git. Treat a Secret as “kept separately so access can be controlled”, not “scrambled”.

Three probes: the kubelet on each node runs these checks against your container. [Kubernetes docs: Probes]

ProbeQuestion it asksWhen it fails
livenessProbeIs the app stuck?The kubelet restarts the container
readinessProbeCan it serve users right now?The Pod is removed from the Service's endpoints; no restart
startupProbeHas it finished starting?Liveness and readiness wait until it passes; if it never passes in time, restart

Think of the college canteen. Liveness: is the cook awake? If not, replace the cook. Readiness: is food ready to serve? If not, don't send students to that counter yet, but don't fire the cook either. Startup: the morning dosa batter takes 40 minutes; don't ask “are you awake?” every 5 seconds during that time.

Before you start

You need the three-node cluster from lesson 9 and your ~/k8s-practice folder from lesson 11. Check the cluster is up and default is clean:

kubectl get nodes
kubectl get all
cd ~/k8s-practice

Do it: config

  1. Create a ConfigMap and a Secret. Here imperative commands are fine for a quick test; at work these would be files too. 
    kubectl create configmap app-config \
  --from-literal=LOG_LEVEL=info \
  --from-literal=PAYMENT_GATEWAY_URL=https://pay.example.com
kubectl create secret generic db-secret --from-literal=DB_PASSWORD=Fest2026
kubectl get configmap app-config -o yaml
    The ConfigMap shows your values in plain text, under data:.
  2. Now look at the Secret, and decode it: 
    kubectl get secret db-secret -o yaml
kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d; echo
    The YAML shows DB_PASSWORD: RmVzdDIwMjY=. One command later you have Fest2026 back. No key, no password. That's base64: an encoding, not a lock. If you can read the Secret object, you can read the password, so the real protection is controlling who can read Secrets.
  3. Write a small app that prints its settings. Create cfg.yaml: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: cfg
spec:
  replicas: 1
  selector:
    matchLabels:
      app: cfg
  template:
    metadata:
      labels:
        app: cfg
    spec:
      containers:
        - name: app
          image: busybox:1.36
          command: ["sh", "-c", "while true; do echo LOG_LEVEL=$LOG_LEVEL URL=$PAYMENT_GATEWAY_URL password_length=${#DB_PASSWORD}; sleep 5; done"]
          envFrom:
            - configMapRef:
                name: app-config
          env:
            - name: DB_PASSWORD
              valueFrom:
                secretKeyRef:
                  name: db-secret
                  key: DB_PASSWORD
    envFrom turns every key in the ConfigMap into an environment variable. secretKeyRef picks one key from the Secret. The app prints only the password's length: never print a secret in logs. 
    kubectl apply -f cfg.yaml
kubectl logs deploy/cfg --tail=2
    You see LOG_LEVEL=info and password_length=8.
  4. Change the setting while the app runs. Predict first: after you edit the ConfigMap, will the running app print debug? 
    kubectl create configmap app-config --from-literal=LOG_LEVEL=debug \
  --from-literal=PAYMENT_GATEWAY_URL=https://pay.example.com \
  --dry-run=client -o yaml | kubectl apply -f -
sleep 10; kubectl logs deploy/cfg --tail=1
    Still info. Environment variables are copied into the process once, when the container starts, just like in any Linux program. Editing the ConfigMap doesn't touch a running process. Restart the Pods to pick up the change: 
    kubectl rollout restart deployment/cfg
kubectl rollout status deployment/cfg
kubectl logs deploy/cfg --tail=1
    Now it says debug. (A ConfigMap mounted as a file does get updated inside the Pod after a short delay, but the app still has to re-read the file. Most apps don't, so plan for a restart either way.)
  5. Break it on purpose. Edit cfg.yaml and change key: DB_PASSWORD to key: password, a key that doesn't exist in the Secret. Apply and watch: 
    kubectl apply -f cfg.yaml
kubectl get pods -l app=cfg
    The new Pod shows CreateContainerConfigError. Run kubectl describe pod -l app=cfg and read the last event: couldn't find key password in Secret default/db-secret. The old Pod keeps running, so users are safe. Put the key back to DB_PASSWORD, apply, and clean up: kubectl delete -f cfg.yaml.

Do it: health checks

  1. Watch liveness restart a stuck app. This test image from the Kubernetes docs answers /healthz with 200 for its first 10 seconds, then with 500 forever, like an app that hangs. Create liveness.yaml: 
    apiVersion: v1
kind: Pod
metadata:
  name: liveness
spec:
  containers:
    - name: app
      image: registry.k8s.io/e2e-test-images/agnhost:2.40
      args: ["liveness"]
      livenessProbe:
        httpGet:
          path: /healthz
          port: 8080
        initialDelaySeconds: 3
        periodSeconds: 3
    kubectl apply -f liveness.yaml
kubectl get pod liveness -w
    After about 20 seconds, RESTARTS goes to 1, then 2. Press Ctrl+C and run kubectl describe pod liveness: the events say Liveness probe failed: HTTP probe failed with statuscode: 500 and Container app failed liveness probe, will be restarted. The process never crashed; the probe found it broken. Delete it: kubectl delete -f liveness.yaml.
  2. Now the most common probe mistake at work. This app takes 30 seconds to start, like an API warming up its cache. Create slow.yaml: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: slow
spec:
  replicas: 2
  selector:
    matchLabels:
      app: slow
  template:
    metadata:
      labels:
        app: slow
    spec:
      containers:
        - name: web
          image: nginx:1.27-alpine
          command: ["sh", "-c", "sleep 30; echo ok > /usr/share/nginx/html/ready; exec nginx -g 'daemon off;'"]
          livenessProbe:
            httpGet:
              path: /
              port: 80
            initialDelaySeconds: 5
            periodSeconds: 5
            failureThreshold: 3
---
apiVersion: v1
kind: Service
metadata:
  name: slow
spec:
  selector:
    app: slow
  ports:
    - port: 80
    Predict first: the liveness probe starts at 5 seconds and allows 3 failures, 5 seconds apart. The app needs 30 seconds. What happens? 
    kubectl apply -f slow.yaml
kubectl get pods -l app=slow -w
    The Pods restart every ~20 seconds and never become 1/1. The probe gives up at about 5 + 3×5 = 20 seconds, kills the container, and the 30-second start begins again. Soon the status shows CrashLoopBackOff. The app is fine; the probe is wrong.
  3. Fix it with a startup probe and a readiness probe. In slow.yaml, replace the whole livenessProbe: block with: 
              startupProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 5
            failureThreshold: 12
          readinessProbe:
            httpGet:
              path: /ready
              port: 80
            periodSeconds: 5
          livenessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 10
            failureThreshold: 3
    The startup probe allows 12 × 5 = 60 seconds to start. Until it passes, liveness and readiness don't run. After that, liveness checks “still alive?” every 10 seconds, and readiness checks /ready. 
    kubectl apply -f slow.yaml
kubectl get pods -l app=slow -w
    The new Pods sit at 0/1 Running for about 30 seconds, then turn 1/1, with 0 restarts.
  4. Watch readiness take a Pod out of traffic without restarting it. Pick one Pod and delete its ready file, as if it lost its database connection: 
    kubectl get endpointslices -l kubernetes.io/service-name=slow
POD=$(kubectl get pods -l app=slow -o jsonpath='{.items[0].metadata.name}')
kubectl exec $POD -- rm /usr/share/nginx/html/ready
sleep 20
kubectl get pods -l app=slow
kubectl get endpointslices -l kubernetes.io/service-name=slow
    That Pod is 0/1 but RESTARTS is still 0, and the EndpointSlice now lists only one IP. The Service stops sending users to it, and nothing is killed. Put the file back (kubectl exec $POD -- sh -c 'echo ok > /usr/share/nginx/html/ready') and it rejoins. Clean up: kubectl delete -f slow.yaml, then kubectl delete configmap app-config and kubectl delete secret db-secret.
Drill: spot the problems. A canteen-ordering API reads MENU_URL, LOG_LEVEL and UPI_API_KEY. It takes about 45 seconds to load the day's menu before it can serve orders. Find four problems in this part of its Deployment, and say what each one causes. 
env:
  - name: UPI_API_KEY
    value: sk_live_9f8e7d6c          # in the manifest, in Git
envFrom:
  - configMapRef: { name: canteen-config }
livenessProbe:
  httpGet: { path: /healthz, port: 8000 }
  initialDelaySeconds: 10
  periodSeconds: 5
  failureThreshold: 2
Show the answer

1. The API key is written in the manifest, so it sits in Git history forever, readable by anyone with the repo. Put it in a Secret (created outside Git, or encrypted in Git) and use secretKeyRef.
2. No readiness probe: the Pod gets traffic as soon as its container starts, so for 45 seconds users get errors, and during a rolling update the old Pods are removed while the new ones can't answer. Add a readinessProbe.
3. The liveness probe kills the app before it can start: 10 + 2 × 5 = 20 seconds, but it needs 45. The Pod restarts forever (CrashLoopBackOff). Add a startupProbe with enough budget, e.g. periodSeconds: 5, failureThreshold: 12 (60 seconds).
4. Changing canteen-config won't reach running Pods: env vars are read once at start. After editing the ConfigMap, run kubectl rollout restart (or change something in the Pod template) so new Pods pick it up.

Practice questions

5 marks · 9 minutes

A food-delivery API reads four settings: RESTAURANT_SEARCH_URL, CACHE_TTL_SECONDS, SMS_GATEWAY_TOKEN and DB_PASSWORD.

  1. [1]Analyze which belong in a ConfigMap and which in a Secret, and why.
  2. [1]Analyze why the base64 encoding used in a Secret is not encryption.
  3. [1]Explain what actually protects a Secret.
  4. [2]Examine what happens to running Pods when the ConfigMap is edited to change CACHE_TTL_SECONDS.
Model answer and marking
  • ConfigMap: RESTAURANT_SEARCH_URL and CACHE_TTL_SECONDS. They aren't sensitive; anyone on the team may read them, and they can be kept in Git with the manifests.
  • Secret: SMS_GATEWAY_TOKEN and DB_PASSWORD. Anyone who has them can send SMS on the company's bill or read the database. A Secret is a separate object type, so access can be limited to it on its own, and kubectl doesn't print its values in describe.
  • base64 isn't encryption: it's an encoding, there to carry any bytes safely in YAML. There's no key; anyone runs base64 -d and reads the value.
  • What protects a Secret: RBAC rules that let only the people and ServiceAccounts who need it get Secrets; encryption at rest in etcd (on EKS, with a KMS key); and keeping the plain value out of Git, for example by creating it from AWS Secrets Manager, Sealed Secrets or an Ansible Vault file.
  • Editing the ConfigMap: environment variables are read once when the container starts, so running Pods keep the old CACHE_TTL_SECONDS. New Pods get the new value: run kubectl rollout restart deployment to replace them gradually. (If the ConfigMap were mounted as files, the files would update after a minute or so, but the app would still have to re-read them.)

Marking (5): correct split with reasons 1; base64 isn't encryption 1; what protects a Secret 1; what happens to running Pods when the ConfigMap is edited 2.

5 marks · 9 minutes

A train-ticket booking API needs about 60 seconds to load seat maps into memory before it can serve requests. With the liveness probe below, its Pods never become Ready and their restart count keeps rising.

livenessProbe:
  httpGet:
    path: /healthz
    port: 8080
  initialDelaySeconds: 10
  periodSeconds: 10
  failureThreshold: 3
  1. [2]Analyze why the Pods keep restarting.
  2. [2]Differentiate between liveness, readiness and startup probes.
  3. [1]State how to fix the configuration.
Model answer and marking
  • Why: the first check is at 10 s, then every 10 s. While the seat maps are loading, /healthz doesn't answer, so the checks at about 10, 20 and 30 s fail. After 3 failures (about 30 s) the kubelet kills the container and restarts it, long before the 60 s it needs. Every start is killed the same way, so the Pod never becomes Ready and ends in CrashLoopBackOff.
  • Liveness: “is the process stuck?” If it fails, the kubelet restarts the container. Readiness: “can it serve traffic now?” If it fails, the Pod is removed from the Service's endpoints but not restarted. Startup: “has it finished starting?” Liveness and readiness checks wait until it succeeds, which protects slow starters.
  • Fix: add a startup probe with a budget longer than 60 s, for example periodSeconds: 10 and failureThreshold: 9 (90 s); add a readiness probe so traffic arrives only when the seat maps are loaded; keep the liveness probe for later hangs.
startupProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 9
readinessProbe:
  httpGet: { path: /ready, port: 8080 }
  periodSeconds: 5
livenessProbe:
  httpGet: { path: /healthz, port: 8080 }
  periodSeconds: 10
  failureThreshold: 3

Marking (5): why the Pods restart, with the timing 2; the three probe types 2; fix with a startup probe 1. Raising the liveness probe's initial delay above 60 s also earns the fix mark if explained.

5 marks · 9 minutes

The Deployment below is for a hostel mess-menu API that listens on port 8080. The Secret mess-db has a single key, DB_PASS.

apiVersion: apps/v1
kind: Deployment
metadata: { name: menu-api }
spec:
  replicas: 2
  selector: { matchLabels: { app: menu-api } }
  template:
    metadata: { labels: { app: menu-api } }
    spec:
      containers:
      - name: api
        image: ghcr.io/hostel/menu-api:2.1.0
        ports:
        - containerPort: 8080
        env:
        - name: DB_PASSWORD
          valueFrom:
            secretKeyRef: { name: mess-db, key: password }
        readinessProbe:
          httpGet: { path: /healthz, port: 80 }
        resources:
          requests: { cpu: "2" }
          limits:   { cpu: "1" }
  1. [3]Detect any three errors, and state the fix for each.
  2. [2]Explain the symptom each error causes in the cluster.
Model answer and marking
  • CPU request bigger than the limit (2 vs 1). Symptom: the API server rejects the Deployment on apply: must be less than or equal to cpu limit of 1. No Pods are created at all. Fix: request no more than the limit, for example requests: 250m, limits: 1. The next two errors show up once this one is fixed.
  • Wrong Secret key: the Secret's key is DB_PASS, not password. Symptom: Pods stay in CreateContainerConfigError; kubectl describe pod shows couldn't find key password in Secret. Fix: key: DB_PASS.
  • Readiness probe on the wrong port (80; the app listens on 8080). Symptom: Pods are Running but 0/1 Ready, events show Readiness probe failed: connection refused, the Service has no endpoints, and callers get errors. Fix: port: 8080.

Marking (5): three errors, each with its fix 3 (1 each); symptoms explained for all three 2. A correct description of each fix earns the mark.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. A teammate says, “It's safe to commit the Secret YAML to Git, the password is encrypted.” What's wrong?

2. A Pod's readiness probe starts failing. What does Kubernetes do?

3. You change LOG_LEVEL in a ConfigMap that a Deployment reads with envFrom. What happens to the running Pods?

4. An app needs 90 seconds to start, then should be restarted quickly if it hangs. Which probe solves the slow start?

5. Exit question (say it out loud or type it): “What's the difference between liveness, readiness and startup probes? Give one example of each going wrong.”

Compare with a model answer

All three are checks the kubelet runs against a container. A liveness probe asks “is the app stuck?”; if it fails enough times, the kubelet restarts the container. Example: a Node.js app with a deadlock still has a running process, so without liveness it would sit broken forever. A readiness probe asks “can it serve users right now?”; if it fails, the Pod is taken out of the Service's endpoints, but it's not restarted. Example: without readiness, during a rolling update users are sent to new Pods that are still loading and get errors. A startup probe asks “has it finished starting?”; liveness and readiness wait until it passes. Example: an API that warms its cache for 40 seconds, with only a liveness probe that gives up after 20 seconds, gets restarted forever and never becomes ready. The fix is a startup probe with a long enough budget.
