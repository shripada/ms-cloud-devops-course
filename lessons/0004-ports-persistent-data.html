Ports & persistent data

Today's goal: understand exactly what -p does, edit a website live from your Mac, and run a Postgres database whose data survives when the container is deleted. About 35 minutes.

Why this matters for DevOps

Containers are meant to be thrown away. You delete one and start a fresh one every time you deploy. That is fine for your app's code, but not for your users' data. If the database container is deleted and the student records go with it, that is a real production incident. Every Kubernetes and cloud setup you will see later is built on today's two ideas: how traffic gets into a container, and where data lives outside it.

Three ideas, no more

-p HOST:CONTAINER is a forwarding rule. A container has its own private network, like a hostel room with its own internal phone line. -p 8080:80 tells Docker: “anything that arrives at port 8080 on my Mac, forward it to port 80 inside the container.” The left number is yours to choose. The right number is whatever the app listens on. You already met the other half of this in lesson 3: EXPOSE only documents a port, and -p actually opens it. [Docker docs: port publishing]

A container's own files die with the container. In lesson 2 you saw that every container gets a thin writable layer on top of the image. Anything the app writes goes there. docker rm deletes that layer, and the data is gone. Stopping and restarting keeps it. Removing does not.

A mount puts a folder from outside into the container. There are two kinds you will use every day. [Docker docs: storage]

  • Bind mount: a folder on your Mac, for example -v "$PWD":/app. You see and edit the same files from both sides. Great during development.
  • Named volume: storage that Docker creates and manages, for example -v pgdata:/var/lib/postgresql/data. You don't care where it is on disk. Use this for databases.

Canteen analogy: the container is the plate. You wash it and reuse it all day, and nobody minds. The volume is the canteen's account register. You would never throw that away with the plate.

Do it: ports

  1. Run nginx twice, on two different Mac ports, from the same image: 
    docker run -d --name web1 -p 8080:80 nginx:alpine
docker run -d --name web2 -p 8081:80 nginx:alpine
curl -s localhost:8080 | head -4
curl -s localhost:8081 | head -4
    Both containers listen on port 80 inside, and there is no clash, because each has its own network. Only the Mac side must be unique.
  2. See the forwarding rule Docker made: 
    docker port web1
    You get 80/tcp -> 0.0.0.0:8080: container port 80 is reachable on Mac port 8080.
  3. Now try to start a third one on 8080 again: 
    docker run -d --name web3 -p 8080:80 nginx:alpine
    It fails with port is already allocated. Two things cannot answer the same phone number on your Mac. Clean up: 
    docker rm -f web1 web2 web3

Do it: a bind mount for live editing

  1. Make a folder with a web page: 
    mkdir fest-site && cd fest-site
echo '<h1>My college fest page</h1>' > index.html
  2. Run nginx with this folder mounted where nginx looks for its pages: 
    docker run -d --name fest -p 8080:80 \
  -v "$PWD":/usr/share/nginx/html:ro nginx:alpine
curl localhost:8080
    $PWD is the current folder. The :ro at the end means read-only: the container can read your files but not change them.
  3. Edit the file on your Mac and fetch the page again. No rebuild, no restart: 
    echo '<h1>Edited on my Mac</h1>' > index.html
curl localhost:8080
    This is why developers use bind mounts: save the file, refresh the browser.
  4. Clean up and go back: 
    docker rm -f fest
cd ..

Do it: a database that survives

  1. First, watch data get lost. Start Postgres without a volume, add a row, delete the container, start a new one: 
    docker run -d --name db -e POSTGRES_PASSWORD=secret postgres:17
sleep 5
docker exec db psql -U postgres -c "CREATE TABLE students(name text); INSERT INTO students VALUES ('Asha');"
docker rm -f db

docker run -d --name db -e POSTGRES_PASSWORD=secret postgres:17
sleep 5
docker exec db psql -U postgres -c "SELECT * FROM students;"
    You get relation "students" does not exist. Asha is gone. -e sets an environment variable; the Postgres image refuses to start without a password.
  2. Remove it and do it properly, with a named volume: 
    docker rm -f db
docker volume create pgdata
docker run -d --name db -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data postgres:17
sleep 5
docker exec db psql -U postgres -c "CREATE TABLE students(name text); INSERT INTO students VALUES ('Asha');"
  3. Now delete the container, as if you were deploying a new version, and start a brand-new one on the same volume: 
    docker rm -f db
docker run -d --name db -e POSTGRES_PASSWORD=secret \
  -v pgdata:/var/lib/postgresql/data postgres:17
sleep 5
docker exec db psql -U postgres -c "SELECT * FROM students;"
    Asha is still there. The container is new; the data is not.
  4. Look at the volume: 
    docker volume ls
docker volume inspect pgdata
    Mountpoint is a path inside Docker's Linux VM, not on your Mac. That is exactly the point: Docker manages it for you.
  5. Clean up. A volume is not deleted when its container is, so you remove it on purpose: 
    docker rm -f db
docker volume rm pgdata

The mount path must match what the image actually uses. For postgres:17 it is /var/lib/postgresql/data. From postgres:18 onwards it is /var/lib/postgresql. Mount the wrong path and Postgres writes somewhere else, so your data is lost again with no error. The image's page on Docker Hub always says the right path. Read it.

Stretch: run docker run --rm -v notes:/data alpine sh -c 'echo "chai at 4pm" >> /data/notes.txt' three times, then docker run --rm -v notes:/data alpine cat /data/notes.txt. Three different containers, each deleted right away by --rm, and all three lines are saved. Also try docker volume prune to see which unused volumes you have collected, but read what it lists before you say yes.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. A Flask app inside the container listens on 5000. You want to open it at localhost:9000 on your Mac. Which flag?

2. You run two nginx containers, both listening on port 80 inside. Can both run at once?

3. A container wrote a log file into its own filesystem (no volume). Which command loses that file?

4. You are developing a website and want every save on your Mac to show in the container right away. What do you use?

5. Your teammate mounted a volume on the Postgres container, but data still disappears after docker rm. The most likely cause?

6. Interview practice (say it out loud or type it): “You run your database in Docker. How do you make sure the data isn't lost when the container is replaced? What's the difference between a volume and a bind mount?”

Compare with a model answer

Anything written into a container's own filesystem lives in its writable layer and is deleted with the container. So I mount a named volume at the database's data directory, for example -v pgdata:/var/lib/postgresql/data, checking the image docs for the exact path. The volume is managed by Docker and lives independently of any container, so I can delete and replace the container and the new one sees the same data. A bind mount instead maps a specific folder from the host into the container. I use bind mounts in development for live code editing and for config files, and named volumes for database data because Docker manages them and they don't depend on the host's folder layout.
