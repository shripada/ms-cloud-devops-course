Updates & releases

Why this matters for DevOps

Think of IRCTC at 10 a.m., when Tatkal booking opens. The team can't say “site down for 10 minutes, we're deploying”. Real teams ship many times a day, while users keep clicking. So every release must replace old Pods with new ones a few at a time, check each new Pod is ready before it gets traffic, and have a one-command way back when the new version is broken. That's what a Deployment's rollout does for you, as long as you set it up right.

Three ideas, no more

A rollout makes a new ReplicaSet: when you change anything in a Deployment's Pod template (usually the image), the Deployment creates a new ReplicaSet for the new version, scales it up, and scales the old one down. The old ReplicaSet is kept at 0 replicas. That's the rollback: “scale the old one back up”. Changing only replicas doesn't touch the template, so no rollout happens. That answers lesson 11's stretch question. [Kubernetes docs: Deployments]

maxSurge and maxUnavailable: the two dials of the RollingUpdate strategy. maxSurge is how many extra Pods may exist above replicas during the update. maxUnavailable is how many of the wanted Pods may be not-ready. With 4 replicas, maxSurge: 1 and maxUnavailable: 0, Kubernetes starts 1 new Pod (5 in total), waits until it's ready, removes 1 old Pod, and repeats. Users never have fewer than 4 ready Pods. The readiness probe from lesson 12 is what “ready” means here.

Release strategies:

StrategyHowUse when
RollingUpdate (default)Replace Pods a few at a time; old and new run together for a whileMost releases. Needs old and new to work side by side
RecreateDelete all old Pods, then start new ones; short downtimeOld and new can't run together, e.g. a database schema change the old version can't read
Blue-greenTwo full Deployments; the Service selector points at one; switch it in one stepYou want an instant switch and an instant way back, and can pay for double the Pods
CanaryA few new Pods share the Service with many old ones, so a small share of users try the new versionYou want to test a risky change on, say, 10% of users first

Your college changes its exam timetable. Rolling: one department at a time moves to the new timetable. Recreate: the whole college closes for a day, then everyone starts on the new one. Blue-green: the new timetable is printed and ready on a second notice board, and the principal switches the arrow from the old board to the new one. Canary: only the final-year students try the new timetable for a week first.

Before you start

Same cluster and ~/k8s-practice folder as before. Open a second terminal for watching. Lesson 11's who.yaml should still exist; if it doesn't, copy it from lesson 11, step 3.

Do it: rolling update and rollback

  1. Give who a safe update strategy and a readiness probe. In the Deployment part of who.yaml, set replicas: 4, set the image to traefik/whoami:v1.10, and add these lines. strategy goes under spec:, next to replicas; readinessProbe goes under the container, next to ports: 
    spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0
  ...
          readinessProbe:
            httpGet:
              path: /
              port: 80
            periodSeconds: 2
    kubectl apply -f who.yaml
kubectl rollout status deployment/who
kubectl get rs -l app=who
    One ReplicaSet with 4 Pods.
  2. Ship version 1.11. In the second terminal, watch: kubectl get pods -l app=who -w. In the first, edit the file's image to traefik/whoami:v1.11 and apply. Predict first: at the busiest moment, how many Pods exist, and how many are ready? 
    kubectl apply -f who.yaml
kubectl rollout status deployment/who
kubectl get rs -l app=who
    In the watch you see one new Pod appear, become 1/1, then one old Pod Terminating, four times over. At most 5 non-terminating rollout Pods count towards replicas + maxSurge, and there are never fewer than 4 ready. A terminating Pod is not counted in that limit, so kubectl get pods can briefly display more than 5 while its grace period expires. Now there are two ReplicaSets: the new one with 4 and the old one with 0. The old one is kept on purpose: it's the way back.
  3. Ship a broken version. Change the container to pass an argument whoami doesn't know, as if a bad build crashes on start-up. Under the container, next to image, add: 
              args: ["--no-such-flag"]
    kubectl apply -f who.yaml
kubectl rollout status deployment/who --timeout=30s
kubectl get pods -l app=who
    The rollout times out. One new Pod is in CrashLoopBackOff, and all four old Pods are still 1/1. Because maxUnavailable: 0, Kubernetes won't remove an old Pod until a new one is ready, and this one never will be. Users see nothing wrong. Without the readiness probe, or with maxUnavailable bigger than 0, they would.
  4. Roll back. You can ask Kubernetes to go back to the previous ReplicaSet: 
    kubectl rollout history deployment/who
kubectl rollout undo deployment/who
kubectl rollout status deployment/who
kubectl get rs -l app=who
    Back to the healthy version in seconds. But now your file still says --no-such-flag, and the next kubectl apply (or the next CI run) would break it again. rollout undo is the emergency brake. The real fix is in Git: remove the args line, commit, and apply. Do that now, then check kubectl diff -f who.yaml shows nothing.
  5. Feel the difference with Recreate. Change strategy to just type: Recreate (delete the rollingUpdate: block, it isn't allowed with Recreate), change the image back to v1.10, and apply while the watch runs. All four Pods go Terminating together, and only then do new ones start. For a few seconds there are zero Pods: that's real downtime. Put the strategy back to RollingUpdate when you're done.
  6. Try the shortcut, and see why it's a trap. kubectl set image changes the image of a live Deployment directly: 
    kubectl set image deployment/who whoami=traefik/whoami:v1.11
kubectl diff -f who.yaml
    The diff shows the cluster runs v1.11 but Git says v1.10. That's drift (lesson 11). Nobody reading the repo knows what's running, and you can't rebuild the same cluster from Git. At work: CI builds the image once, then changes the tag in the manifest in Git, and that commit is what gets applied. The same image moves from dev to staging to production; only its settings (lesson 12) change. That's build once, deploy many. Put the file and cluster back in step: kubectl apply -f who.yaml.

Do it: blue-green and canary

  1. Blue-green is just two Deployments and a Service selector. Create bluegreen.yaml: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-blue
spec:
  replicas: 2
  selector:
    matchLabels: { app: shop, track: blue }
  template:
    metadata:
      labels: { app: shop, track: blue }
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.10
---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-green
spec:
  replicas: 2
  selector:
    matchLabels: { app: shop, track: green }
  template:
    metadata:
      labels: { app: shop, track: green }
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.11
---
apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  selector: { app: shop, track: blue }
  ports:
    - port: 80
    kubectl apply -f bluegreen.yaml
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c 'for i in 1 2 3 4 5 6; do wget -qO- http://shop | grep Hostname; done'
    Every answer comes from a shop-blue-… Pod. Green is running and ready, but gets no users. Now switch: in the file, change the Service's selector to track: green, apply, and run the same kubectl run line. Every answer now comes from shop-green-…. One small change moved all users at once, and switching back is the same change in reverse.
  2. Canary: let both share the Service. Change the Service's selector to only { app: shop }, and set shop-blue to 3 replicas and shop-green to 1. Apply and run the loop again, with 12 requests instead of 6. About a quarter of answers come from green, because the Service spreads requests across all 4 matching Pods. To widen the canary, change the replica counts. (Tools like Argo Rollouts or a service mesh give exact percentages; the idea is the same.) Clean up: kubectl delete -f bluegreen.yaml.

Do it: pulling from a private registry

  1. In lesson 8 your CI pushed an image to GitHub Container Registry (GHCR). If that package is private, define the workload in mine.yaml (put your own GitHub username, image name and immutable tag in): 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: mine
spec:
  replicas: 1
  selector:
    matchLabels: { app: mine }
  template:
    metadata:
      labels: { app: mine }
    spec:
      containers:
        - name: app
          image: ghcr.io/YOUR-USERNAME/YOUR-IMAGE:YOUR-TAG
    kubectl apply -f mine.yaml
kubectl get pods -l app=mine
kubectl describe pod -l app=mine | tail -5
    ImagePullBackOff, and the events say something like 401 Unauthorized or denied. The kubelet on the node tried to pull the image with no login. (If your package is public it just works; change its visibility to private in GitHub to try this.)
  2. Give the cluster credentials. Create a GitHub personal access token (classic) with only the read:packages scope. Generate a local Secret manifest, keep it out of Git, and apply it: 
    printf '%s\n' 'ghcr-pull.local.yaml' >> .gitignore
kubectl create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io \
  --docker-username=YOUR-USERNAME \
  --docker-password=YOUR-TOKEN \
  --dry-run=client -o yaml > ghcr-pull.local.yaml
kubectl apply -f ghcr-pull.local.yaml
    Now add imagePullSecrets to mine.yaml under the Pod's spec, beside containers: 
          imagePullSecrets:
        - name: ghcr-pull
    kubectl apply -f mine.yaml
kubectl get pods -l app=mine -w
    The new Pod pulls the image and runs. The Deployment's desired state remains in mine.yaml; only the credential value stays in the ignored local file. At work, a secrets manager or encrypted-secret controller normally supplies it. Clean up: kubectl delete -f mine.yaml -f ghcr-pull.local.yaml.
Drill. The college results portal has 6 replicas with maxSurge: 2 and maxUnavailable: 1, and a readiness probe. (a) During an update, what's the most Pods that can exist, and the fewest that can be ready? (b) The new version never becomes ready. How many old Pods are still serving when the rollout gets stuck? (c) Version 4.0 changes the results table so version 3.x can't read it. Which strategy, and why?
Show the answer

(a) At most 6 + 2 = 8 Pods; at least 6 − 1 = 5 ready. (b) Kubernetes may take 1 old Pod down at once and add up to 2 new ones. The new ones never get ready, so no more old ones are removed: 5 old Pods keep serving, and 3 new ones are stuck. Users are fine, with a little less capacity. Follow it with kubectl rollout status, go back with kubectl rollout undo, then fix the manifest in Git. (c) Recreate (or blue-green with a planned cut-over): during a rolling update old and new Pods run at the same time, and the old ones would fail reading the new table. Recreate stops every old Pod before any new one starts, at the cost of a short planned downtime.

Practice questions

5 marks · 9 minutes

The train-booking API below must:

  • run four replicas
  • be updated without downtime
  • receive traffic only once a Pod is ready to serve
apiVersion: apps/v1
kind: Deployment
metadata: { name: booking-api }
spec:
  replicas: 1
  strategy:
    type: RollingUpdate
    rollingUpdate: { maxSurge: 0, maxUnavailable: 1 }
  selector: { matchLabels: { app: booking-api } }
  template:
    metadata: { labels: { app: booking-api } }
    spec:
      containers:
      - name: api
        image: ghcr.io/rail/booking-api:3.2.0
        ports:
        - containerPort: 8080
        livenessProbe:
          httpGet: { path: /healthz, port: 8080 }
  1. [3]Detect the three problems that prevent this, and state how to fix each.
  2. [2]Analyze how your corrected manifest protects users during a rolling update.
Model answer and marking
  • replicas: 1: one Pod means no spare; if it restarts, or its node fails, the API is down. Fix: replicas: 4.
  • maxSurge: 0, maxUnavailable: 1: no extra Pod may be added, and one may be taken away, so the update kills an old Pod before its replacement exists. With one replica that's a full outage on every update; with four, capacity drops by a quarter. Fix: maxSurge: 1, maxUnavailable: 0.
  • Liveness probe only, no readiness probe: a new Pod is added to the Service as soon as its container starts, before the app can serve, so users get errors. Fix: add a readinessProbe, for example httpGet on /healthz, port 8080.
  • How the fixed manifest protects users: with maxUnavailable: 0, an old Pod is removed only after a new one is Ready, and a new Pod joins the Service only when its readiness probe passes. If the new version can't start, it never gets traffic: the rollout stalls and the four old Pods keep serving.

Marking (5): three problems, each with its fix 3 (1 each); how readiness and the rolling update together protect users 2. A correct description of each fix earns the mark.

5 marks · 9 minutes

A Deployment runs six replicas of ghcr.io/rail/booking-api:2.3.0 with the RollingUpdate strategy, maxSurge: 2, maxUnavailable: 0 and a readiness probe. The image is changed to 2.4.0, which never passes its readiness probe.

  1. [2]Analyze the sequence in which Pods are created and removed during the update.
  2. [1]Examine what users experience with 2.4.0.
  3. [1]Explain how the team can follow the rollout and return to 2.3.0.
  4. [1]Analyze why the old ReplicaSet is kept after the update.
Model answer and marking
  • Limits: maxSurge: 2 allows at most 8 Pods at once; maxUnavailable: 0 means 6 must always be available.
  • Sequence: the Deployment creates a new ReplicaSet for 2.4.0 and starts 2 new Pods (8 in total). As each becomes Ready, the old ReplicaSet is scaled down by one and another new Pod starts. This repeats until the new ReplicaSet has 6 and the old one has 0.
  • With the bad 2.4.0: the 2 new Pods never become Ready, so no old Pod is removed. The rollout stalls with all six 2.3.0 Pods still serving. Users see no outage; the unready Pods never get traffic.
  • Follow and roll back: kubectl rollout status shows it waiting (and fails after progressDeadlineSeconds, 10 minutes by default); kubectl get rs shows old 6, new 2 not ready; kubectl rollout history lists the revisions. Go back with kubectl rollout undo, or set the tag back to 2.3.0 in the manifest in Git and apply it.
  • Old ReplicaSet kept: it stays, scaled to 0, so a rollback only scales it back up, using the exact same Pod template. That's fast and exact. How many are kept is set by revisionHistoryLimit (default 10).

Marking (5): Pod sequence 2; what users experience with the bad version 1; following the rollout and returning to 2.3.0 1 (exact commands not required); why the old ReplicaSet is kept 1.

5 marks · 9 minutes

Version 5.0 of a university's exam-results API renames a database column that version 4.x reads.

  1. [1]Analyze the RollingUpdate and Recreate strategies of a Deployment.
  2. [2]Explain how blue-green and canary releases can be built with labels and Services.
  3. [2]Examine which strategy the team should use for version 5.0, and why.
Model answer and marking
  • RollingUpdate (default): replaces Pods a few at a time, within maxSurge and maxUnavailable, so there is no downtime, but old and new versions run side by side for a while.
  • Recreate: stops all old Pods, then starts the new ones. There's a short downtime, but the two versions never run at the same time.
  • Blue-green: run two Deployments, results-blue (4.x, labelled version: blue) and results-green (5.0, version: green). The Service selects version: blue. Test green privately, then change the Service's selector to version: green: all traffic switches at once, and switching back is instant.
  • Canary: both Deployments share a label the Service selects on, for example app: results, with 9 old Pods and 1 new one, so about 10% of requests reach the new version. Watch its errors, then shift the replica counts step by step. (A Gateway API implementation or service mesh can split by explicit weights.)
  • For 5.0: rolling update and canary both run 4.x and 5.0 together, and 4.x Pods would fail once the column is renamed. Use Recreate in a planned maintenance window (stop 4.x, migrate, start 5.0), or blue-green with a single planned cut-over and the migration done at the switch. Better long-term: change the schema in backward-compatible steps (add the new column, deploy, then drop the old one), so rolling updates work again.

Marking (5): RollingUpdate vs Recreate 1; blue-green and canary with labels and Services 2; strategy for the schema change with reasoning 2.

5 marks · 9 minutes

CI pushes the hostel API image to a private repository on Docker Hub, and the new Pods fail with ImagePullBackOff.

  1. [1]Analyze the cause.
  2. [2]Explain how the cluster can be given the credentials it needs to pull the image.
  3. [2]Compare changing the image of a running Deployment directly with changing the image tag in the manifest stored in Git, and analyze which keeps the cluster reproducible.
Model answer and marking
  • Cause: each node's container runtime pulls the image. The repository is private, and the node has no credentials, so the registry answers unauthorized (or “not found”). kubectl describe pod shows it in Events. The kubelet keeps retrying, with longer and longer waits: ImagePullBackOff.
  • Giving credentials: create a read-only access token in Docker Hub, store it as a Secret of type docker-registry (kubectl create secret docker-registry hub-pull --docker-server=... --docker-username=... --docker-password=<token>), and reference it in the Pod template with imagePullSecrets: [ { name: hub-pull } ], or attach it to the namespace's ServiceAccount so every Pod gets it. (On EKS with ECR, the node's IAM role gives pull access instead.)
  • kubectl set image directly: quick, but the cluster now differs from what Git says. There's no review, no record of who changed it or why, and the next kubectl apply of the manifest silently puts the old image back.
  • Changing the tag in Git: the change goes through a pull request, is reviewed, and is recorded in history; apply (or a GitOps tool like Argo CD) makes the cluster match. Anyone can rebuild the cluster from Git, and rollback is a git revert. This keeps the cluster reproducible. Build the image once and promote the same tag (or digest) from dev to prod.

Marking (5): cause 1; how to give the cluster credentials 2; comparison of the two ways, with the reproducible choice justified 2. Exact commands aren't required.

Compare with a model answer

Changing the image changes the Pod template, so the Deployment creates a new ReplicaSet. With maxSurge: 1 it may run one extra Pod, so it starts one new Pod (5 in total). With maxUnavailable: 0 it may not drop below 4 ready Pods, so it waits until the new Pod passes its readiness probe, then removes one old Pod, and repeats until the new ReplicaSet has 4 and the old one has 0. If the new version crashes on start-up, the first new Pod goes into CrashLoopBackOff and never becomes ready, so no old Pod is ever removed. Users keep using the 4 old Pods and see nothing. I'd see it with kubectl rollout status timing out and kubectl get pods, check kubectl logs --previous for the reason, go back with kubectl rollout undo, which scales the old ReplicaSet (kept for this reason) back up, and then fix the image tag in the manifest in Git so the next apply doesn't bring the bad version back.
