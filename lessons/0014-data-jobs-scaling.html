Data, jobs & scaling

Why this matters for DevOps

Pods are cattle: Kubernetes deletes and recreates them all the time, on any node. That's fine for a stateless API, but a database Pod that forgets every order when it moves is a disaster. You also need work that runs on a clock, like a backup at 2 a.m., and apps that grow when a placement-results page gets ten times its usual traffic and shrink again after. These three things are the most common “day two” questions in interviews.

Three ideas, no more

emptyDir vs PersistentVolumeClaim: an emptyDir volume is a scratch folder that lives exactly as long as the Pod. Delete the Pod and it's gone. A PersistentVolumeClaim (PVC) is a request: “I need 1 GiB of disk”. The cluster's StorageClass creates a real disk (a PersistentVolume) for it, which lives on after the Pod. ReadWriteOnce means only one node can mount that disk at a time, which is what a normal cloud disk like AWS EBS allows. [Kubernetes docs: Persistent Volumes]

Job and CronJob: a Deployment keeps Pods running forever. A Job runs a Pod until it finishes successfully. A CronJob creates a Job on a schedule, written in the same format as Linux cron: 0 2 * * * means 02:00 every day, by the cluster's clock unless you set timeZone, for example timeZone: "Asia/Kolkata". Three settings matter: restartPolicy (retry in the same Pod, OnFailure, or never, Never), backoffLimit (how many retries before the Job is marked failed), and concurrencyPolicy (what to do if the last run is still going when the next is due). [Kubernetes docs: CronJob]

HorizontalPodAutoscaler (HPA): a controller that changes a Deployment's replicas to keep average CPU near a target. It reads CPU from metrics-server and works in percent of the CPU request, so a Pod with no CPU request can't be measured at all. [Kubernetes docs: HPA]

Your hostel room is a PVC: you go home for the holidays (the Pod is deleted) and your books are still there when you come back. A train's sleeper berth is an emptyDir: get off, and whatever you left behind is gone. The HPA is the canteen manager who opens a second counter when the queue gets long, and closes it after lunch.

Before you start

Same cluster and folder. Check that your cluster can create disks: there should be a StorageClass marked (default).

kubectl get storageclass

On Docker Desktop and minikube you'll see one (often named hostpath or standard). On a laptop it makes a folder on one node; on AWS the same YAML would create an EBS disk.

Do it: data that survives

  1. First, the wrong storage setup. Keep the password in a local manifest that is excluded from Git. Create db-secret.local.yaml: 
    apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  POSTGRES_PASSWORD: Orders2026
    Add db-secret.local.yaml to .gitignore. Then create db.yaml with a PostgreSQL Deployment that uses emptyDir: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: db
spec:
  replicas: 1
  strategy:
    type: Recreate
  selector:
    matchLabels: { app: db }
  template:
    metadata:
      labels: { app: db }
    spec:
      containers:
        - name: postgres
          image: postgres:17.6
          env:
            - name: POSTGRES_PASSWORD
              valueFrom:
                secretKeyRef: { name: db-secret, key: POSTGRES_PASSWORD }
            - name: PGDATA
              value: /var/lib/postgresql/data/pgdata
          volumeMounts:
            - name: data
              mountPath: /var/lib/postgresql/data
      volumes:
        - name: data
          emptyDir: {}
    printf '%s\n' 'db-secret.local.yaml' >> .gitignore
kubectl apply -f db-secret.local.yaml
kubectl apply -f db.yaml
kubectl rollout status deployment/db
    The password comes from a Secret (lesson 12), the image has a fixed version, and PGDATA points at a sub-folder, which PostgreSQL needs when the mount is a fresh disk.
  2. Save an order, then lose it. Predict first: will the order survive a Pod delete? 
    kubectl exec deploy/db -- psql -U postgres -c "CREATE TABLE orders (id int, item text); INSERT INTO orders VALUES (1, 'masala dosa');"
kubectl exec deploy/db -- psql -U postgres -c "SELECT * FROM orders;"
kubectl delete pod -l app=db
kubectl rollout status deployment/db
kubectl exec deploy/db -- psql -U postgres -c "SELECT * FROM orders;"
    relation "orders" does not exist. The new Pod got a brand new, empty emptyDir. Every order is gone.
  3. Now the right way. Add a PVC to the top of db.yaml, followed by a --- line: 
    apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
spec:
  accessModes: ["ReadWriteOnce"]
  resources:
    requests:
      storage: 1Gi
---
    and at the bottom, replace emptyDir: {} with: 
              persistentVolumeClaim:
            claimName: db-data
    kubectl apply -f db.yaml
kubectl rollout status deployment/db
kubectl get pvc,pv
    The PVC is Bound to a PersistentVolume the StorageClass created for you.
  4. Repeat step 2: create the table, insert the order, delete the Pod, and select again. This time masala dosa is still there. Run kubectl get pod -l app=db -o wide before and after the delete: on most laptop clusters the disk is a folder on one node, so the new Pod is placed on that same node. On AWS, an EBS disk is detached from the old node and attached to the new one instead.
  5. Why replicas: 1 and Recreate? Two PostgreSQL processes writing to the same data folder corrupt it, and a ReadWriteOnce disk can't be mounted on two nodes anyway. A rolling update would start the new Pod while the old one still holds the disk. Recreate stops the old Pod first. Need more than one database copy? That's a StatefulSet with PostgreSQL's own replication, or, more often at work, a managed database like Amazon RDS outside the cluster.

Do it: a nightly job

  1. Write a “backup” CronJob. For the demo it runs every minute and takes 90 seconds, so runs overlap. Create backup.yaml: 
    apiVersion: batch/v1
kind: CronJob
metadata:
  name: backup
spec:
  schedule: "* * * * *"          # at work: "0 2 * * *"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: busybox:1.36
              command: ["sh", "-c", "echo backup started at $(date); sleep 90; echo done"]
    kubectl apply -f backup.yaml
kubectl get jobs -w
    Wait three minutes. A new Job is due every minute, but you never see two running together: with Forbid, a run that's due while the last is still going is skipped. With Allow (the default), two backups would run together and fight over the same files. Replace would kill the old one and start the new one.
  2. Make the backup fail. Change the command to ["sh", "-c", "echo disk full; exit 1"] and restartPolicy to Never, apply, and wait for the next run: 
    kubectl get pods -w
    With Never, each failure makes a new Pod, so you can read every failed run's logs. After the first try plus backoffLimit: 2 retries (3 Pods), the Job is marked Failed and stops. kubectl describe job shows BackoffLimitExceeded. That's the event you'd alert on at work. Before cleanup, inspect kubectl get pv and its RECLAIM POLICY. Deleting the PVC deletes its backing storage when that policy is Delete; with Retain, the volume and data remain for manual recovery. Now run kubectl delete -f backup.yaml -f db.yaml -f db-secret.local.yaml.

Do it: autoscaling

  1. The HPA needs metrics-server. Check if you have it: kubectl top nodes. If you get Metrics API not available, install it, and on a laptop cluster tell it to trust the kubelets' self-signed certificates: 
    kubectl apply -f https://github.com/kubernetes-sigs/metrics-server/releases/download/v0.9.0/components.yaml
kubectl patch -n kube-system deployment metrics-server --type=json \
  -p '[{"op":"add","path":"/spec/template/spec/containers/0/args/-","value":"--kubelet-insecure-tls"}]'
kubectl rollout status -n kube-system deployment/metrics-server
    Metrics Server 0.9.x supports Kubernetes 1.34 and newer. If kubectl version reports Kubernetes 1.31–1.33, use the pinned v0.8.1 components manifest instead. After a minute, kubectl top nodes prints CPU and memory per node.
  2. Deploy a CPU-hungry app (from the Kubernetes docs) with a CPU request, and an HPA. Create hpa.yaml: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: php-apache
spec:
  selector:
    matchLabels: { app: php-apache }
  template:
    metadata:
      labels: { app: php-apache }
    spec:
      containers:
        - name: php-apache
          image: registry.k8s.io/hpa-example
          resources:
            requests: { cpu: 200m }
            limits: { cpu: 500m }
---
apiVersion: v1
kind: Service
metadata:
  name: php-apache
spec:
  selector: { app: php-apache }
  ports:
    - port: 80
---
apiVersion: autoscaling/v2
kind: HorizontalPodAutoscaler
metadata:
  name: php-apache
spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50
    200m means 200 millicores, a fifth of one CPU. 50% utilisation means “aim for 100m per Pod on average”. The Deployment omits replicas: it initially defaults to 1, then the HPA owns that field. Keeping a fixed replica count in a repeatedly applied manifest would fight the autoscaler. 
    kubectl apply -f hpa.yaml
kubectl get hpa php-apache -w
    After a minute, TARGETS shows about cpu: 0%/50%.
  3. Create a rush. In the second terminal, start a load generator: 
    kubectl run load --rm -it --image=busybox:1.36 --restart=Never -- \
  sh -c "while sleep 0.01; do wget -qO- http://php-apache; done"
    Predict first: how many replicas will you get? Watch the first terminal. CPU jumps above 100%, and within a minute or two REPLICAS climbs (to 4 or 5). The HPA's rule is roughly: wanted replicas = current replicas × current CPU ÷ target CPU, rounded up, kept between min and max. Stop the load with Ctrl+C. Scale-down is slow on purpose: by default the HPA waits 5 minutes of low CPU before removing Pods, so a short dip doesn't make it shrink and grow again.
  4. Break it: remove the resources: block (all three lines) from the Deployment and apply. After a minute, kubectl get hpa shows cpu: <unknown>/50%, and kubectl describe hpa php-apache says missing request for cpu. No request means no 100% to measure against, so the HPA does nothing. Clean up: kubectl delete -f hpa.yaml.

What limits how fast you can scale? The HPA checks every 15 seconds and metrics-server data is a little behind; each new Pod must be scheduled, pull its image (fast if small and cached), start, and pass its readiness probe; and if the nodes are full, new Pods stay Pending until a cluster autoscaler adds nodes, which takes minutes. For a known sale, teams raise minReplicas before it starts.

Drill: spot the problems. The placement cell runs MySQL for student records with this Deployment. A 2 GiB PVC called records already exists. Find three problems, and say what happens to the data when the Pod moves to another node. 
spec:
  replicas: 3
  template:
    spec:
      containers:
        - name: mysql
          image: mysql:latest
          env:
            - { name: MYSQL_ROOT_PASSWORD, value: placement@123 }
          volumeMounts:
            - { name: data, mountPath: /var/lib/mysql }
      volumes:
        - name: data
          emptyDir: {}
Show the answer

With emptyDir, the data lives and dies with the Pod: when the Pod moves to another node, every student record is gone. Problems: (1) emptyDir instead of the PVC: use persistentVolumeClaim: { claimName: records }. (2) replicas: 3: three MySQL processes would each have their own empty data, or with one shared disk would corrupt it, and a ReadWriteOnce disk mounts on one node only. Use 1 replica with strategy: Recreate, or a StatefulSet with replication, or a managed database. (3) The root password is in plain text in the manifest: move it to a Secret and use secretKeyRef. Bonus: mysql:latest can jump to a new major version on the next restart and fail to read the old data files; pin a version like mysql:8.4.

Practice questions

5 marks · 9 minutes

A food-delivery app runs PostgreSQL with the Deployment below. A PersistentVolumeClaim named orders-data (10 GiB, ReadWriteOnce) already exists.

apiVersion: apps/v1
kind: Deployment
metadata: { name: db }
spec:
  replicas: 2
  selector: { matchLabels: { app: db } }
  template:
    metadata: { labels: { app: db } }
    spec:
      containers:
      - name: db
        image: postgres:latest
        env:
        - name: POSTGRES_PASSWORD
          value: Food@2026
        volumeMounts:
        - name: data
          mountPath: /data
      volumes:
      - name: data
        persistentVolumeClaim: { claimName: orders-data }
  1. [2]Analyze what happens to the orders when the database Pod is rescheduled to another node.
  2. [3]Detect any three errors or bad practices in the manifest, and state how to fix each.
Model answer and marking
  • Rescheduling: the claim is mounted at /data, but PostgreSQL keeps its files in /var/lib/postgresql/data. So the orders are written to the container's own writable layer, not to the volume. When the Pod is rescheduled, the new container starts empty and every order is lost, even though a PVC exists. (With the right path, the volume would be detached and attached to the new node, and the data would survive.)
  • Wrong mountPath: fix it to /var/lib/postgresql/data (newer images use /var/lib/postgresql; check the image's docs, or set PGDATA to match).
  • replicas: 2: two PostgreSQL servers can't share one data directory; they would corrupt it. A ReadWriteOnce volume also attaches to only one node, so the second Pod may hang in ContainerCreating with a Multi-Attach error. Fix: replicas: 1 with strategy: Recreate (so the old Pod releases the disk before the new one starts), or a StatefulSet or operator with real replication, or a managed database like RDS.
  • postgres:latest: a restart can pull a new major version that can't read the existing data files. Fix: pin a version, for example postgres:17.
  • Password in plain value: anyone who can read the manifest or the Git repo sees it. Fix: valueFrom: secretKeyRef pointing to a Secret.

Marking (5): rescheduling analysis 2; any three errors, each with its fix 3 (1 each). The wrong mountPath may count as one of the three. Exact syntax isn't required.

5 marks · 9 minutes

A college ERP sends each department's attendance report every night at 23:30 using a CronJob.

  1. [3]Analyze the effect of the restartPolicy, backoffLimit and concurrencyPolicy settings on this job.
  2. [2]Examine what should happen if one night's report is still running when the next is due, and which setting controls it.
Model answer and marking
  • How it runs: the CronJob (schedule: "30 23 * * *") creates a Job at each scheduled time; the Job creates a Pod and counts it done when the Pod exits with code 0.
  • restartPolicy (in the Pod template; must be OnFailure or Never, because a Job's Pod is meant to finish): OnFailure restarts the failed container inside the same Pod; Never leaves the failed Pod for you to inspect and the Job creates a new Pod.
  • backoffLimit (default 6): how many times the Job retries, with growing delays, before it's marked Failed. Too high and a broken report keeps retrying for a long time; too low and one short database hiccup fails the whole night. A small number such as 3, plus an alert on failed Jobs, is sensible.
  • concurrencyPolicy: Allow (default) starts the new run alongside the old one; Forbid skips the new run while the old one is still going; Replace stops the old run and starts the new one.
  • If last night's report is still running: two runs at once would load the database twice and could send duplicate or half-finished reports. Use concurrencyPolicy: Forbid, so the new run is skipped, and add activeDeadlineSeconds so a stuck run is stopped long before the next one is due.

Marking (5): the three settings explained 3 (1 each); what should happen on overlap, and which setting controls it 2.

5 marks · 9 minutes

On results day, traffic to a university's results API rises twenty times for a few hours. A HorizontalPodAutoscaler keeps the results Deployment between 3 and 15 replicas at 60% average CPU utilisation.

  1. [2]Explain how it decides when to add or remove Pods.
  2. [1]Analyze why the Pods must declare CPU requests for this to work.
  3. [2]Examine what limits how fast the API can scale.
Model answer and marking
  • Deciding: metrics-server collects each Pod's CPU use from the kubelets. About every 15 s, the HPA works out the average utilisation and calculates desired = ceil(current replicas × current utilisation ÷ 60%), kept between 3 and 15. Example: 3 Pods at 180% → 3 × 180 ÷ 60 = 9 replicas. It scales up quickly; it scales down only after utilisation has stayed low for a while (5 minutes by default), so it doesn't flap.
  • Why CPU requests are needed: utilisation means usage ÷ request. 300m used with a 500m request is 60%. Without a request, there's nothing to divide by: the HPA shows <unknown> and doesn't scale.
  • What limits the speed: the metrics delay (tens of seconds); the max of 15; free space on the nodes, since extra Pods stay Pending until the cluster autoscaler or Karpenter adds nodes, which takes minutes; image pull time and app start-up before readiness passes; and shared parts that don't scale, such as the database's connection limit. Known peaks like results day are better handled by raising minReplicas beforehand.

Marking (5): how it decides, including scale-down 2; why CPU requests are needed 1; what limits scaling speed 2.

Check yourself

Answer before clicking.

1. A Pod with an emptyDir volume is deleted and the Deployment creates a new one. What's in the new Pod's volume?

2. A daily backup sometimes takes longer than 24 hours. You never want two backups running at once, and you never want to kill one half-way. Which setting?

3. An HPA shows cpu: <unknown>/70% and never scales. metrics-server works. Most likely cause?

4. An HPA targets 60% CPU. There are 4 replicas, averaging 90%. About how many replicas will it ask for?

5. Exit question: “Why do we run PostgreSQL with a PVC, one replica and the Recreate strategy, instead of an emptyDir and three replicas?”

Compare with a model answer

An emptyDir is deleted with the Pod, and Kubernetes deletes and recreates Pods all the time, for updates, node failures and rescheduling, so the database would lose its data. A PersistentVolumeClaim asks the StorageClass for a real disk, such as an EBS volume on AWS, which lives on after the Pod and is attached to whichever Pod uses the claim. One replica, because PostgreSQL doesn't allow two servers to share one data folder: they would corrupt it, and a ReadWriteOnce disk can only be mounted on one node anyway. Recreate, because a rolling update would start the new Pod while the old one still holds the disk and the data files; Recreate stops the old one first, with a short downtime. For more than one copy you'd use a StatefulSet with PostgreSQL replication, or a managed database outside the cluster.
