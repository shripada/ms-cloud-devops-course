Manifests & kubectl apply

Why this matters for DevOps

In lessons 9 and 10 you typed commands like kubectl create deployment, kubectl scale and kubectl expose. That works on your laptop. Now imagine a real team: five people, three clusters (dev, staging, production), and an incident at 2 a.m. Someone asks, “how many replicas should the backend have, and who changed it last week?” If the answer only lives in someone's shell history, nobody knows.

Real teams write the desired state of every app into files, keep the files in Git, and let a command (or a CI pipeline) make the cluster match the files. Git then tells you what is running, who changed it, and why, and you can undo a change with git revert. This idea is called declarative configuration, and it's the base of everything in the rest of this course: Terraform in module 3, and GitOps tools like Argo CD at work. [Kubernetes docs: Object management]

Three ideas, no more

Imperative vs declarative: an imperative command says what to do: “scale to 5”, “create this Service”. A declarative file says what should exist: “there is a Deployment called who with 5 replicas”. You hand the file to Kubernetes and it works out the steps. This is the same control loop you saw in lesson 9, where you deleted a Pod and the Deployment brought it back. Now you write the desired state yourself.

A manifest: a YAML file describing one or more Kubernetes objects. Every object has the same four top-level fields [Kubernetes docs: Objects]:

FieldMeaningExample
apiVersionWhich API group and version the object belongs toapps/v1 for Deployments, v1 for Services
kindThe type of objectDeployment, Service
metadataIts name, namespace and labelsname: who
specThe desired state: what you wantreplicas: 3

When you read an object back from the cluster, there is a fifth field, status: what Kubernetes actually has right now. You write spec. Kubernetes writes status, and the controllers keep pushing status towards spec.

kubectl apply: “make the cluster match this file”. If the object doesn't exist, apply creates it. If it exists, apply compares the file with the live object and changes only the fields that differ. If nothing differs, it does nothing. Running it twice is safe, which is what you want in a CI pipeline that runs on every commit. [Kubernetes docs: Declarative management with config files]

Think of ordering lunch for your team. The imperative way: you ring the canteen every time someone joins or leaves: “add one thali”, “cancel one dosa”. Miss a call and nobody knows the real order. The declarative way: a shared sheet lists the order, and the canteen makes whatever the sheet says. To change the order, you edit the sheet. The sheet is your manifest, and the canteen is the control plane.

Before you start

You need the three-node cluster from lesson 9 and a clean default namespace (lesson 10's cleanup step did this). Check:

kubectl config current-context
kubectl get all

You should see docker-desktop (or minikube), and only the built-in kubernetes Service. Make a folder for this lesson and work inside it:

mkdir -p ~/k8s-practice
cd ~/k8s-practice

Any text editor works. VS Code is a good choice: install the “YAML” extension by Red Hat and it will underline Kubernetes mistakes as you type. YAML cares about indentation, and it must be spaces, never tabs.

Do it

  1. You don't have to write YAML from memory. Ask kubectl to print a manifest instead of creating anything. --dry-run=client means “don't send it to the cluster”, and -o yaml prints the object: 
    kubectl create deployment who --image=traefik/whoami --replicas=3 --dry-run=client -o yaml
    Find apiVersion, kind, metadata and spec. Notice app: who appears three times: as the Deployment's own label, in the selector, and on the Pod template. Keep that in mind for step 7. The empty strategy: {}, resources: {} and status: {} lines are noise you can leave out.
  2. To see what a field means, ask the cluster itself. kubectl explain reads the API's own documentation, so it always matches your Kubernetes version: 
    kubectl explain deployment.spec.replicas
kubectl explain deployment.spec.template.spec.containers.ports
  3. Now write the file. Create who.yaml with this content. It holds one object: the Deployment from lesson 9. 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: who
  labels:
    app: who
spec:
  replicas: 3
  selector:
    matchLabels:
      app: who
  template:
    metadata:
      labels:
        app: who
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.11
          ports:
            - containerPort: 80
    Two small upgrades over the generated YAML: the image has a fixed tag, v1.11, not the moving latest (remember lesson 2), and containerPort documents which port the app listens on.
  4. Apply this one file. -f names the file to apply: 
    kubectl apply -f who.yaml
kubectl rollout status deployment/who
kubectl get deployment who
    You see deployment.apps/who created, and after a few seconds 3/3 Pods ready. Same result as kubectl create deployment in lesson 9, but now the desired state is written down in a file.
    Predict first: what will kubectl print if you run the exact same apply again? Write your guess down, then run it: 
    kubectl apply -f who.yaml
    It says deployment.apps/who unchanged. Apply compared the file with the cluster, found nothing different, and did nothing. Running it a hundred times gives the same result. That property is called idempotent, and it's why a CI pipeline can safely run kubectl apply on every push. (Try kubectl create deployment who --image=traefik/whoami now: it fails with already exists.)
  5. Change the app by editing the file, not the cluster. In who.yaml, change replicas: 3 to replicas: 5 and save. Before applying, preview what will change: 
    kubectl diff -f who.yaml
    The output is a normal diff: - replicas: 3 and + replicas: 5, plus a generation number that goes up by one each time the spec changes. Nothing has changed in the cluster yet. Now apply: 
    kubectl apply -f who.yaml
kubectl get deployment who
    This time it says configured, and you have 5 Pods. At work, kubectl diff is what you paste into a pull request so reviewers see exactly what will change in production.
  6. Now play the teammate who “quickly fixes something” by hand at 2 a.m.: 
    kubectl scale deployment/who --replicas=1
kubectl get deployment who
    The cluster now says 1, but your file says 5. This mismatch is called drift. Predict first: what will kubectl diff show, and what will happen after the next apply? 
    kubectl diff -f who.yaml
kubectl apply -f who.yaml
kubectl get deployment who
    The diff shows replicas: 1 going to replicas: 5, and apply puts it back. The file in Git is the source of truth, so a hand fix that isn't also written into the file will be undone by the next deploy. The rule at work: change the file, not the cluster.
  7. Break it on purpose. Kubernetes checks your manifest before accepting it. Copy the file, and in the copy change only the Pod template's label (the one under template:, the third app: who) to app: whoo: 
    cp who.yaml bad.yaml
# edit bad.yaml: under template → metadata → labels, set  app: whoo
kubectl apply -f bad.yaml
    You get: `selector` does not match template `labels`. The Deployment's selector looks for app=who, but its own Pods would carry app=whoo, so it could never find them. Kubernetes refuses the whole Deployment. Now try a typo in a field name. In bad.yaml, fix the label back to who, then change replicas: to replicass:, and apply again. The error is long, but look for unknown field "spec.replicass". Both checks happen on the API server before anything changes, so a broken file never half-applies. Delete the copy: rm bad.yaml.
  8. Your Deployment has no Service yet, so nothing can reach it by name. Add the Service from lesson 10 to the same file. At the end of who.yaml, add a line with just ---, then the Service. The --- line separates two objects in one file: 
    ---
apiVersion: v1
kind: Service
metadata:
  name: who
spec:
  selector:
    app: who
  ports:
    - port: 80
      targetPort: 80
    Read it field by field. It's the same object you printed with kubectl get service who -o yaml in lesson 10:
    • apiVersion: v1 and kind: Service: Services belong to the core API group, which is written as just v1.
    • metadata.name: who: the Service's name, which is also its DNS name. Other Pods call http://who.
    • spec.selector: app: who: send traffic to Pods carrying this label. It has to match the labels on the Pod template (under template.metadata.labels), because those are the labels the Pods actually get.
    • port: 80: the port the Service listens on. targetPort: 80: the port traffic is forwarded to inside the container. It must match the port the app really listens on, the containerPort in the Deployment. If the app listened on 3000, you would keep port: 80 and set targetPort: 3000.
    • There is no type line, so this is a ClusterIP Service, reachable only inside the cluster. To open it to your laptop, you would add type: LoadBalancer under spec. To fix the node port, you would add nodePort: 30090 next to port, with type: NodePort or LoadBalancer.
    Predict first: the file now has two objects, and one of them already exists. What will apply print for each? Then run it: 
    kubectl apply -f who.yaml
kubectl get deployment,service who
    You see deployment.apps/who unchanged and service/who created. Apply handles each object on its own: it left the Deployment alone and created only the missing Service.
  9. Delete what the file created, using the same file: 
    kubectl delete -f who.yaml
kubectl get all
    Both the Deployment and the Service are gone, and only the built-in kubernetes Service remains. Compare with lesson 10, where you had to remember to delete the Service separately. The file remembers for you. Keep who.yaml: you will build on it in the next lessons.
Stretch: make it a real repository. Run git init in ~/k8s-practice, commit who.yaml, and apply it. Then change the image tag to v1.10, run kubectl diff -f who.yaml, commit, and apply. Run kubectl get pods -w in a second terminal while you apply. Answer: changing replicas kept the old Pods, but changing the image replaced every Pod. Why? (Hint: which part of the Deployment did you change, spec.replicas or spec.template? Lesson 13 covers this properly.) Finish with git log -p: the full history of your app's desired state.

Practice questions

5 marks · 9 minutes

A train-booking app's Deployment is kept as a manifest that says replicas: 4. During a rush, someone runs kubectl scale deployment booking --replicas=10 on the live Deployment. The next day, the manifest is applied again.

  1. [1]Analyze the difference between managing workloads imperatively, with one-off commands, and declaratively, with manifests applied by kubectl apply.
  2. [1]Examine why teams keep manifests in Git.
  3. [1]Explain what kubectl diff shows before the apply.
  4. [2]Analyze what happens to the Deployment when the manifest is applied again.
Model answer and marking
  • Imperative vs declarative: imperative commands say what to do, step by step: kubectl create deployment, kubectl scale, kubectl set image. They're quick, but they leave no file behind, can fail if run twice (“already exists”), and the result depends on the order they were typed in. Declarative manifests say what should exist: kubectl apply -f compares the file with the cluster and changes only the difference, creating what's missing and updating what's different. Running it again with no changes does nothing.
  • Why Git: the manifests become the single record of what should run. Every change goes through a pull request and review, history shows who changed what and why, a bad change is undone with git revert, and the whole app can be rebuilt on a new cluster from the repo (and GitOps tools like Argo CD can apply it automatically).
  • What a diff shows: kubectl diff -f sends the manifest to the API server as a dry run and prints, line by line, how the live objects would change: for example - replicas: 10 / + replicas: 4, or a new image tag. Nothing is changed. It's the preview a reviewer checks before applying.
  • The manual scale, then apply: the live Deployment has 10 replicas, but Git still says 4, so the cluster has drifted from the code. When the manifest is applied, replicas is a field the manifest sets, so apply sets it back to 4 and 6 Pods are removed, possibly while traffic is still high. The scale-up was never recorded, so it's silently undone. (Fields the manifest doesn't mention, like an extra annotation added by hand, are left alone.) The fix: make the change in Git, or let an HorizontalPodAutoscaler own the replica count and remove replicas from the manifest so apply doesn't fight it.

Marking (5): imperative versus declarative 1; why Git 1; what a diff shows 1; manual edit analysis 2.

5 marks · 9 minutes

In a food-delivery app:

  • users reach the React frontend from outside the cluster on node port 30090
  • the orders API is called only by the frontend's Nginx proxy, inside the cluster
  • Redis is used only by the orders API
apiVersion: v1
kind: Service
metadata:
  name: frontend
spec:
  type: ClusterIP
  selector:
    app: frontend
  ports:
    - port: 80
      targetPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: orders-api
spec:
  type: NodePort
  selector:
    app: orders-api
  ports:
    - port: 80
      targetPort: 3000
      nodePort: 30300
---
apiVersion: v1
kind: Service
metadata:
  name: redis
spec:
  type: LoadBalancer
  selector:
    app: redis
  ports:
    - port: 6379
      targetPort: 6379
  1. [3]Detect the three problems with how these Services expose the components, and state the fix for each.
  2. [2]Analyze the risk or failure each problem causes.
Model answer and marking
  • frontend is ClusterIP: it has only an internal cluster address, so users outside can't open the app at all. Fix: type: NodePort with nodePort: 30090.
  • orders-api is NodePort 30300: the API is reachable on port 30300 of every node, so anyone who can reach a node can call it directly, skipping the frontend proxy and whatever checks it does, and the attack surface grows. Fix: type: ClusterIP and remove nodePort; the proxy reaches it at orders-api inside the cluster.
  • redis is LoadBalancer: on a cloud this creates a paid load balancer with a public address in front of Redis, which often has no password: anyone on the internet could read or wipe the cache, or plant data. Fix: type: ClusterIP.
  • Principle: expose each component only as far as its callers need. Only the entry point is reachable from outside; everything else stays internal.

Marking (5): three problems, each with its fix 3 (1 each); risk or failure analysed for each 2. A correct description of each fix earns the mark.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. You run kubectl apply -f who.yaml twice in a row without editing anything. What happens the second time?

2. In a manifest, which field holds the state you want?

3. Your Git repo's manifest says replicas: 4. During an incident, a teammate runs kubectl scale --replicas=10. The next day CI runs kubectl apply with the same file. How many replicas are there after that?

4. Before changing production, your lead asks, “show me exactly what this file will change”. Which command do you run?

5. Interview practice (say it out loud or type it): “What's the difference between kubectl create and kubectl apply? Why do teams keep manifests in Git?”

Compare with a model answer

kubectl create is imperative: it creates an object, and fails if the object already exists. kubectl apply is declarative: you give it a manifest describing the desired state, and it creates the object if it's missing, or changes only the fields that differ if it exists. If nothing differs, it does nothing, so it's safe to run again and again, which makes it a good fit for CI. A manifest has apiVersion, kind, metadata and spec; Kubernetes adds status, and the controllers keep the actual state moving towards the spec. Teams keep manifests in Git so the files are the single source of truth: every change is reviewed in a pull request, often with the output of kubectl diff, every change has an author and a reason, and a bad change can be undone with git revert. Changes made by hand with commands like kubectl scale are drift, and the next apply undoes them, so the rule is to change the file, not the cluster. Tools like Helm and Argo CD build on this same idea.
