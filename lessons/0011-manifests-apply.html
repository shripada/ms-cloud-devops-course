Manifests & kubectl apply

Today's goal: write your app (a Deployment and a Service) as a YAML file, create it with kubectl apply, change it by editing the file, preview changes with kubectl diff, and watch the file win when someone changes the cluster by hand. About 30 minutes.

Why this matters for DevOps

In lessons 9 and 10 you typed commands like kubectl create deployment, kubectl scale and kubectl expose. That works on your laptop. Now imagine a real team: five people, three clusters (dev, staging, production), and an incident at 2 a.m. Someone asks, “how many replicas should the backend have, and who changed it last week?” If the answer only lives in someone's shell history, nobody knows.

Real teams write the desired state of every app into files, keep the files in Git, and let a command (or a CI pipeline) make the cluster match the files. Git then tells you what is running, who changed it, and why, and you can undo a change with git revert. This idea is called declarative configuration, and it's the base of everything in the rest of this course: Helm in lesson 17, Terraform in module 3, and GitOps tools like Argo CD at work. [Kubernetes docs: Object management]

Three ideas, no more

Imperative vs declarative: an imperative command says what to do: “scale to 5”, “create this Service”. A declarative file says what should exist: “there is a Deployment called who with 5 replicas”. You hand the file to Kubernetes and it works out the steps. This is the same control loop you saw in lesson 9, where you deleted a Pod and the Deployment brought it back. Now you write the desired state yourself.

A manifest: a YAML file describing one or more Kubernetes objects. Every object has the same four top-level fields [Kubernetes docs: Objects]:

FieldMeaningExample
apiVersionWhich API group and version the object belongs toapps/v1 for Deployments, v1 for Services
kindThe type of objectDeployment, Service
metadataIts name, namespace and labelsname: who
specThe desired state: what you wantreplicas: 3

When you read an object back from the cluster, there is a fifth field, status: what Kubernetes actually has right now. You write spec. Kubernetes writes status, and the controllers keep pushing status towards spec.

kubectl apply: “make the cluster match this file”. If the object doesn't exist, apply creates it. If it exists, apply compares the file with the live object and changes only the fields that differ. If nothing differs, it does nothing. Running it twice is safe, which is what you want in a CI pipeline that runs on every commit. [Kubernetes docs: Declarative management with config files]

Think of ordering lunch for your team. The imperative way: you ring the canteen every time someone joins or leaves: “add one thali”, “cancel one dosa”. Miss a call and nobody knows the real order. The declarative way: a shared sheet lists the order, and the canteen makes whatever the sheet says. To change the order, you edit the sheet. The sheet is your manifest, and the canteen is the control plane.

Before you start

You need the three-node cluster from lesson 9 and a clean default namespace (lesson 10's cleanup step did this). Check:

kubectl config current-context
kubectl get all

You should see docker-desktop (or minikube), and only the built-in kubernetes Service. Make a folder for this lesson and work inside it:

mkdir -p ~/k8s-practice/k8s
cd ~/k8s-practice

Any text editor works. VS Code is a good choice: install the “YAML” extension by Red Hat and it will underline Kubernetes mistakes as you type. YAML cares about indentation, and it must be spaces, never tabs.

Do it

  1. You don't have to write YAML from memory. Ask kubectl to print a manifest instead of creating anything. --dry-run=client means “don't send it to the cluster”, and -o yaml prints the object: 
    kubectl create deployment who --image=traefik/whoami --replicas=3 --dry-run=client -o yaml
    Find apiVersion, kind, metadata and spec. Notice app: who appears three times: as the Deployment's own label, in the selector, and on the Pod template. Keep that in mind for step 7. The empty strategy: {}, resources: {} and status: {} lines are noise you can leave out.
  2. To see what a field means, ask the cluster itself. kubectl explain reads the API's own documentation, so it always matches your Kubernetes version: 
    kubectl explain deployment.spec.replicas
kubectl explain deployment.spec.template.spec.containers.ports
  3. Now write the file. Create k8s/who.yaml with this content. The --- line separates two objects in one file: the Deployment from lesson 9 and the Service from lesson 10. 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: who
  labels:
    app: who
spec:
  replicas: 3
  selector:
    matchLabels:
      app: who
  template:
    metadata:
      labels:
        app: who
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.11
          ports:
            - containerPort: 80
---
apiVersion: v1
kind: Service
metadata:
  name: who
spec:
  selector:
    app: who
  ports:
    - port: 80
      targetPort: 80
    Two small upgrades over the generated YAML: the image has a fixed tag, v1.11, not the moving latest (remember lesson 2), and containerPort documents which port the app listens on.
  4. Apply the whole folder. -f k8s/ applies every YAML file in it: 
    kubectl apply -f k8s/
kubectl rollout status deployment/who
kubectl get deployment,service who
    You see deployment.apps/who created and service/who created. One command, two objects.
    Predict first: what will kubectl print if you run the exact same apply again? Write your guess down, then run it: 
    kubectl apply -f k8s/
    Both lines say unchanged. Apply compared the file with the cluster, found nothing different, and did nothing. Running it a hundred times gives the same result. That property is called idempotent, and it's why a CI pipeline can safely run kubectl apply on every push.
  5. Change the app by editing the file, not the cluster. In k8s/who.yaml, change replicas: 3 to replicas: 5 and save. Before applying, preview what will change: 
    kubectl diff -f k8s/
    The output is a normal diff: - replicas: 3 and + replicas: 5, plus a generation number that goes up by one each time the spec changes. Nothing has changed in the cluster yet. Now apply: 
    kubectl apply -f k8s/
kubectl get deployment who
    The Deployment says configured, and the Service says unchanged. Apply only touched what differed. At work, kubectl diff is what you paste into a pull request so reviewers see exactly what will change in production.
  6. Now play the teammate who “quickly fixes something” by hand at 2 a.m.: 
    kubectl scale deployment/who --replicas=1
kubectl get deployment who
    The cluster now says 1, but your file says 5. This mismatch is called drift. Predict first: what will kubectl diff show, and what will happen after the next apply? 
    kubectl diff -f k8s/
kubectl apply -f k8s/
kubectl get deployment who
    The diff shows replicas: 1 going to replicas: 5, and apply puts it back. The file in Git is the source of truth, so a hand fix that isn't also written into the file will be undone by the next deploy. The rule at work: change the file, not the cluster.
  7. Break it on purpose. Kubernetes checks your manifest before accepting it. Copy the file, and in the copy change only the Pod template's label (the one under template:, the third app: who) to app: whoo: 
    cp k8s/who.yaml bad.yaml
# edit bad.yaml: under template → metadata → labels, set  app: whoo
kubectl apply -f bad.yaml
    You get: `selector` does not match template `labels`. The Deployment's selector looks for app=who, but its own Pods would carry app=whoo, so it could never find them. Kubernetes refuses the whole Deployment. Now try a typo in a field name. In bad.yaml, fix the label back to who, then change replicas: to replicass:, and apply again. The error is long, but look for unknown field "spec.replicass". Both checks happen on the API server before anything changes, so a broken file never half-applies. Delete the copy: rm bad.yaml.
  8. Delete everything the folder created, using the same files: 
    kubectl delete -f k8s/
kubectl get all
    Only the built-in kubernetes Service remains. Compare with lesson 10, where you had to remember to delete the Services separately. The files remember for you. Keep the k8s/ folder: you will build on it in the next lessons.
Stretch: make it a real repository. Run git init in ~/k8s-practice, commit k8s/who.yaml, and apply it. Then change the image tag to v1.10, run kubectl diff -f k8s/, commit, and apply. Run kubectl get pods -w in a second terminal while you apply. Answer: changing replicas kept the old Pods, but changing the image replaced every Pod. Why? (Hint: which part of the Deployment did you change, spec.replicas or spec.template? Lesson 13 covers this properly.) Finish with git log -p: the full history of your app's desired state.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. You run kubectl apply -f k8s/ twice in a row without editing anything. What happens the second time?

2. In a manifest, which field holds the state you want?

3. Your Git repo's manifest says replicas: 4. During an incident, a teammate runs kubectl scale --replicas=10. The next day CI runs kubectl apply with the same file. How many replicas are there after that?

4. Before changing production, your lead asks, “show me exactly what this file will change”. Which command do you run?

5. Interview practice (say it out loud or type it): “What's the difference between kubectl create and kubectl apply? Why do teams keep manifests in Git?”

Compare with a model answer

kubectl create is imperative: it creates an object, and fails if the object already exists. kubectl apply is declarative: you give it a manifest describing the desired state, and it creates the object if it's missing, or changes only the fields that differ if it exists. If nothing differs, it does nothing, so it's safe to run again and again, which makes it a good fit for CI. A manifest has apiVersion, kind, metadata and spec; Kubernetes adds status, and the controllers keep the actual state moving towards the spec. Teams keep manifests in Git so the files are the single source of truth: every change is reviewed in a pull request, often with the output of kubectl diff, every change has an author and a reason, and a bad change can be undone with git revert. Changes made by hand with commands like kubectl scale are drift, and the next apply undoes them, so the rule is to change the file, not the cluster. Tools like Helm and Argo CD build on this same idea.
