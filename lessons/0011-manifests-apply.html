Manifests & kubectl apply

Why this matters for DevOps

In lessons 9 and 10 you typed commands like kubectl create deployment, kubectl scale and kubectl expose. That works on your laptop. Now imagine a real team: five people, three clusters (dev, staging, production), and an incident at 2 a.m. Someone asks, “how many replicas should the backend have, and who changed it last week?” If the answer only lives in someone's shell history, nobody knows.

Real teams write the intended state of their apps into files, keep the files in Git, and let a command (or a CI pipeline) apply those files to the cluster. Git records what should run, who changed it, and why; the cluster still tells you what is actually running. A reverted Git change must be applied again, or reconciled by a GitOps tool, before the cluster changes. This idea is called declarative configuration, and it's the base of everything in the rest of this course: Terraform in module 3, and GitOps tools like Argo CD at work. [Kubernetes docs: Object management]

Three ideas, no more

Imperative vs declarative: an imperative command says what to do: “scale to 5”, “create this Service”. A declarative file says what should exist: “there is a Deployment called who with 5 replicas”. You hand the file to Kubernetes and it works out the steps. This is the same control loop you saw in lesson 9, where you deleted a Pod and the Deployment brought it back. Now you write the desired state yourself.

A manifest: a YAML document describing one Kubernetes object. A YAML file can contain several documents separated by ---. The Deployment and Service in this lesson use four familiar top-level fields [Kubernetes docs: Objects]:

FieldMeaningExample
apiVersionWhich API group and version the object belongs toapps/v1 for Deployments, v1 for Services
kindThe type of objectDeployment, Service
metadataIts name, namespace and labelsname: who
specThe desired state: what you wantreplicas: 3

When you read a Deployment or Service back from the cluster, you also see status: what Kubernetes observes right now. You write spec. Controllers move the actual state towards the spec and report what they observe in status. Not every object uses spec and status: next lesson's ConfigMaps and Secrets store values under fields such as data.

kubectl apply: create the object if it is missing; otherwise calculate a patch from the manifest, the live object and the configuration applied previously. Values declared in the manifest are set on the live object, and fields previously applied but now removed from the manifest are cleared. Unrelated fields added by another writer can remain. Running the same apply again normally changes nothing, which is what you want in a CI pipeline that runs on every commit. Removing a whole object from a multi-document file does not delete the live object automatically; deletion is a separate operation. [Kubernetes docs: Declarative management with config files]

Think of ordering lunch for your team. The imperative way: you ring the canteen every time someone joins or leaves: “add one thali”, “cancel one dosa”. Miss a call and nobody knows the real order. The declarative way: a shared sheet lists the order, and the canteen makes whatever the sheet says. To change the order, you edit the sheet. The sheet is your manifest, and the canteen is the control plane.

Before you start

You need the three-node cluster from lesson 9 and a clean default namespace (lesson 10's cleanup step did this). Check:

kubectl config current-context
kubectl get all

You should see docker-desktop (or minikube), and only the built-in kubernetes Service. Make a folder for this lesson and work inside it:

mkdir -p ~/k8s-practice
cd ~/k8s-practice

Any text editor works. VS Code is a good choice: install the “YAML” extension by Red Hat and it will underline Kubernetes mistakes as you type. YAML cares about indentation, and it must be spaces, never tabs.

Do it

  1. You don't have to write YAML from memory. Ask kubectl to print a manifest instead of creating anything. --dry-run=client means “don't send it to the cluster”, and -o yaml prints the object: 
    kubectl create deployment who --image=traefik/whoami --replicas=3 --dry-run=client -o yaml
    Find apiVersion, kind, metadata and spec. Notice app: who appears three times, but the three occurrences do not have the same job. You will trace them in step 3. The empty strategy: {}, resources: {} and status: {} lines are defaults or output fields you can leave out of this manifest.
  2. To see what a field means, ask the cluster itself. kubectl explain reads the API's own documentation, so it always matches your Kubernetes version: 
    kubectl explain deployment.spec.replicas
kubectl explain deployment.spec.template.spec.containers.ports
  3. Now write the file. Create who.yaml with this content. It holds one object: the Deployment from lesson 9. 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: who
  labels:
    app: who
spec:
  replicas: 3
  selector:
    matchLabels:
      app: who
  template:
    metadata:
      labels:
        app: who
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.11
          ports:
            - containerPort: 80
    Read it from the outside in:
    • apiVersion: apps/v1 and kind: Deployment choose the Deployment API.
    • metadata.name: who names the Deployment. metadata.labels labels the Deployment object itself, for example so you can find it with kubectl get deployments -l app=who. This label does not select Pods and could be omitted without changing which Pods the Deployment manages.
    • spec.replicas: 3 asks the Deployment to keep three Pods running.
    • spec.selector.matchLabels tells the Deployment which Pods belong to it. It must match spec.template.metadata.labels, because the template supplies the labels on every Pod the Deployment creates. Kubernetes rejects a Deployment when these two do not match.
    • spec.template is the blueprint for each Pod. Inside it, containers is a list because a Pod can run more than one container. This Pod runs one container named whoami from the traefik/whoami:v1.11 image.
    • containerPort: 80 documents that the process is expected to listen on port 80. It does not open the port or make the application listen; the process inside the image must actually do that.
    The image has an explicit version tag, v1.11, instead of relying on the moving latest tag (remember lesson 2).
  4. Apply this one file. -f names the file to apply: 
    kubectl apply -f who.yaml
kubectl rollout status deployment/who
kubectl get deployment who
    You see deployment.apps/who created, and after a few seconds 3/3 Pods ready. Same result as kubectl create deployment in lesson 9, but now the desired state is written down in a file.
    Predict first: what will kubectl print if you run the exact same apply again? Write your guess down, then run it: 
    kubectl apply -f who.yaml
    It says deployment.apps/who unchanged. None of the fields managed by this manifest needed changing. Repeating the same operation produces the same result; that property is called idempotent, and it's why a CI pipeline can safely run kubectl apply on every push. (Try kubectl create deployment who --image=traefik/whoami now: it fails with already exists.)
  5. Now change the declared replica count. In who.yaml, change replicas: 3 to replicas: 5 and save. Editing the file records the new intended state; it does not change the running Deployment. Before applying it, preview what Kubernetes would change: 
    kubectl diff -f who.yaml
    The output is a normal diff: - replicas: 3 and + replicas: 5, plus a generation number that goes up by one each time the spec changes. Nothing has changed in the cluster yet. Now apply: 
    kubectl apply -f who.yaml
kubectl get deployment who
    This time it says configured, and you have 5 Pods. At work, kubectl diff is what you paste into a pull request so reviewers see exactly what will change in production.
  6. Now play the teammate who “quickly fixes something” by hand at 2 a.m.: 
    kubectl scale deployment/who --replicas=1
kubectl get deployment who
    The cluster now says 1, but your file says 5. This mismatch is called drift. Predict first: what will kubectl diff show, and what will happen after the next apply? 
    kubectl diff -f who.yaml
kubectl apply -f who.yaml
kubectl get deployment who
    The diff shows replicas: 1 going to replicas: 5, and apply restores 5 because the manifest still says replicas: 5. The earlier kubectl scale command changed only the live Deployment. If the Deployment should stay at 1 replica, change the manifest to replicas: 1 and apply it.
  7. Break it on purpose. Kubernetes checks your manifest before accepting it. Copy the file, and in the copy change only the Pod template's label (the one under template:, the third app: who) to app: whoo: 
    cp who.yaml bad.yaml
# edit bad.yaml: under template → metadata → labels, set  app: whoo
kubectl apply -f bad.yaml
    You get: `selector` does not match template `labels`. The Deployment's selector looks for app=who, but its own Pods would carry app=whoo, so it could never find them. Kubernetes rejects that Deployment update without partly changing the Deployment. Now try a typo in a field name. In bad.yaml, fix the label back to who, then change replicas: to replicass:, and apply again. The error is long, but look for unknown field "spec.replicass". Delete the copy: rm bad.yaml.
  8. Your Deployment has no Service yet, so nothing can reach it by name. Add the Service from lesson 10 to the same file. At the end of who.yaml, add a line with just ---, then the Service. The --- line separates two objects in one file: 
    ---
apiVersion: v1
kind: Service
metadata:
  name: who
spec:
  selector:
    app: who
  ports:
    - port: 80
      targetPort: 80
    Read it field by field. It's the same object you printed with kubectl get service who -o yaml in lesson 10:
    • apiVersion: v1 and kind: Service: Services belong to the core API group, which is written as just v1.
    • metadata.name: who: the Service's name. A Pod in the same namespace can call http://who. A Pod in another namespace needs a qualified name such as who.default or who.default.svc.cluster.local.
    • spec.selector: app: who: send traffic to Pods carrying this label. This selector should match the Pod labels under template.metadata.labels, because those are the labels the Pods actually get. Unlike a mismatched Deployment selector, a Service selector that matches no Pods is still valid: the Service is created, but it has no endpoints and cannot deliver requests.
    • port: 80: the port clients use on the Service. targetPort: 80: the port on the selected Pods to which traffic is sent. The target must be where the application process really listens. The Deployment's containerPort documents that expectation but does not configure the process or control a numeric targetPort. If the app listened on 3000, you would keep port: 80 and set targetPort: 3000.
    • There is no type line, so this is a ClusterIP Service, reachable only inside the cluster. To open it to your laptop on this course setup, you would add type: LoadBalancer under spec. To choose a fixed node port, add nodePort: 30090 next to port and use type: NodePort or LoadBalancer.

    Trace the connection: the Deployment selector must match the Pod-template labels so the Deployment can manage its Pods. The Service selector independently looks for those Pod labels so it can send traffic to them. Client traffic arrives at the Service's port, then goes to the application's real listening port through targetPort.

    Predict first: the file now has two objects, and one of them already exists. What will apply print for each? Then run it: 
    kubectl apply -f who.yaml
kubectl get deployment,service who
    You see deployment.apps/who unchanged and service/who created. Apply handles each object on its own: it left the Deployment alone and created only the missing Service. This also means a multi-document apply is not one transaction. If one object is valid and a later object is invalid, the valid object may already have been changed.
  9. Delete the objects named in the file, using the same file: 
    kubectl delete -f who.yaml
kubectl get all
    Both the Deployment and the Service are gone, and only the built-in kubernetes Service remains. Compare with lesson 10, where you had to remember to delete the Service separately. The file remembers for you. Keep who.yaml: you will build on it in the next lessons.
Stretch: make it a real repository. Run git init in ~/k8s-practice, commit who.yaml, and apply it. Then change the image tag to v1.10, run kubectl diff -f who.yaml, commit, and apply. Run kubectl get pods -w in a second terminal while you apply. Answer: changing replicas kept the old Pods, but changing the image replaced every Pod. Why? (Hint: which part of the Deployment did you change, spec.replicas or spec.template? Lesson 13 covers this properly.) Finish with git log -p: the full history of your app's desired state.

Practice questions

5 marks · 9 minutes

A train-booking app's Deployment is kept as a manifest that says replicas: 4. During a rush, someone runs kubectl scale deployment booking --replicas=10 on the live Deployment. The next day, the manifest is applied again.

  1. [1]Analyze the difference between managing workloads imperatively, with one-off commands, and declaratively, with manifests applied by kubectl apply.
  2. [1]Examine why teams keep manifests in Git.
  3. [1]Explain what kubectl diff shows before the apply.
  4. [2]Analyze what happens to the Deployment when the manifest is applied again.
Model answer and marking
  • Imperative vs declarative: imperative commands say what to do, step by step: kubectl create deployment, kubectl scale, kubectl set image. They're quick, but they leave no file behind, can fail if run twice (“already exists”), and the result depends on the order they were typed in. Declarative manifests say what should exist: kubectl apply -f creates missing objects and patches existing objects so the fields managed by the manifest have the declared values. Running it again with no changes normally does nothing.
  • Why Git: the manifests record what the team intends to run. Pull requests can review each change, history shows who changed what and why, and git revert can restore an earlier configuration. The reverted configuration must then be applied, either by a person, CI or a GitOps tool such as Argo CD. Kubernetes objects stored in the repo can also be recreated on a new cluster.
  • What a diff shows: kubectl diff -f sends the manifest to the API server as a dry run and prints, line by line, how the live objects would change: for example - replicas: 10 / + replicas: 4, or a new image tag. Nothing is changed. It's the preview a reviewer checks before applying.
  • The manual scale, then apply: the live Deployment has 10 replicas, but Git still says 4, so the cluster has drifted from the intended configuration. When the manifest is applied, replicas is a field the manifest manages, so apply sets it back to 4 and 6 Pods are removed, possibly while traffic is still high. The scale-up was never recorded, so it is silently undone. (A field the manifest has never managed, such as a new annotation added by hand, can remain.) The fix: make the change in Git, or let a HorizontalPodAutoscaler own the replica count and remove replicas from the manifest so apply does not fight it.

Marking (5): imperative versus declarative 1; why Git 1; what a diff shows 1; manual edit analysis 2.

5 marks · 9 minutes

An orders API listens on port 8080. A teammate writes these two manifests:

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
  labels:
    app: orders-control
spec:
  selector:
    matchLabels:
      app: orders
  template:
    metadata:
      labels:
        app: orders-v2
    spec:
      containers:
        - name: api
          image: example/orders:v2
          ports:
            - containerPort: 8080
---
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  selector:
    app: order
  ports:
    - port: 80
      targetPort: 3000
  1. [2]Analyze what happens when Kubernetes tries to apply the Deployment, and fix the relevant labels.
  2. [2]Assume the Deployment is fixed. Analyze what happens when the Service is applied, and fix its selector.
  3. [1]Fix the Service port mapping. Does changing containerPort make the application listen on that port?
Model answer and marking
  • Deployment: Kubernetes rejects it because spec.selector.matchLabels says app: orders, while spec.template.metadata.labels says app: orders-v2. Make the Pod-template label app: orders. The Deployment's own metadata.labels.app: orders-control is not the cause: it labels the Deployment object and does not have to match the Pod selector.
  • Service selector: the Service itself is valid and is created, but app: order matches none of the fixed Deployment's Pods, so the Service has no endpoints. Change it to app: orders. Kubernetes does not reject a Service merely because its selector currently matches no Pods.
  • Port mapping: clients use Service port 80, but traffic must go to the API's actual listening port, so set targetPort: 8080. containerPort: 8080 documents the expected port; changing that field alone does not reconfigure the application process.

Marking (5): Deployment rejection, label roles and fix 2; valid Service with no endpoints and selector fix 2; correct target port and containerPort explanation 1.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. You run kubectl apply -f who.yaml twice in a row without editing anything. What happens the second time?

2. In a Deployment manifest, which field holds the state you want?

3. Your Git repo's manifest says replicas: 4. During an incident, a teammate runs kubectl scale --replicas=10. The next day CI runs kubectl apply with the same file. How many replicas are there after that?

4. Before changing production, your lead asks, “show me exactly what this file will change”. Which command do you run?

5. Interview practice (say it out loud or type it): “What's the difference between kubectl create and kubectl apply? Why do teams keep manifests in Git?”

Compare with a model answer

kubectl create deployment is imperative: it creates an object and fails if that object already exists. kubectl apply is declarative: you give it a manifest, and it creates the object if it is missing or patches an existing object so the fields managed by the manifest have the declared values. Reapplying the same configuration normally changes nothing, which makes it a good fit for CI. Deployments and Services have apiVersion, kind, metadata and spec; Kubernetes reports their observed state under status. Teams keep manifests in Git so intended configuration can be reviewed and its history recorded. A revert must be applied before it changes the cluster. If a manifest manages spec.replicas, a manual kubectl scale creates drift and the next apply restores the value from the manifest. Tools such as Helm and Argo CD build on the same declarative idea.
