Your first cluster

Why this matters for DevOps

In module 1 you ran an app and a database with Docker Compose. That works well on one machine. Now think about a real company like IRCTC during Tatkal booking at 10 a.m. They need 50 copies of the booking service spread across many servers. When a server dies, its copies must start again somewhere else in seconds. When new code ships, the old copies must be replaced one by one, so nobody sees an error page. Compose cannot do any of this. Its job is “start these containers on this machine”. Nothing in Compose watches over them afterwards.

Kubernetes (often written K8s: K, 8 letters, s) is a container orchestrator. You tell it what you want running. It decides which machine runs each container, and it keeps checking that everything is still running. Almost every Cloud or DevOps job description in placements mentions it. AWS (EKS), Azure (AKS) and Google Cloud (GKE) all sell Kubernetes as a service. [Kubernetes docs: Overview]

Three ideas, no more

Cluster: a group of machines (called nodes) managed together. The control plane is the brain. It holds the cluster's records (in a database called etcd), decides which node each container runs on (the scheduler), and answers every command you type (the API server). Each node runs an agent called the kubelet, which starts containers when the control plane tells it to. You never log in to nodes to start things. You talk only to the API server, using kubectl. [Kubernetes docs: Cluster architecture]

Pod: the smallest thing Kubernetes runs. A Pod wraps one container, or sometimes a few that must stay together. All containers in a Pod share one IP address. Kubernetes never runs a bare container. It always runs a Pod. Pods are disposable: when one dies, it is not repaired. A new Pod, with a new name and a new IP, replaces it. [Kubernetes docs: Pods]

Deployment: you write down the desired state, for example “3 Pods of nginx, always”. A controller inside the control plane runs a loop forever. It compares the desired state with the actual state and fixes any difference. A Deployment does this through a helper called a ReplicaSet, whose only job is to keep the right number of Pods running. [Kubernetes docs: Deployments]

Think of the AC in your hostel room. You set it to 24°C and walk away. You never say “cool for 10 minutes”. The AC keeps checking the room temperature and does whatever it takes to get back to 24°C. In Kubernetes, the Deployment is your 24°C setting and the controller is the thermostat. This idea, declare what you want and let a loop fix the difference, is the most important idea in all of Kubernetes. [Kubernetes docs: Controllers]

Before you start

You need a practice cluster on your laptop. We will build it to look like a real company cluster: three nodes. One is the control plane node, which runs only the brain. The other two are worker nodes, which run your apps. With two workers you can watch Kubernetes spread copies of your app across machines, so that one machine dying doesn't take the whole app down. In production the brain always gets its own machines, so your apps can't use up the CPU and memory it needs. On EKS, AKS and GKE you don't even see those machines. A single-node cluster hides all of this, so don't use one for this module.

There are two good ways to get a three-node cluster. Pick one. Every kubectl command in this module works the same on both.

Option 1 (recommended): the Kubernetes built into Docker Desktop

You already have Docker Desktop from module 1, on macOS or Windows. It can run a Kubernetes cluster for you, and it comes with kubectl, so there is nothing more to install. [Docker docs: Kubernetes in Docker Desktop]

  1. Open the Docker Desktop Dashboard and go to the Kubernetes view.
  2. Select Create cluster and choose the kind type, not kubeadm. kind can build a multi-node cluster, but kubeadm only gives you a single node.
  3. Set the number of nodes to 3. Docker Desktop makes one control plane node and two worker nodes. Leave the Kubernetes version at its default. Select Create. Setup takes a minute or two.
  4. When the cluster shows as running, open a terminal (Terminal on macOS, PowerShell on Windows) and point kubectl at it: 
    kubectl config use-context docker-desktop

kind needs Docker Desktop's containerd image store. If the kind option is greyed out, go to Settings → General, tick Use containerd for pulling and storing images, and select Apply. If you already made a kubeadm cluster, delete it from the Kubernetes view first. If you don't see a Kubernetes view at all, your Docker Desktop is too old. Update it. The old Settings → Kubernetes → Enable Kubernetes switch only gives you a single node.

Option 2: minikube

minikube is a free tool from the Kubernetes project that runs a practice cluster inside Docker. Choose it if you don't use Docker Desktop (for example, on Linux), or if you want a cluster you can throw away and rebuild without touching Docker Desktop. It needs at least 2 CPUs and 2 GB of free memory for each node (so about 6 GB for three nodes), and 20 GB of free disk. [minikube docs: Get started]

  • macOS (Terminal): 
    brew install kubectl minikube
  • Windows (PowerShell): 
    winget install -e --id Kubernetes.kubectl
winget install Kubernetes.minikube
    Close PowerShell and open it again so it finds the new commands. If you don't have winget, use choco install kubernetes-cli minikube instead. [Kubernetes docs: kubectl on Windows]
  • Both: with Docker running, start a three-node cluster. The first start downloads about 1 GB, so give it a few minutes: 
    minikube start --driver=docker --nodes=3
    minikube also points kubectl at this cluster for you. Each node is one Docker container: minikube is the control plane node, and minikube-m02 and minikube-m03 are the workers. [minikube docs: Multi-node clusters]

If you have both clusters, kubectl config get-contexts lists them, and the one marked * is the cluster your commands go to. At work you will switch between dev, staging and production clusters in exactly this way. Checking your context first is a habit that saves careers.

Do it

  1. Say hello to the cluster: 
    kubectl get nodes
    You should see three nodes with status Ready. On option 1 they are desktop-control-plane (role control-plane), desktop-worker and desktop-worker2. On option 2 they are minikube, minikube-m02 and minikube-m03. Now look at the control plane parts from idea 1. They run as Pods too: 
    kubectl get pods -n kube-system -o wide
    Find the Pods whose names start with etcd-, kube-apiserver-, kube-scheduler- and kube-controller-manager-. The NODE column shows they all run on the control plane node. The controller manager is the thermostat from the AC example: it runs the control loops. kube-proxy appears once on each node, because every node needs it. -n picks a namespace, which works like a folder for cluster objects. Your own work goes in the default namespace.
  2. First, try it the wrong way. Start a bare Pod with no Deployment: 
    kubectl run solo --image=nginx
kubectl get pods
    Wait until solo shows Running, then delete it and list again: 
    kubectl delete pod solo
kubectl get pods
    It's gone for good. Nobody had asked Kubernetes to keep it running, so nobody brought it back.
  3. Now do it the right way. Create a Deployment: 
    kubectl create deployment web --image=nginx
kubectl rollout status deployment/web
    The second command waits until the Pod is ready.
  4. See the chain of three objects it created: 
    kubectl get deployment,replicaset,pods -o wide
    Look at the names. The ReplicaSet is web-<hash>, and the Pod is web-<hash>-<random>. The Deployment owns the ReplicaSet, and the ReplicaSet owns the Pod. The SELECTOR column shows the label app=web. The ReplicaSet counts its Pods by this label, not by name. The Pod's NODE column shows which node the scheduler picked.
  5. Open a second terminal and leave this running. It prints every change to Pods as it happens: 
    kubectl get pods --watch
  6. In your first terminal, delete the Pod. Copy its exact name from step 4: 
    kubectl delete pod web-xxxxxxxxxx-xxxxx
    Watch the second terminal. It shows status changes, not app logs (those come from kubectl logs). The old Pod goes to Terminating, and a new Pod with a different name appears straight away, in ContainerCreating and then Running. This is the control loop at work. The desired state is 1, the actual state dropped to 0, so it created a new Pod.
  7. Scale up to three copies, and watch the second terminal again: 
    kubectl scale deployment/web --replicas=3
kubectl get pods -o wide
    -o wide shows each Pod's own IP address and node. Every Pod gets its own IP. Look at the NODE column: the scheduler spreads the Pods across both workers (three Pods on two workers means one worker gets two), so losing one machine doesn't take down every copy. Each node hands out IPs from its own range, so Pods on different nodes have different-looking IPs. On option 1 no Pod ever lands on the control plane node. That node carries a taint, a “staff only” sign that tells the scheduler to keep ordinary Pods away. See it with: 
    kubectl describe node desktop-control-plane | grep -i taints
    Production clusters do the same. System Pods such as kube-proxy carry a matching toleration, like a staff ID card, so they can still run there. (On option 2, minikube does not taint its control plane node, so your Pods may land on both nodes.) Now try deleting all of them at once. Every Pod made by this Deployment carries the label app=web, so you can select them all by that label: 
    kubectl delete pods -l app=web
    Within seconds, three new Pods are running.
  8. Reach nginx from your Mac. Pods live on the cluster's private network, so for now open a temporary tunnel to the Deployment (lesson 10 shows the proper way): 
    kubectl port-forward deployment/web 8080:80
    Open http://localhost:8080 and you should see “Welcome to nginx!”. Press Ctrl+C to close the tunnel. If port 8080 is already in use, try 8081:80.
  9. Your module 1 debugging habits still work, with kubectl instead of docker: 
    kubectl logs deployment/web
kubectl exec deployment/web -- hostname
kubectl describe deployment web
    At the bottom of describe, the Events list shows what the controller did: “Scaled up replica set … from 1 to 3”. When something breaks, describe and its Events are the first place to look.
  10. Prove that these are still ordinary containers. Each node is itself a container, and your nginx containers run inside the worker nodes. crictl is like docker ps, but for the container runtime inside a node.
    Option 1: look inside each worker node: 
    docker exec desktop-worker crictl ps --name nginx
docker exec desktop-worker2 crictl ps --name nginx
    Option 2: look inside each node: 
    minikube ssh -n minikube-m02 "sudo crictl ps --name nginx"
minikube ssh -n minikube-m03 "sudo crictl ps --name nginx"
minikube ssh -n minikube "sudo crictl ps --name nginx"
    You find three nginx containers in total, and the POD column links each one to its Pod. Everything from lesson 7 (namespaces, cgroups, a shared kernel) still applies. Kubernetes only decides where and how many containers run.
  11. Clean up. Deleting the Deployment also deletes its ReplicaSet and Pods: 
    kubectl delete deployment web
kubectl get pods
    Leave the cluster running for the next lesson. To free memory on option 1, stop the cluster from Docker Desktop's Kubernetes view. On option 2, minikube stop pauses the cluster and minikube start brings it back.
Stretch: while the --watch terminal is open, run kubectl scale deployment/web --replicas=0, then --replicas=5. Then look at kubectl get replicaset. The ReplicaSet's DESIRED column follows whatever you set. Then answer this: who scaled the ReplicaSet, you or the Deployment controller? (Hint: kubectl describe deployment web.)

Practice questions

5 marks · 9 minutes

A cluster has one control plane node and two worker nodes. kubectl apply -f deployment.yaml is run for a canteen-menu Deployment with replicas: 4.

  1. [1]Analyze what kubectl, the API server and etcd do with this request.
  2. [1]Analyze how the controller manager and the scheduler turn it into four placed Pods.
  3. [1]Analyze how the kubelet and the container runtime get the Pods Running.
  4. [2]Analyze what the cluster does when one worker node loses power.
Model answer and marking
  • kubectl → API server → etcd: kubectl reads the YAML and sends it over HTTPS to the API server, using the credentials in kubeconfig. The API server checks who you are and whether you're allowed (authentication, RBAC), validates the object, and saves the Deployment in etcd, the cluster's database. Every other component talks only to the API server.
  • Controllers and scheduler: in the controller manager, the Deployment controller sees the new Deployment and creates a ReplicaSet; the ReplicaSet controller sees it wants 4 Pods and has 0, and creates 4 Pod objects with no node yet. The scheduler sees unscheduled Pods, filters out nodes that can't take them (the control plane node is tainted; nodes without enough CPU or memory for the requests), scores the rest, and binds each Pod to a worker, for example 2 and 2.
  • kubelet and container runtime: the kubelet on each worker watches for Pods bound to its node. It asks the container runtime (containerd, through the CRI) to pull the image and start the containers, sets up the Pod's network, then reports the status back to the API server, which stores it in etcd. kubectl get pods now shows 4 Running.
  • A worker loses power: its kubelet stops sending heartbeats. After about 40–50 seconds the node controller marks the node NotReady, and its 2 Pods are removed from Service endpoints, so traffic goes only to the 2 Pods on the healthy worker. After the eviction timeout (5 minutes by default) those Pods are deleted. The ReplicaSet controller then sees 2 of 4 and creates 2 new Pods, which the scheduler places on the remaining worker if it has room (otherwise they stay Pending until capacity is added). The control plane node isn't used, because of its taint.

Marking (5): sequence 3 (kubectl, API server and etcd 1; controllers and scheduler 1; kubelet and container runtime 1); node failure analysis 2.

5 marks · 9 minutes

A Deployment runs four replicas of a hostel-complaints API.

  1. [2]With a diagram, analyze the relationship between a Deployment, a ReplicaSet and a Pod.
  2. [2]Examine what the cluster does when two of its Pods are deleted at once with kubectl delete pod.
  3. [1]Analyze why teams do not create bare Pods for production workloads.
Model answer and marking 
Deployment  complaints-api   (desired image, replicas: 4, update strategy)
    │ owns
    ▼
ReplicaSet  complaints-api-7d9f8c   (one per version of the Pod template)
    │ owns              selector: app=complaints-api
    ▼
Pod  Pod  Pod  Pod      (each runs the containers; label app=complaints-api)
  • Relationship: you create the Deployment. It creates and manages a ReplicaSet for each version of the Pod template, which is how rolling updates and rollbacks work. The ReplicaSet's only job is to keep exactly N Pods matching its label selector. Pods run the containers. Each layer is the owner of the one below, so deleting the Deployment deletes the rest.
  • Deleting two Pods: the API server deletes them; the ReplicaSet controller, which watches its Pods, sees 2 running against 4 desired and immediately creates 2 new Pods with new names (and usually new IPs). The scheduler places them, the kubelets start them, and once they're Ready they're added to the Service's endpoints. The other 2 Pods keep serving throughout. This is the desired-state control loop: the cluster keeps working to make what's actual match what you declared.
  • Why no bare Pods: a Pod you create directly has no owner. If it's deleted, or its node fails, nothing recreates it. You also can't scale it to more replicas or do a rolling update or rollback. A Deployment gives all of that.

Marking (5): relationship with diagram 2; analysis of the delete 2; why not bare Pods 1.

5 marks · 9 minutes

A college fest website runs as three replicas on a cluster with one control plane node.

  1. [2]With a neat diagram, explain the components of the Kubernetes control plane and of a worker node.
  2. [1]Explain the desired-state reconciliation loop.
  3. [1]Analyze what happens to the website when the only control plane node goes down.
  4. [1]Contrast this with a worker node going down.
Model answer and marking 
CONTROL PLANE NODE                         WORKER NODE (×2)
┌────────────────────────────┐            ┌──────────────────────────┐
│ kube-apiserver  ◄──────────┼── kubectl  │ kubelet ──► container    │
│   │                        │            │             runtime      │
│ etcd (cluster state)       │◄──────────►│ kube-proxy  (containerd) │
│ kube-scheduler             │            │ Pods: [web] [web]        │
│ kube-controller-manager    │            └──────────────────────────┘
└────────────────────────────┘
  • Control plane: the API server is the front door; every component and user talks to it. etcd is the key-value database holding all cluster state. The scheduler picks a node for each new Pod. The controller manager runs the control loops (Deployment, ReplicaSet, node controllers and so on).
  • Worker node: the kubelet starts and watches the Pods assigned to its node and reports their status; the container runtime (containerd) pulls images and runs containers; kube-proxy sets up the network rules that send Service traffic to Pods.
  • Reconciliation loop: you declare the desired state (3 replicas of image v2). Each controller repeatedly compares the desired state with the actual state and acts to close the gap: a Pod is missing, so create one; there's one too many, so delete one. It never stops, which is why the cluster heals itself.
  • Control plane down: the website keeps working. The Pods are already running on the workers, the kubelets keep them running (and restart crashed containers locally), and kube-proxy's rules keep routing traffic. But nothing can change: kubectl doesn't work, no new Pods are scheduled, deleted Pods aren't replaced, nothing scales or updates. That's why production clusters run three control plane nodes (managed services like EKS do this for you).
  • Worker down, by contrast: the Pods on that node stop, but the control plane notices (node NotReady), removes them from the Service, and after the eviction timeout recreates them on the other worker. The website loses some capacity for a while but heals itself, which can't happen while the control plane is down.

Marking (5): diagram with control plane and worker components 2; reconciliation loop 1; control plane failure 1; contrast with worker failure 1.

Compare with a model answer

Docker builds images and runs containers on one machine, but nothing keeps watching them. Kubernetes is an orchestrator. It runs containers across a cluster of nodes, decides which node each one goes on, and keeps them running. You declare the desired state, for example a Deployment with three replicas of an image, and controllers in the control plane keep comparing it with the actual state. If a Pod in a Deployment dies, or its node fails, the ReplicaSet sees that only two of three are running and creates a new Pod. The scheduler places it on a healthy node and the kubelet there starts the container. The new Pod has a new name and IP, which is why we put a Service in front of Pods instead of using their IPs directly.
