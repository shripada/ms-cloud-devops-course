Observability: metrics, dashboards & alerts

Why this matters for DevOps

Customers say “checkout is slow sometimes”. Is it? For everyone, or 1 in 20? Since the last release, or always? Without data, the team argues and guesses. kubectl get pods says Running, but Running doesn't mean users are happy. Observability means the system tells you how it's doing, in numbers you can graph and alert on, so you hear about problems from an alert before you hear from customers, and you can prove a fix worked.

Three ideas, no more

Pull model and /metrics: your app keeps a few running numbers in memory (requests so far, errors so far) and shows them as plain text at an HTTP path, usually /metrics. A client library does this for you, for example prom-client in Node.js. Prometheus asks each target for that page every 15 seconds (it pulls, or scrapes), and stores each number with a timestamp: a time series. On Kubernetes it watches the API to find targets, so new Pods are scraped and deleted Pods dropped, with nobody updating a list. [Prometheus docs: Overview]

Three kinds of metric: a counter only goes up (total requests, total errors). The raw number isn't useful; how fast it grows is, so you use rate(). A gauge goes up and down (memory in use, Pods available). A histogram counts requests into duration buckets (“≤ 0.1 s: 900, ≤ 0.5 s: 980, ≤ 2.5 s: 1000”), which is what you need to calculate percentiles like p95. [Prometheus docs: Metric types]

Dashboards and alerts are separate jobs: Grafana draws graphs. It stores no metrics itself; it queries Prometheus as a data source. Prometheus also evaluates alert rules (“error rate above 5% for 2 minutes”) and sends firing alerts to Alertmanager, which groups related alerts into one message, holds back silenced ones, and delivers them to Slack, email or a paging service. [Prometheus docs: Alertmanager]

A hospital ICU. Each patient's monitor shows heart rate and oxygen (the /metrics page). The central nursing station checks every monitor regularly and keeps the readings (Prometheus). The big screen at the station (Grafana) shows graphs for any bed you pick. And the rule “oxygen below 90% for 2 minutes → call the duty doctor” is an alert. Alertmanager is the operator who doesn't phone the doctor ten times for ten readings of the same patient, and doesn't call at all about a patient who's in surgery (silenced).

Before you start

Your 3-node cluster, with about 2 GB of memory free for the monitoring tools (Docker Desktop → Settings → Resources; 8 GB total works). Delete anything left over from earlier lessons. We install everything with Helm, a package installer for Kubernetes: think apt install, but for a set of manifests. Install it with brew install helm (Windows: winget install Helm.Helm). Make a folder, obs-demo. You'll want three terminals.

Do it: install and collect

  1. Create values.yaml, the settings for the install: 
    prometheus:
  prometheusSpec:
    scrapeInterval: 15s
    retention: 15d
    serviceMonitorSelectorNilUsesHelmValues: false
    ruleSelectorNilUsesHelmValues: false
kubeEtcd: { enabled: false }
kubeControllerManager: { enabled: false }
kubeScheduler: { enabled: false }
kubeProxy: { enabled: false }
    Scrape every 15 seconds, keep 15 days of data. The two ...NilUsesHelmValues: false lines let Prometheus pick up your scrape and alert configs from any namespace. The last four lines turn off checks on control plane parts that a laptop cluster doesn't expose.
  2. Install kube-prometheus-stack: Prometheus, Alertmanager, Grafana, kube-state-metrics and node-exporter, already wired together: 
    helm repo add prometheus-community https://prometheus-community.github.io/helm-charts
helm repo update
helm install monitoring prometheus-community/kube-prometheus-stack \
  -n monitoring --create-namespace -f values.yaml --wait --timeout 10m
kubectl get pods -n monitoring
    It takes 2–3 minutes. Count the node-exporter Pods: three, one per node. That's a DaemonSet.
  3. Deploy an app that has /metrics. podinfo is a small demo web server with a counter and a histogram, and handy paths like /status/500 (return an error) and /delay/1 (answer after 1 second). Create shop-api.yaml: 
    apiVersion: apps/v1
kind: Deployment
metadata:
  name: shop-api
spec:
  replicas: 2
  selector:
    matchLabels: { app: shop-api }
  template:
    metadata:
      labels: { app: shop-api }
    spec:
      containers:
        - name: api
          image: ghcr.io/stefanprodan/podinfo:6.9.2
          ports:
            - { name: http, containerPort: 9898 }
---
apiVersion: v1
kind: Service
metadata:
  name: shop-api
  labels: { app: shop-api }
spec:
  selector: { app: shop-api }
  ports:
    - { name: http, port: 80, targetPort: http }
---
apiVersion: monitoring.coreos.com/v1
kind: ServiceMonitor
metadata:
  name: shop-api
spec:
  selector:
    matchLabels: { app: shop-api }
  endpoints:
    - port: http
      path: /metrics
      interval: 15s
    The ServiceMonitor is new: it tells Prometheus “scrape /metrics on every Pod behind any Service labelled app: shop-api”. It's a label selector, like a Service's, so it follows Pods as they come and go. 
    kubectl apply -f shop-api.yaml
kubectl rollout status deploy shop-api
  4. Look at what Prometheus will read. In terminal 2: 
    kubectl port-forward svc/shop-api 9898:80
    In terminal 1: 
    curl -s localhost:9898/ > /dev/null
curl -s localhost:9898/status/500 > /dev/null
curl -s localhost:9898/metrics | grep -E '^# TYPE http|^http_requests_total|_count'
    You'll see lines like: 
    # TYPE http_requests_total counter
http_requests_total{status="200"} 1
http_requests_total{status="500"} 1
# TYPE http_request_duration_seconds histogram
http_request_duration_seconds_count{method="GET",path="root",status="200"} 1
    A metric name, labels in braces, and a value. That's the whole format. Stop the port-forward (Ctrl+C).
  5. Start some customers: a Pod that sends 9 good requests, 1 failing one and 1 slow one, again and again. 
    kubectl run load --image=busybox:1.36 --restart=Never -- sh -c 'while true; do
  for i in 1 2 3 4 5 6 7 8 9; do wget -qO- http://shop-api/ >/dev/null; done
  wget -qO- http://shop-api/status/500 >/dev/null 2>&1
  wget -qO- http://shop-api/delay/1 >/dev/null
  sleep 0.5; done'
    Predict first: 1 failure in every 11 requests. What error percentage should Prometheus show?
  6. Open Prometheus. In terminal 2: 
    kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-prometheus 9090:9090
    Go to localhost:9090 → Status → Target health. Find shop-api: two targets, both UP, one per Pod. Now scale and watch: 
    kubectl scale deploy shop-api --replicas=3
    Refresh after about 30 seconds: three targets. You changed nothing in Prometheus. It saw the new Pod through the Kubernetes API, because the ServiceMonitor selects by label.

Do it: ask questions of the data

Paste each query into the Query page and press Execute (try the Graph tab too). The language is called PromQL. You don't need to memorise it, but you should be able to explain what each part does.

  1. Request rate, in requests per second, for the whole API: 
    sum(rate(http_requests_total{job="shop-api"}[5m]))
    http_requests_total is a counter: on its own it's just a big number that keeps growing. rate(...[5m]) looks at how much it grew over the last 5 minutes and divides by the seconds, giving requests per second for each Pod. (If a Pod restarts, its counter goes back to 0; rate notices and handles it.) sum adds up all the Pods. Click Graph.
  2. Error percentage, the number users feel: 
    sum(rate(http_requests_total{job="shop-api", status=~"5.."}[5m]))
  /
sum(rate(http_requests_total{job="shop-api"}[5m])) * 100
    Top: rate of requests with a 5xx status (=~"5.." means “5 followed by any two characters”). Bottom: rate of all requests. Divide and multiply by 100. You get about 9, which matches your prediction: 1 in 11.
  3. 95th-percentile latency: the time within which 95% of requests finish. 
    histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="shop-api"}[5m])))
    Each bucket (le means “less than or equal”) is a counter of requests at or under that duration. rate gives how fast each bucket grew, sum by (le) adds the Pods together bucket by bucket, and histogram_quantile finds the bucket where the 95% point falls and estimates within it. You get roughly 1.5 seconds: about 9% of requests take 1 second (the /delay/1 ones), so the 95th percentile falls in the 1–2.5 s bucket. Now try the average: sum(rate(http_request_duration_seconds_sum[5m])) / sum(rate(http_request_duration_seconds_count[5m])). About 0.1 seconds: the average makes it look fine and hides the slow requests. That's why “checkout is slow for some” needs a percentile, and a percentile needs a histogram. Because buckets are just counters, you can add them up across Pods, which you can't do with percentiles each Pod worked out for itself.
  4. The other sources, one query each: 
    kube_deployment_status_replicas_available{deployment="shop-api"}
sum by (pod) (rate(container_cpu_usage_seconds_total{pod=~"shop-api.*", container="api"}[5m]))
node_memory_MemAvailable_bytes
    kube-state-metrics (a gauge: 3), cAdvisor (CPU per Pod, from a counter of CPU-seconds), node-exporter (one series per node).

Do it: one screen in Grafana

  1. Get the password, then open Grafana. In terminal 3: 
    kubectl get secret -n monitoring monitoring-grafana -o jsonpath='{.data.admin-password}' | base64 -d; echo
kubectl port-forward -n monitoring svc/monitoring-grafana 3000:80
    Log in at localhost:3000 as admin with that password. Connections → Data sources shows Prometheus already added: Grafana reads from it and keeps no metrics of its own.
  2. Dashboards → open Kubernetes / Compute Resources / Namespace (Pods). The drop-down lists at the top (namespace and others) are dashboard variables. Grafana fills each list by querying Prometheus for the values that exist. Pick default, then monitoring: every panel redraws. Open any panel's menu → Edit and read its query: it contains namespace="$namespace". The selected value is put into every panel's query. One dashboard serves every team and every cluster.
  3. Build the panel your on-call engineer wants. Dashboards → New → New dashboard → Add visualization → Prometheus. Paste the error-percentage query from step 8, set the title “shop-api error %”, and save. Add a second panel with the p95 query from step 9. That's the start of the one screen: request rate, error rate, latency.

Do it: alert, route, silence

  1. Write the alert rule, alerts.yaml: 
    apiVersion: monitoring.coreos.com/v1
kind: PrometheusRule
metadata:
  name: shop-api-alerts
spec:
  groups:
    - name: shop-api
      rules:
        - alert: ShopApiHighErrorRate
          expr: |
            sum(rate(http_requests_total{job="shop-api", status=~"5.."}[5m]))
              /
            sum(rate(http_requests_total{job="shop-api"}[5m])) > 0.05
          for: 2m
          labels:
            severity: page
          annotations:
            summary: "shop-api: {{ $value | humanizePercentage }} of requests are failing"
    Three parts: what is measured (the share of requests failing over 5 minutes), the threshold (more than 5%), and the duration (for: 2m: it must stay above 5% for 2 minutes, so one bad moment doesn't wake anyone). 
    kubectl apply -f alerts.yaml
  2. In Prometheus, open Alerts. Predict first: with about 9% errors, what state is ShopApiHighErrorRate in after 1 minute, and after 3? First Pending (condition true, waiting out the 2 minutes), then Firing. You'll also see Watchdog always firing, which is on purpose: it proves the alert pipeline works. On a laptop cluster a few built-in alerts like NodeClockNotSynchronising may show as pending; ignore them today.
  3. See it arrive in Alertmanager: 
    kubectl port-forward -n monitoring svc/monitoring-kube-prometheus-alertmanager 9093:9093
    Open localhost:9093. The alert is there, with its labels. In a real setup, Alertmanager's config would send it to Slack: 
    route:
  receiver: oncall-slack
  group_by: [alertname, namespace]
  group_wait: 30s
  repeat_interval: 4h
receivers:
  - name: oncall-slack
    slack_configs:
      - api_url: <Slack webhook URL, from a Secret>
        channel: "#shop-oncall"
        send_resolved: true
    group_by is grouping: if all three Pods break at once, the alerts with the same name and namespace become one Slack message, not three. repeat_interval reminds every 4 hours while it's still firing. send_resolved posts again when it's fixed.
  4. Planned maintenance tonight: you'll restart the database, errors are expected, and nobody should be paged. In the Alertmanager page click New Silence, add the matcher alertname="ShopApiHighErrorRate", set the duration to 1h, write a comment like “planned DB maintenance” and create it. Or from the terminal: 
    kubectl exec -n monitoring alertmanager-monitoring-kube-prometheus-alertmanager-0 -c alertmanager -- \
  amtool --alertmanager.url=http://localhost:9093 silence add \
  alertname=ShopApiHighErrorRate --duration=1h --comment="planned DB maintenance"
    The alert is still firing in Prometheus, but Alertmanager marks it suppressed and sends nothing. When the hour ends, notifications start again by themselves, so a forgotten silence can't hide problems forever.
  5. Fix the “bug”: kubectl delete pod load. Within a few minutes the error rate drops to 0 and the alert resolves.
  6. Clean up: 
    kubectl delete -f alerts.yaml -f shop-api.yaml
helm uninstall monitoring -n monitoring
kubectl delete namespace monitoring

Alert on what users feel, and how much failure is allowed

Why didn't we alert on “CPU above 80%”? Because CPU isn't what users feel. A Pod can sit at 90% CPU and serve every request fast: no one should wake up. And the database can go down, so the API returns 500s instantly while using almost no CPU: users suffer, and a CPU alert stays quiet. Alert on the symptoms users see (errors, latency); use CPU and memory on the dashboard to find the cause.

How many errors are too many? Zero isn't realistic, and chasing it stops you from ever releasing. A service level objective (SLO) sets the target, for example “99.5% of checkout requests succeed, measured over 30 days”. The other 0.5% is the error budget. With 10 lakh checkout requests a month, that's 5,000 failed requests the team may “spend”. A bad release that fails 1% of requests uses up the month's budget in about 15 days, so it gets rolled back. If the budget is nearly used up, the team slows down releases and works on reliability; if lots is left, they can ship faster. The dashboard shows the 30-day success rate and the budget left, and an alert fires when the success rate over the last hour drops below 99.5%:

sum(rate(http_requests_total{job="shop-api", status!~"5.."}[1h]))
  /
sum(rate(http_requests_total{job="shop-api"}[1h])) < 0.995
Drill: spot the problems. A team wrote these alert rules for their API. Find four problems and say how to fix each. 
- alert: APIErrors
  expr: http_requests_total{status="500"} > 100
- alert: APISlow
  expr: avg(http_request_duration_seconds_sum / http_request_duration_seconds_count) > 1
  for: 5m
- alert: HighCPU
  expr: rate(container_cpu_usage_seconds_total{container="api"}[5m]) > 0.8
  labels: { severity: page }
Show the answer

1. Raw counter in APIErrors: a counter only grows, so after the hundredth error since the Pod started, this fires forever, even if there are no errors now. Use the rate of 5xx errors divided by the rate of all requests, a percentage. Also, status="500" misses 502, 503 and 504: use status=~"5..". 2. No for: on APIErrors: one short spike pages someone. Add a duration, like for: 2m. 3. Average latency in APISlow: averages hide the slow requests, and dividing the all-time totals gives an average since the Pod started, not the last few minutes. Use histogram_quantile(0.95, ...) on the rate of the buckets. 4. Paging on CPU: high CPU isn't what users feel, and it can be normal. Show CPU on a dashboard and page on error rate and latency instead. Also accept: no annotations summary, so the person paged doesn't know what's wrong; and HighCPU fires once per Pod (no sum), so one problem sends several pages unless Alertmanager groups them.

Practice questions

5 marks · 9 minutes · part (a)

Users of a train-ticket booking app say seat search is sometimes slow, but the team has no data to confirm it. The team needs:

  • request count, error count and request duration of the search API Pods, and CPU and memory of the nodes
  • collected every 30 seconds
  • kept as time series for 30 days and queried on demand
  1. [1]Choose a suitable tool and justify the choice.
  2. [2]Show how it finds and collects data from search API Pods that the Deployment creates and destroys.
  3. [2]Show how the percentage of search requests that failed with a 5xx status over the last 10 minutes is calculated from the collected data.
Model answer and marking
  • Tool: Prometheus, with node-exporter for node CPU and memory, installed together as kube-prometheus-stack. It's a pull-based time-series database with Kubernetes service discovery, a configurable scrape interval (30 s) and retention (30 days), and a query language (PromQL). A managed service such as CloudWatch Container Insights, well justified, can also earn the choice mark.
  • Finding Pods: the search API exposes /metrics through a client library. Prometheus watches the Kubernetes API; a ServiceMonitor selects the search Service by label, so Prometheus always knows the current Pods behind it. When the Deployment creates a Pod, it's added as a target; when a Pod is deleted, it's dropped. Nobody edits a list of IPs. Every 30 s Prometheus pulls (scrapes) each Pod's /metrics and stores each value with a timestamp and labels such as pod and status.
  • Calculation: http_requests_total is a counter that only goes up, so use its rate: how fast it grew over the last 10 minutes, per second. Take the rate for requests whose status is 5xx, summed over all search Pods; divide by the rate for all requests, summed the same way; multiply by 100. sum(rate(http_requests_total{job="search",status=~"5.."}[10m])) / sum(rate(http_requests_total{job="search"}[10m])) * 100. rate also handles counters that go back to zero when a Pod restarts.

Marking (5): tool choice and justification 1; dynamic discovery of Pods 2; calculation 2 (counter and rate over a 10-minute window 1, ratio of 5xx to all requests 1). Exact query syntax isn't required.

5 marks · 9 minutes · part (b)

The engineer handling production problems wants:

  • one screen showing request rate, error rate and 99th-percentile latency for each service
  • a Slack notification when the search API's 99th-percentile latency stays above 2 seconds for 10 minutes
  1. [2]Choose suitable tools for the screen and the notification, and show how they connect to the data from part (a).
  2. [1]Describe the alert condition: what is measured, the threshold and the duration.
  3. [1]Show how the alert reaches Slack.
  4. [1]Explain why the alert uses the latency users experience rather than high memory usage.
Model answer and marking
  • Tools and how they connect: Grafana for the screen; Alertmanager for Slack (Grafana's own alerting with a Slack contact point is also acceptable). Grafana stores no metrics: it uses Prometheus from (a) as a data source and runs a query for each panel (request rate, error rate, p99), with a service drop-down to pick the service. Prometheus evaluates the alert rule every few seconds and sends firing alerts to Alertmanager.
  • Alert condition: measure the search API's 99th-percentile request duration, calculated from the histogram buckets' rate over the last 5 minutes and summed across Pods (histogram_quantile(0.99, ...)). Threshold: above 2 seconds. Duration: for: 10m, so it fires only if it stays above 2 s for 10 minutes, not for a short spike.
  • To Slack: Alertmanager's route sends alerts (for example those with severity: page) to a receiver with a slack_configs entry: the incoming-webhook URL, kept in a Secret, and the channel. It groups related alerts into one message and sends a “resolved” message when it's fixed.
  • Why latency, not memory: alert on symptoms users feel. Slow search is what users feel; high memory may be normal (caches use memory on purpose) and hurts no one. And search can be slow while memory is fine, for example when the database is slow. Show memory on the dashboard to find the cause; page on latency and errors.

5 marks · 9 minutes · part (a)

For every Pod, the team wants its CPU and memory use and the number of container restarts, with 30 days of history for planning next year's cluster size. kubectl top only shows the current values.

  1. [1]Choose a suitable tool and justify the choice.
  2. [2]Show how the Node.js orders API must expose its own measurements so the tool can collect them.
  3. [1]Explain where each Pod's CPU and memory data come from.
  4. [1]Explain where the restart data come from.
Model answer and marking
  • Tool: Prometheus, with kube-state-metrics and the kubelet's built-in cAdvisor, installed together as kube-prometheus-stack. It's a time-series database with configurable retention (30 days), Kubernetes discovery and a query language. A managed service (CloudWatch Container Insights, Datadog), well justified, can earn the choice mark.
  • How the API exposes its measurements: the API uses a client library, prom-client for Node.js, to keep counters (requests, errors), histograms (request duration) and gauges in memory, and serves them on an HTTP endpoint, usually /metrics, as plain text: metric name, labels, value. Prometheus finds the Pods through the Kubernetes API (a ServiceMonitor selecting the Service by label) and pulls that endpoint every few seconds.
  • CPU and memory: from cAdvisor, which is built into the kubelet on every node and measures each container through its cgroups (container_cpu_usage_seconds_total, container_memory_working_set_bytes). Node-level numbers come from node-exporter.
  • Restarts: from kube-state-metrics, which reads the state of Kubernetes objects from the API server and turns it into metrics, such as kube_pod_container_status_restarts_total and the last termination reason (for example OOMKilled).

Marking (5): tool choice and justification 1; how the API exposes its measurements 2; where CPU and memory data come from 1; where restart data come from 1.

5 marks · 9 minutes · part (b)

Management sets a target: 99.9% of UPI payment requests succeed over every 28-day period. The team needs:

  • a view of progress against the target
  • email and Slack notifications to the engineer handling production problems
  • related alerts grouped into one message
  • alerts switched off during planned maintenance
  1. [2]Choose suitable tools, and show how they connect to each other.
  2. [1]Describe the alert condition that fires when the success rate over the last 30 minutes falls below 99.9%.
  3. [1]Show how alerts are grouped, and switched off during maintenance.

5 marks · 9 minutes · part (a)

After a release, the 99th-percentile latency of a college ERP's login API rose from 300 ms to 3 s. Engineers need to see the last fourteen days and compare the periods before and after the release.

  1. [1]Choose a suitable tool to collect and store this data, and justify the choice.
  2. [2]Explain which kind of measurement (a counter, a gauge or a histogram) the API must record for request duration, and why.
  3. [2]Show how the 99th-percentile latency is worked out from it.
Model answer and marking
  • Tool: Prometheus. It keeps time series for as long as its retention allows (14 days or more) and calculates percentiles from histograms. A managed equivalent, well justified, can earn the choice mark.
  • Counter: only goes up (total logins). Gauge: goes up and down (logins in progress, memory). Histogram: counts how many requests fell into each duration bucket (up to 0.1 s, up to 0.5 s, up to 1 s, up to 5 s…), plus their total count and sum.
  • Why a histogram: an average hides the slow requests: 98 fast logins and 2 very slow ones still average out “fine”. A percentile needs the spread of durations, which only the buckets keep. And bucket counts from all Pods can be added together, which percentiles each Pod worked out for itself can't.
  • Working out p99: take how fast each bucket's count grew over a short window (say 5 minutes), add the buckets up across Pods, and find the duration below which 99% of requests fall, estimated within the bucket where that point lies (histogram_quantile(0.99, ...)). Plot it over the last 14 days with a marker at the release time to compare before and after.

Marking (5): tool choice and justification 1; counter, gauge and histogram explained, and histogram chosen with the reason 2; how the 99th percentile is worked out 2. Exact syntax isn't required.

5 marks · 9 minutes · part (b)

The team runs a staging and a prod cluster, and wants:

  • one place to view the health of both, with a drop-down list to switch between clusters and namespaces
  • a Slack message whenever any Deployment has fewer available replicas than it asks for, for more than 10 minutes
  1. [2]Choose suitable tools for the view and the notification, and show how they connect to the data from part (a) in both clusters.
  2. [1]Explain how the drop-down list works.
  3. [1]Describe the alert condition for the missing replicas.
  4. [1]Show how the alert reaches Slack.
Model answer and marking
  • Tools and how they connect across two clusters: Grafana for the view; Alertmanager (or Grafana's own alerting) for Slack. Each cluster runs its own Prometheus. Grafana has a data source for each, or both send their data to one central store (with Prometheus remote-write, or Thanos or Mimir) with a cluster label on every series. Each Prometheus evaluates the alert rule and sends firing alerts to Alertmanager, which sends them to Slack.
  • Drop-down list: a Grafana dashboard variable. Its options are read from the data: first the list of clusters, then the namespaces that exist in the chosen cluster (for example from label_values(kube_pod_info{cluster="$cluster"}, namespace)). Every panel's query filters on cluster="$cluster", namespace="$namespace", so choosing a different item redraws all panels.
  • Alert condition: for each Deployment, compare the available replicas with the desired replicas, both from kube-state-metrics: kube_deployment_status_replicas_available < kube_deployment_spec_replicas. Fire when this has been true for 10 minutes (for: 10m), naming the cluster, namespace and Deployment in the message.
  • Slack: Alertmanager's route sends these alerts to a Slack receiver (webhook URL and channel), grouped by cluster and namespace so many Deployments failing at once arrive as one message.

Marking (5): tool choice and how they connect across two clusters 2; how the drop-down list works 1; alert condition 1; Slack routing 1. Exact syntax isn't required.

5. Exit question: “Customers report checkout is slow for some requests. Choose tools to measure it, show it on one screen and alert the on-call engineer in Slack. Explain how the API's Pods are found, how the 5xx percentage over 5 minutes is calculated, and why you alert on that instead of CPU.”

Compare with a model answer

Prometheus for collecting and storing, installed as kube-prometheus-stack with node-exporter and kube-state-metrics; Grafana for the screen; Alertmanager for Slack. The API uses a client library to expose a request counter labelled by status and a request-duration histogram on /metrics. Prometheus pulls that every 15 seconds and keeps 15 days of time series. It finds the Pods through the Kubernetes API, using a ServiceMonitor that selects the API's Service by label, so Pods the Deployment creates or deletes are added or dropped automatically. For the 5xx percentage, take the rate at which the counter grew over the last 5 minutes for 5xx statuses, divide by the rate for all requests, summed across Pods, and multiply by 100. Slowness for some requests comes from the histogram: histogram_quantile(0.95, ...) over the bucket rates gives p95, which an average would hide. Grafana uses Prometheus as its data source for panels showing request rate, error rate and p95. Prometheus evaluates the alert rule, for example error rate above 5% for 2 minutes, and sends it to Alertmanager, which groups related alerts into one Slack message and supports silences for maintenance. I alert on the error rate because that's what users experience: CPU can be high while every request succeeds, and requests can fail with CPU low, for example when the database is down.
