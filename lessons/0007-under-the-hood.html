Under the hood

Today's goal: prove to yourself that a container is just a normal Linux process with a limited view (namespaces) and a limited budget (cgroups), all sharing one kernel. About 35 minutes.

Why this matters for DevOps

“What is the difference between a container and a virtual machine?” is asked in almost every Cloud and DevOps interview. Most candidates say “containers are lightweight VMs”, which is wrong, and the interviewer knows it. Today you will see the real answer with your own eyes. It also explains things you have already met: why lesson 6's container got OOMKilled, why each container can use port 80, and why a container stops when PID 1 ends.

Three ideas, no more

A container is a process, not a machine. When you start a container, Docker asks the Linux kernel to start an ordinary process, the same kind you studied in your OS course. There is no second operating system booting. That is why a container starts in under a second and a VM takes a minute.

Namespaces limit what the process can see. The kernel gives the process its own private view of certain things [man7: namespaces]:

  • PID: its own process list, where it is PID 1.
  • NET: its own network interfaces, IP address and ports. (That is why two containers can both use port 80.)
  • MNT: its own filesystem, made from the image layers.
  • UTS: its own hostname.
  • IPC and USER: its own shared memory and user IDs.

cgroups limit what the process can use. Control groups set how much memory, CPU and how many processes a container may use. -m 20m in lesson 6 was a cgroup limit, and the kernel killed the process when it went over. [man7: cgroups]

Hostel analogy: the whole hostel is one Linux machine with one kernel, the warden. Each room is a container. Namespaces are the walls: from inside your room you only see your own things and your own room number. cgroups are the mess card: you get a fixed quota of food and electricity, however hungry you are. A VM, on the other hand, is building a whole separate hostel with its own warden.

One thing first: where is Linux on your Mac?

Namespaces and cgroups are Linux kernel features. macOS does not have them. So Docker Desktop runs a small Linux virtual machine in the background, and every container runs inside it. When this lesson says “the host”, it means that Linux VM, not macOS. On a Linux server in a company, there is no such VM: the containers run directly on the server's kernel.

Do it: one shared kernel

  1. Ask two very different images which kernel they run on: 
    docker run --rm alpine uname -r
docker run --rm ubuntu uname -r
    Both print the same version, something like 7.0.12-linuxkit. That is the kernel of Docker's Linux VM.
  2. Now ask which operating system they think they are: 
    docker run --rm alpine cat /etc/os-release | head -1
docker run --rm ubuntu cat /etc/os-release | head -1
uname -r
    One says Alpine, one says Ubuntu, but the kernel is shared. The image only brings the files of a distribution (its programs and libraries), never its own kernel. The last command runs on your Mac and prints the macOS (Darwin) kernel version, a completely different kernel.

Do it: PID namespace

  1. Start a long-running container: 
    docker run -d --name sleeper alpine sleep 300
  2. Look at the process list from inside: 
    docker exec sleeper ps
    Only two processes: sleep 300 as PID 1, and your ps. The container cannot see anything else on the machine.
  3. Now look at the same process from outside: 
    docker top sleeper
    The same sleep 300, but with a big PID like 6545. One process, two numbers: PID 1 inside its namespace, and a normal PID on the host.
  4. Remove the wall. --pid=host starts a container that shares the host's PID namespace: 
    docker run --rm --pid=host alpine ps | grep 'sleep 300'
docker run --rm --pid=host alpine ps | wc -l
    Now you see the sleeper, with the host PID, among nearly 200 processes of the Linux VM. The isolation you saw in step 2 was only a namespace. Nothing else was hiding it.

Do it: the other namespaces

  1. UTS: give a container its own hostname: 
    docker run --rm --hostname hostel-room-12 alpine hostname
  2. NET: a container has its own network interface and IP address: 
    docker run --rm alpine ip -4 addr show eth0
    You see an address like 172.17.0.3, on the container's own eth0.
  3. See all namespaces of a process. Every file here is one namespace, and its number is its ID: 
    docker run --rm alpine ls -l /proc/self/ns
  4. Compare the PID namespace of two containers: 
    docker exec sleeper readlink /proc/1/ns/pid
docker run --rm alpine readlink /proc/1/ns/pid
    Two different numbers: two separate PID namespaces, two separate “rooms”.

Do it: cgroups

  1. Start a container with a memory and CPU limit, and read the limits from inside: 
    docker run --rm -m 100m --cpus 0.5 alpine \
  cat /sys/fs/cgroup/memory.max /sys/fs/cgroup/cpu.max
    You get 104857600 (100 MB in bytes) and 50000 100000, which means 50,000 microseconds of CPU in every 100,000: half a CPU. These files are the kernel's cgroup settings. Docker just wrote numbers into them.
  2. Without any flags, there is no limit: 
    docker run --rm alpine cat /sys/fs/cgroup/memory.max
    max. By default, one container can use all the memory of the machine. In production you always set limits.
  3. Limit the number of processes, then try to start too many: 
    docker run --rm --pids-limit 5 alpine \
  sh -c 'for i in 1 2 3 4 5 6 7 8; do sleep 5 & done; wait'
    can't fork: Resource temporarily unavailable. That is the cgroup stopping it. This also protects the machine from a “fork bomb”.
  4. You can change a running container's limits, and watch its usage live: 
    docker update --memory 50m --memory-swap 50m sleeper
docker stats --no-stream sleeper
    The memory column now shows / 50MiB.
  5. Clean up: 
    docker rm -f sleeper
Stretch: run docker run --rm alpine id. It says uid=0(root). By default the process inside is root, and without a user namespace it is the same root user as the host, only fenced in by namespaces. This is why good Dockerfiles switch to a non-root user with the USER instruction, and why you should be very careful with --privileged and with mounting /var/run/docker.sock. Then read about “rootless mode” in the Docker docs and explain in two sentences what it changes.

2. Which kernel feature stops a container from seeing other processes, and which stops it from using all the memory?

3. Why can two containers both listen on port 80 at the same time?

4. Inside a container, ps shows sleep 300 as PID 1. On the host, docker top shows it as PID 6545. Which is true?

5. On a Mac, where do your containers' namespaces and cgroups actually live?

6. Interview practice (say it out loud or type it): “What is the difference between a container and a virtual machine? How does Docker isolate containers?”

Compare with a model answer

A VM virtualizes hardware: a hypervisor runs a full guest operating system with its own kernel, so it is heavy, takes a while to boot and is sized in GBs. A container is just a process on the host that shares the host's kernel, so it starts in under a second and only carries the app and its libraries. The isolation comes from two Linux kernel features. Namespaces control what the process can see: its own PID tree where it is PID 1, its own network stack and ports, its own mount tree built from the image layers, hostname, IPC and users. cgroups control what it can use: memory, CPU and number of processes. For example, a memory limit is a cgroup, and going over it gets the process OOM-killed. Because the kernel is shared, isolation is weaker than a VM's, so in production you run as non-root, set resource limits and avoid privileged containers. On a Mac, Docker Desktop runs a small Linux VM, because macOS doesn't have these features.
