Debug broken containers

Today's goal: break four containers on purpose and fix each one with the same four-step method: status, logs, inspect, exec. About 40 minutes.

Why this matters for DevOps

Writing a Dockerfile is maybe 20% of the job. The other 80% is the call that says “the container keeps crashing” or “the site is not opening”. A DevOps engineer is the person who calmly finds out why. Interviewers love this topic because it shows whether you have actually used Docker or only read about it. “A container exits right after starting. How do you debug it?” is one of the most common questions you will get.

Three ideas, no more

Always follow the same order: status → logs → inspect → exec. Don't guess, and don't rebuild blindly. Like a doctor: first check if the patient is breathing (docker ps -a), then ask what happened (docker logs), then read the full report (docker inspect), and only then go inside (docker exec). Nine times out of ten, the logs already tell you the answer.

A container lives only as long as its main process. In your OS course you learnt that every process has a PID and an exit code. The command in CMD runs as PID 1 inside the container. When it ends, for any reason, the container stops. So “my container keeps exiting” really means “my main process keeps ending”, and the exit code tells you how it ended. [Docker docs: exit status]

Exit codes are clues. Learn these few:

  • 0: the process finished normally. Nothing crashed. It simply had no more work to do.
  • 1, 2 and similar small numbers: the app itself reported an error. Read the logs.
  • 125: docker run itself failed, for example a bad flag or name. The container never started.
  • 126 / 127: the command in CMD could not be run, or was not found.
  • 137: the process was killed (128 + signal 9). Often it ran out of memory.

Railway analogy: docker ps -a is the IRCTC status board telling you the train has stopped. docker logs is the guard's diary. docker inspect is the full technical report of the train. docker exec is walking into the coach yourself. You read the board and the diary before you walk down the track.

The toolkit

docker ps -a                        # every container, including stopped ones, with status
docker logs NAME                    # everything the app printed (add -f to keep following)
docker inspect NAME                 # full details as JSON: state, exit code, ports, env, mounts
docker inspect -f '{{.State.ExitCode}}' NAME   # pick out one field
docker exec -it NAME sh             # open a shell inside a RUNNING container
docker port NAME                    # the port forwarding rules
docker stats                        # live CPU and memory use

The official reference for each is in the Docker CLI reference.

Case 1: the database that won't stay up

  1. Start Postgres the way a hurried teammate might: 
    docker run -d --name db postgres:17
    Docker happily prints a container ID. It looks fine.
  2. Status. Check whether it is running: 
    docker ps
docker ps -a
    docker ps shows nothing. docker ps -a shows Exited (1). The container started and died within a second.
  3. Logs. Ask it why: 
    docker logs db
    Error: Database is uninitialized and superuser password is not specified. The image even tells you the fix: -e POSTGRES_PASSWORD=.... Solved in one step.
  4. Fix it and clean up: 
    docker rm db
docker run -d --name db -e POSTGRES_PASSWORD=secret postgres:17
docker ps
docker rm -f db

Case 2: the app with a typo

  1. Make a folder with an app and a Dockerfile that has a mistake in it: 
    mkdir broken-app && cd broken-app
echo 'print("Hello from the quiz app")' > app.py
cat > Dockerfile <<'EOF'
FROM python:3.12-slim
WORKDIR /app
COPY . .
CMD ["python", "main.py"]
EOF
docker build -t broken-app .
    The build succeeds. Docker does not check that main.py exists, because CMD only runs later (remember lesson 3).
  2. Run it and read the clues: 
    docker run --name quiz-app broken-app
docker ps -a --filter name=quiz-app
docker logs quiz-app
    Status is Exited (2), and the log says can't open file '/app/main.py'.
  3. You can't exec into a stopped container. Instead, start a new throwaway container from the same image and run a different command in place of CMD: 
    docker run --rm broken-app ls
    It lists Dockerfile and app.py. There is no main.py. Anything you write after the image name replaces CMD, which makes this a very handy trick for looking inside any image.
  4. Fix the CMD to use app.py, rebuild and run again: 
    docker rm quiz-app
docker build -t broken-app .
docker run --rm broken-app
cd ..

Case 3: running, but the page won't open

  1. Start nginx with a port mistake: 
    docker run -d --name web -p 8080:8080 nginx:alpine
curl localhost:8080
    Connection reset by peer. But docker ps says the container is Up. So the process is fine, and the problem is the path to it.
  2. Inspect. Check the forwarding rule: 
    docker port web
    8080/tcp -> 0.0.0.0:8080. Docker is forwarding to port 8080 inside the container.
  3. Exec. Go inside and test from there, where port publishing does not matter: 
    docker exec web wget -qO- 127.0.0.1:8080
docker exec web wget -qO- 127.0.0.1:80 | head -4
    8080 is refused, 80 works. nginx listens on 80. The fix is -p 8080:80. Testing from inside the container splits the problem in half: if it works inside but not outside, the app is fine and the port mapping is wrong.
  4. Explore while you are in. Open a real shell, look around, then leave: 
    docker exec -it web sh
ps
env
ls /usr/share/nginx/html
exit
    ps shows only nginx's own processes. That is lesson 7's topic.
  5. Fix and clean up: 
    docker rm -f web
docker run -d --name web -p 8080:80 nginx:alpine
curl -s localhost:8080 | head -4
docker rm -f web

Case 4: killed without a single error

  1. Give a container only 20 MB of memory, then ask Python for 200 MB: 
    docker run --name hungry -m 20m python:3.12-slim \
  python -c "x = bytearray(200 * 1024 * 1024)"
    It stops with no Python error at all. The logs are empty too. This is the hardest kind of crash.
  2. Inspect the state: 
    docker inspect -f '{{.State.ExitCode}} {{.State.OOMKilled}}' hungry
    137 true. Exit code 137 and OOMKilled (out of memory) true: the kernel killed it for using more than its limit. When the logs are silent, inspect still knows. You will meet this exact situation in Kubernetes as OOMKilled.
  3. Clean up: 
    docker rm hungry
Stretch: run docker run -d --name quick alpine echo hello, then docker ps -a. It shows Exited (0). Nothing crashed: echo finished, so PID 1 ended, so the container stopped. Beginners often think this is a bug. The Compose commands work like the ones you learnt today.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. You ran docker run -d myapp, but docker ps shows nothing. What should you do first?

2. A container exited with code 137 and OOMKilled: true. What happened?

3. A container exits immediately, so docker exec fails. How can you look at the files inside the image?

4. curl localhost:8080 fails from your Mac, but inside the container wget 127.0.0.1:80 works. Where is the problem?

5. docker ps -a shows Exited (0) for a container that ran a short script. Is something broken?

6. Interview practice (say it out loud or type it): “A container exits right after it starts. Walk me through how you debug it.”

Compare with a model answer

A container runs only as long as its main process, so I'm finding out why that process ended. First docker ps -a to see the status and exit code. Then docker logs, which usually shows the error directly, like a missing environment variable or a file not found. If the logs are empty I use docker inspect to check the exit code, OOMKilled, the command, environment variables and mounts. Exit code 137 with OOMKilled means it hit the memory limit; 126 or 127 means the command couldn't be run or found; 0 means it simply finished, for example because the command runs in the background instead of the foreground. Since I can't exec into a stopped container, I start a new one from the same image with docker run --rm -it IMAGE sh and check the files and the command by hand. Then I fix the Dockerfile or the run command and rebuild.
