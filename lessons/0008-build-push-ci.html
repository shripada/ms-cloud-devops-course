Build & push in CI

Today's goal: make GitHub build, test and publish your Docker image by itself every time you push code. No docker build on your laptop. About 45 minutes.

Why this matters for DevOps

Until now, every image was built on your Mac. In a company, nobody ships an image built on someone's laptop. “It worked on my machine” is exactly the problem Docker was supposed to solve. Instead, a CI pipeline (Continuous Integration) builds the image on a clean server for every change, tests it, and pushes it to a registry. From there, Kubernetes or a cloud service pulls it. Setting up this pipeline is one of the first real tasks a fresher DevOps engineer is given. It also looks very good on your GitHub profile when you apply for placements.

Three ideas, no more

A workflow is a recipe for a robot. It is a YAML file in .github/workflows/ inside your repository. It says when to run (for example, on every push to main) and what to do, as a list of steps. GitHub reads it and runs it on a fresh Linux virtual machine called a runner, which already has Docker installed. [GitHub docs: Actions quickstart]

Most steps are ready-made actions. uses: actions/checkout@v7 means “run the checkout action, version 7”, which downloads your code onto the runner. Docker publishes official actions for logging in to a registry and for building and pushing images. You combine them like Lego blocks instead of writing shell scripts. [Docker docs: GitHub Actions]

Build → test → push, and never push what failed. The pipeline builds the image, starts it and checks that it answers. Only if that passes does it push. On a pull request it builds and tests but does not push, so half-finished work never reaches the registry. Each image is tagged with the Git commit it came from, so you can always tell exactly which code is running.

Mess kitchen analogy: until now you cooked at home and carried the tiffin to college. CI is the college's central kitchen. The recipe (workflow) is pinned on the wall, every batch is cooked in a clean kitchen, a cook tastes it before it leaves (smoke test), and each box is stamped with the batch number (the commit SHA). If a box is bad, you know exactly which batch it came from.

Before you start

  • A GitHub account, and git working on your Mac with a way to push (SSH key or gh auth login).
  • The hello-docker folder from lesson 3 (app.py, requirements.txt, Dockerfile). If you deleted it, make it again from lesson 3's steps 2–4.
  • We push to GitHub Container Registry (ghcr.io), GitHub's own registry. The workflow can log in to it with a token GitHub creates automatically for every run, so you don't need to set up any passwords. [GitHub docs: Container registry]

Do it

  1. Go into your lesson 3 folder and make it a Git repository: 
    cd hello-docker
git init -b main
git add .
git commit -m "Flask app with Dockerfile"
  2. Create an empty repository on GitHub called hello-docker (public, no README), then push to it. Replace YOUR-USERNAME: 
    git remote add origin git@github.com:YOUR-USERNAME/hello-docker.git
git push -u origin main
    If you use the GitHub CLI, gh repo create hello-docker --public --source . --push does both at once.
  3. Create the workflow file. The folder names must be exactly these: 
    mkdir -p .github/workflows
    Then create .github/workflows/docker.yml: 
    name: Build and push image

on:
  push:
    branches: [main]
  pull_request:

permissions:
  contents: read
  packages: write

jobs:
  build:
    runs-on: ubuntu-latest
    steps:
      - name: Get the code
        uses: actions/checkout@v7

      - name: Work out image name and tags
        id: meta
        uses: docker/metadata-action@v6
        with:
          images: ghcr.io/${{ github.repository }}
          tags: |
            type=sha
            type=raw,value=latest,enable={{is_default_branch}}

      - name: Set up Docker Buildx
        uses: docker/setup-buildx-action@v4

      - name: Log in to GitHub Container Registry
        if: github.event_name != 'pull_request'
        uses: docker/login-action@v4
        with:
          registry: ghcr.io
          username: ${{ github.actor }}
          password: ${{ secrets.GITHUB_TOKEN }}

      - name: Build and test the image
        uses: docker/build-push-action@v7
        with:
          context: .
          load: true
          tags: hello-docker:test
          cache-from: type=gha
          cache-to: type=gha,mode=max

      - name: Smoke test
        run: |
          docker run -d --name app -p 5000:5000 hello-docker:test
          sleep 3
          curl --fail --silent localhost:5000

      - name: Push the image
        if: github.event_name != 'pull_request'
        uses: docker/build-push-action@v7
        with:
          context: .
          push: true
          tags: ${{ steps.meta.outputs.tags }}
          labels: ${{ steps.meta.outputs.labels }}
          cache-from: type=gha
    Section by section:
    • on: run on every push to main, and on every pull request.
    • permissions: let this workflow read the code and write packages (images). Without packages: write, the push is refused.
    • runs-on: ubuntu-latest: a fresh Linux VM from GitHub, thrown away after the run.
    • metadata-action: works out the image name ghcr.io/your-username/hello-docker (in lowercase, which registries require) and the tags: sha-1a2b3c4 for every build, plus latest on main.
    • setup-buildx-action: sets up BuildKit, the modern builder you have been using on your Mac all along.
    • login-action: logs in to ghcr.io with GITHUB_TOKEN, a short-lived token GitHub makes for each run. It never appears in the logs. Skipped for pull requests.
    • First build-push-action: builds the image and loads it into the runner's Docker, so the next step can run it. cache-from/cache-to: type=gha saves layers between runs, so lesson 3's layer caching works in CI too.
    • Smoke test: plain shell commands. It starts the container and calls it. curl --fail exits with an error if the app does not answer properly, and that fails the whole run. A failed step stops the job, so the push never happens.
    • Second build-push-action: pushes with the real tags. Thanks to the cache it does not rebuild. It reuses the layers from the first build.
  4. Commit and push the workflow: 
    git add .github
git commit -m "Build, test and push the image in CI"
git push
  5. On GitHub, open your repository and click the Actions tab. You see the run start. Click it, then click the build job, and watch each step's log live. A first run takes one to two minutes. A green tick means it worked.
  6. Find your image: on your repository's main page, look for Packages on the right side. Click hello-docker. You see the tags latest and sha-…. New packages are private by default. Open Package settings, scroll to Danger Zone and change the visibility to Public, so anyone can pull it without logging in.
  7. Pull and run the image that GitHub built, on your Mac: 
    docker run -d --name from-ci -p 5050:5000 ghcr.io/YOUR-USERNAME/hello-docker:latest
curl localhost:5050
docker rm -f from-ci
    Your laptop never built this image. A clean server did, from the exact code in your repository. On an Apple Silicon Mac (M1 or later) you may see a warning that the image's platform linux/amd64 does not match your machine. GitHub's runner is an Intel machine, so it built an Intel image, and Docker Desktop runs it through emulation. It still works. The last stretch below shows how to build for both.
  8. Now make CI catch a mistake. Break the app on purpose: in app.py, change port=5000 to port=5001. Commit and push: 
    git commit -am "Oops: wrong port"
git push
    In the Actions tab, the Smoke test step turns red, and Push the image is skipped. The broken image never reached the registry. latest is still your last good version. Change it back to 5000, commit and push, and the run goes green again.

Version numbers like @v7 move over time. When you read this, a newer major version may exist. Each action's GitHub page shows its latest version. In company projects, teams often pin to an exact commit SHA for security, and let a bot like Dependabot update them.

Stretch: make a new branch, change the message in app.py and open a pull request. Watch the workflow run for the pull request: it builds and runs the smoke test, but the login and push steps are skipped. That is how teams check every change before it is merged. For a second stretch, push a Git tag like v1.0.0 and extend the workflow so it also runs on tags (on: push: tags: ['v*']) and adds type=semver,pattern={{version}} to the tags list. Your image then gets a proper version number too. Finally, add a docker/setup-qemu-action@v4 step before Buildx and platforms: linux/amd64,linux/arm64 to the push step, so one image tag works on both Intel machines and Apple Silicon Macs.

Check yourself

Answer before clicking. Getting it wrong first is fine. That struggle is what makes it stay in your head.

1. Why do companies build images in CI instead of on a developer's laptop?

2. Where must the workflow file be, for GitHub to run it?

3. The smoke test step fails. What happens to the push step?

4. Why tag each image with the commit SHA, not only latest?

5. The workflow logs in to ghcr.io with secrets.GITHUB_TOKEN. Where did you set that password?

6. Interview practice (say it out loud or type it): “Describe a CI pipeline you have built for a Docker image.”

Compare with a model answer

I set up a GitHub Actions workflow for a Flask app. It runs on every push to main and on every pull request, on a fresh Ubuntu runner. It checks out the code, uses Docker's metadata action to work out the image name and tags, sets up Buildx and builds the image with the GitHub Actions layer cache, so unchanged dependency layers are reused between runs. Then a smoke test starts the container and curls it with --fail. If that passes and it's not a pull request, it logs in to GitHub Container Registry with the automatic GITHUB_TOKEN, so no long-lived passwords are stored, and pushes the image tagged with the commit SHA and latest. If any step fails, the push is skipped, so only tested images reach the registry. I tested that by pushing a deliberate bug: the smoke test failed and latest stayed on the last good version.
