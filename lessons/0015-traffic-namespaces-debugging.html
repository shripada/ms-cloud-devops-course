Traffic, namespaces & debugging

Why this matters for DevOps

A real shop has a frontend, an API and more, all behind one website address. Giving each Service its own cloud load balancer creates another billable resource and another address, certificate and firewall policy to manage. And a real cluster isn't yours alone: dev, testing and sometimes other teams share it, so one team's mistake must not starve the others. Finally, every week something is Pending or CrashLoopBackOff, and the person who can find out why in two minutes is the one the team calls.

Three ideas, no more

Gateway API and its implementation: Gateway API is the modern Kubernetes API for traffic entering and moving through a cluster. A GatewayClass chooses an implementation, a Gateway declares listeners such as HTTP on port 80, and an HTTPRoute says “requests for shop.local whose path is /api or under it (/api/orders, but not /apiary) go to the api Service”. These objects are configuration; they do not proxy traffic by themselves. In this lesson, the Envoy Gateway controller watches them and configures Envoy Proxy Pods, which handle the live requests. Kubernetes recommends Gateway API for new work; the older Ingress API is frozen but not scheduled for removal. [Gateway API: Getting started] [Envoy Gateway architecture]

Namespaces, labels and ResourceQuotas: a namespace is a folder for objects: names only have to be unique inside it, and you give each team its own. Labels are tags on objects (app=front, team=testing) that you filter on with -l. A ResourceQuota caps what one namespace may use in total: CPU, memory, number of Pods. The API server refuses any new Pod that would go over. [Kubernetes docs: Resource Quotas]

kubeconfig and contexts: ~/.kube/config lists clusters, users (credentials) and contexts. A context is a saved combination of cluster, user and default namespace. kubectl talks to whichever context is current. One engineer with a laptop cluster and an EKS cluster has two contexts and switches between them. [Kubernetes docs: kubeconfig]

A big apartment building has one main gate. The gate itself is the Gateway, the security company named in its contract is the GatewayClass, and the visitor register contains the HTTPRoute rules: “visitors for flat 4B, go to Tower A”. Envoy Proxy is the guard who handles each visitor. Each tower is a namespace, and “each tower gets at most 3 parking spots” is a ResourceQuota.

Before you start

Same cluster and folder. You need about 1 GB of free memory for Envoy Gateway and the managed Envoy Proxy. Open a second terminal. The install manifest is pinned to Envoy Gateway v1.9.2 so the exercise does not change underneath you.

Do it: one Gateway, two Services

  1. Install the Gateway API CRDs and the Envoy Gateway controller from the project's pinned manifest, then wait for the controller: 
    kubectl apply --server-side -f https://github.com/envoyproxy/gateway/releases/download/v1.9.2/install.yaml
kubectl wait --timeout=5m -n envoy-gateway-system deployment/envoy-gateway --for=condition=Available
kubectl get crd gateways.gateway.networking.k8s.io
    Envoy Gateway is the control plane: it watches Gateway API objects and creates or configures Envoy Proxy as the data plane. Envoy Proxy alone would not watch these Kubernetes objects.
  2. Declare both applications, both internal Services and the complete routing configuration in shop.yaml: 
    apiVersion: apps/v1
kind: Deployment
metadata: { name: web }
spec:
  replicas: 2
  selector:
    matchLabels: { app: web }
  template:
    metadata:
      labels: { app: web }
    spec:
      containers:

          image: traefik/whoami:v1.11
          ports: [{ name: http, containerPort: 80 }]
---
apiVersion: v1
kind: Service
metadata: { name: web }
spec:
  selector: { app: web }
  ports: [{ name: http, port: 80, targetPort: http }]
---
apiVersion: apps/v1
kind: Deployment
metadata: { name: api }
spec:
  replicas: 2
  selector:
    matchLabels: { app: api }
  template:
    metadata:
      labels: { app: api }
    spec:
      containers:
        - name: whoami

          ports: [{ name: http, containerPort: 80 }]
---
apiVersion: v1
kind: Service
metadata: { name: api }
spec:
  selector: { app: api }
  ports: [{ name: http, port: 80, targetPort: http }]
---
apiVersion: gateway.networking.k8s.io/v1
kind: GatewayClass
metadata: { name: eg }
spec:
  controllerName: gateway.envoyproxy.io/gatewayclass-controller
---
apiVersion: gateway.networking.k8s.io/v1
kind: Gateway
metadata: { name: shop }
spec:
  gatewayClassName: eg
  listeners:
    - name: http
      protocol: HTTP

        namespaces: { from: Same }
---

metadata: { name: shop }

    - name: shop

      backendRefs:
        - { name: web, port: 80 }
    The application Services omit type, so they are ClusterIP Services. Only Envoy's entry-point Service needs external exposure. This lab keeps every object together so you can see the complete system. At work, a platform team commonly owns the GatewayClass and shared Gateway, while application teams own their Deployments, Services and HTTPRoutes.
  3. Apply the one file and inspect both desired and observed state: 
    kubectl apply -f shop.yaml
kubectl rollout status deployment/web
kubectl rollout status deployment/api
kubectl get gatewayclass,gateway,httproute
kubectl describe gateway shop
kubectl describe httproute shop
    The Gateway should become Accepted and Programmed; the HTTPRoute should show that its parent accepted it. Envoy Gateway also creates an Envoy Proxy Deployment and a LoadBalancer Service for this Gateway.
  4. Find that LoadBalancer Service: 
    kubectl get service -n envoy-gateway-system \
  -l gateway.envoyproxy.io/owning-gateway-namespace=default,gateway.envoyproxy.io/owning-gateway-name=shop
    On minikube, run minikube tunnel in the second terminal. On a supported cloud or a local cluster with a load-balancer implementation, use the address in kubectl get gateway shop: 
    GATEWAY_HOST=$(kubectl get gateway shop -o jsonpath='{.status.addresses[0].value}')
curl -s -H "Host: shop.local" http://$GATEWAY_HOST/ | grep Hostname
curl -s -H "Host: shop.local" http://$GATEWAY_HOST/api/orders | grep Hostname
    If the address remains empty or <pending>, the cluster has no LoadBalancer implementation; that is an infrastructure condition, not an HTTPRoute error.
    For a local fallback, find the generated Service and port-forward it: 
    ENVOY_SERVICE=$(kubectl get service -n envoy-gateway-system \
  -l gateway.envoyproxy.io/owning-gateway-namespace=default,gateway.envoyproxy.io/owning-gateway-name=shop \
  -o jsonpath='{.items[0].metadata.name}')
kubectl port-forward -n envoy-gateway-system service/$ENVOY_SERVICE 8080:80
    This fallback enters through Envoy and exercises the Gateway and HTTPRoute, but bypasses the external load balancer. Back in the first terminal, send requests with the Host header: 
    curl -s -H "Host: shop.local" http://localhost:8080/ | grep Hostname
curl -s -H "Host: shop.local" http://localhost:8080/api/orders | grep Hostname
curl -s -H "Host: other.local" http://localhost:8080/ | head -3
    The first answers from a web-… Pod, the second from an api-… Pod, and the third gets 404 because no route matches that hostname. One Envoy entry point routes to both internal Services.
  5. Break the route twice. First, change the / match from PathPrefix to Exact, apply, and try / and /about. Only / works. Restore PathPrefix. Second, change the HTTPRoute's parentRefs name from shop to missing and apply. kubectl describe httproute shop no longer shows an accepted attachment to the working Gateway, and the route is not programmed. Restore shop, apply, and wait for the accepted status.

Do it: sharing a cluster

  1. Give the testing team a namespace and a quota. Create testing.yaml: 
    apiVersion: v1
kind: Namespace
metadata:
  name: testing
---
apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: testing
spec:
  hard:
    pods: "3"
    requests.cpu: "1"
    requests.memory: 1Gi
    kubectl apply -f testing.yaml
kubectl describe quota -n testing
  2. The testing team asks for 5 replicas. Add the Deployment and its internal Service to the bottom of testing.yaml: 
    ---
apiVersion: apps/v1
kind: Deployment
metadata:
  name: front
  namespace: testing
spec:
  replicas: 5
  selector:
    matchLabels: { app: front }
  template:
    metadata:
      labels: { app: front }
    spec:
      containers:
        - name: front
          image: traefik/whoami:v1.11
          ports: [{ name: http, containerPort: 80 }]
---
apiVersion: v1
kind: Service
metadata:
  name: front
  namespace: testing
spec:
  selector: { app: front }
  ports: [{ name: http, port: 80, targetPort: http }]
    Predict first: how many Pods start? Apply the complete desired state: 
    kubectl apply -f testing.yaml
kubectl get pods -n testing
kubectl get events -n testing --sort-by=.lastTimestamp | tail -3
    Zero! The event says something like failed quota: team-quota: must specify requests.cpu…. Once a namespace has a CPU or memory quota, every Pod must say how much it requests, or the quota can't count it. Add this under the container in testing.yaml, beside ports: 
              resources:
            requests:
              cpu: 100m
              memory: 64Mi
    Reconcile from the file: 
    kubectl apply -f testing.yaml
sleep 10
kubectl get pods -n testing
kubectl describe quota -n testing
    Now 3 Pods run. The quota shows pods 3/3. The events say exceeded quota: team-quota, requested: pods=1, used: pods=3, limited: pods=3. The Deployment still wants 5, and the ReplicaSet keeps trying, but the API server refuses Pods 4 and 5. Nothing in default was affected.
  3. Labels and names across namespaces: 
    kubectl get pods -n testing -l app=front
kubectl get pods -A -l app=front
kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- \
  wget -qO- http://front.testing.svc.cluster.local | grep Hostname
    -l filters by label, -A looks in all namespaces. A temporary Pod in default reached the manifest-managed Service in testing by its full DNS name, <service>.<namespace>.svc.cluster.local. Inside the same namespace the short name (front) is enough. Note what namespaces don't do: they don't block network traffic between teams. That needs a NetworkPolicy. Clean up with kubectl delete -f testing.yaml; because the file includes the Namespace, everything in it is removed.
  4. Look at your kubeconfig: 
    kubectl config get-contexts
kubectl config current-context
kubectl config view --minify
    The * marks the current context. When you later run aws eks update-kubeconfig --name shop-prod, it adds a second context to this file. Then kubectl config use-context <name> switches, and kubectl --context <name> get pods runs one command against the other cluster. The habit that saves careers: check the current context before any delete.

  1. Make a Pending Pod and read the message: 
    kubectl create deployment big --image=traefik/whoami:v1.11
kubectl set resources deployment big --requests=memory=64Gi
kubectl get pods -l app=big
kubectl describe pod -l app=big | grep -A3 Events
    Read it piece by piece: 0/3 nodes are available: 1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: }, 2 Insufficient memory. That's all three nodes explained: the control plane node is tainted so normal Pods stay off it (lesson 9), and neither worker has 64 GiB free. Fix: ask for a sensible amount (or add bigger nodes). kubectl delete deployment big.
  2. One more pattern to recognise: an API's logs say connect ECONNREFUSED 127.0.0.1:5432. Inside a Pod, 127.0.0.1 (localhost) is the Pod itself, and the database runs in a different Pod. The app must use the database's Service name, like db or db.shop.svc.cluster.local, usually set through a ConfigMap. It works when the app and database both run straight on your laptop, then breaks in the cluster, so it shows up in nearly every first deploy.
  3. Clean up everything from today. Stop the port-forward or minikube tunnel with Ctrl+C, then delete the application, Services and routing objects from their authoritative file: kubectl delete -f shop.yaml. To remove Envoy Gateway and its CRDs too, run kubectl delete -f https://github.com/envoyproxy/gateway/releases/download/v1.9.2/install.yaml.
Drill: spot the problems. This HTTPRoute should attach to the fest Gateway, send everything for fest.example.com to the site Service, and send everything under /tickets to the tickets Service. Both Services listen on port 80. Find three errors. 
apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: fest }
spec:
  parentRefs: [{ name: missing }]
  hostnames: [fest.example.com]
  rules:
    - matches:
        - path: { type: Exact, value: /tickets }
      backendRefs: [{ name: tickets, port: 80 }]
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs: [{ name: fest-site, port: 8080 }]
Show the answer

1. Wrong parent: parentRefs names missing, so this route does not attach to the fest Gateway. Use name: fest. 2. type: Exact on /tickets: /tickets/123 does not match and falls through to the / rule. Use PathPrefix. 3. The / backend is wrong: the Service is called site, not fest-site, and it listens on 80, not 8080. Fix both the name and port. kubectl describe httproute fest and its status conditions help distinguish attachment and backend-reference failures.

Practice questions

5 marks · 9 minutes

The HTTPRoute below should attach to the food Gateway, send every request for food.example.com to the frontend Service, and send requests under /api to the orders-api Service. Both Services listen on port 80.

apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata: { name: food }
spec:
  parentRefs: [{ name: shop }]
  hostnames: [food.example.com]
  rules:
    - matches:
        - path: { type: PathPrefix, value: / }
      backendRefs: [{ name: frontend, port: 80 }]
    - matches:
        - path: { type: Exact, value: /api }
      backendRefs: [{ name: orders, port: 80 }]
  1. [3]Detect any three errors, and state how to fix each.
  2. [2]Analyze why one shared Gateway is cheaper and simpler than giving each application Service its own cloud load balancer.
Model answer and marking
  • Wrong parent: parentRefs names shop, but the required Gateway is food. The route is not attached to the intended listener. Fix: name: food.
  • type: Exact on /api: only the exact path /api matches; /api/orders/42 falls through to the / rule and goes to the frontend. Fix: type: PathPrefix.
  • Backend name orders: the Service is called orders-api. The route condition reports an unresolved backend reference, and API requests cannot be delivered. Fix: name: orders-api.
  • Why one Gateway is cheaper and simpler: with the usual cloud implementation, each application Service of type LoadBalancer requests its own external load balancer. A shared Gateway exposes one proxy fleet through one LoadBalancer Service and routes by hostname and path to many internal ClusterIP Services. That centralizes addresses, TLS and routing policy. Exact billing and whether load balancers can be shared are implementation-specific.

Marking (5): any three errors, each with its fix 3 (1 each); why one Gateway is cheaper and simpler 2.

5 marks · 9 minutes

One cluster is shared by a backend team and a QA team. The qa namespace has a ResourceQuota of 6 CPUs, 12 GiB of memory and 30 Pods.

  1. [2]Analyze how namespaces, labels and ResourceQuotas keep the two teams from affecting each other.
  2. [2]Examine what happens when the QA team tries to start a Pod that would go over the quota.
  3. [1]Explain how labels let them list only their API Pods.
Model answer and marking
  • Namespaces: each team gets its own (backend, qa). Names only need to be unique inside a namespace, so both can have a Deployment called api; RBAC can give each team rights only in its own namespace; deleting a namespace removes only that team's objects.
  • ResourceQuotas: cap the total requests and object counts of one namespace, so one team can't use up the cluster's CPU and memory and leave the other team's Pods Pending.
  • Going over the quota: the API server checks the quota when the Pod is created and refuses it with exceeded quota. The Pod is never created (it isn't Pending). If a Deployment asked for it, the ReplicaSet's events show FailedCreate ... exceeded quota, and the Deployment stays below its desired count until something is freed. Once a namespace has a CPU or memory quota, every Pod must declare requests, or it's refused too.
  • Labels: key-value tags such as app=api, team=qa. kubectl get pods -n qa -l app=api lists only their API Pods; Services and Deployments use the same label selectors to find their Pods.

Marking (5): how namespaces, labels and quotas separate the teams 2; what happens when the quota would be exceeded 2; listing by label 1. Exact commands aren't required.

5 marks · 9 minutes

Three ways of getting a cluster: a local multi-node cluster on a laptop (kind or minikube), a cluster built with kubeadm on three virtual machines, and a managed cluster such as Azure AKS or Amazon EKS.

  1. [3]Compare the three, and analyze which suits a student's laptop, a training institute's lab and a production food-delivery company.
  2. [2]Explain the role of the kubeconfig file and contexts when one engineer works with a staging and a production cluster.
Model answer and marking
  • kind / minikube: nodes are containers or a VM on one machine; one command to create or delete; free; not highly available. Suits a student's laptop: quick practice that can be thrown away.
  • kubeadm on VMs: you install the runtime, run kubeadm init on the control plane and kubeadm join on the workers, and you run upgrades, certificates and etcd backups yourself. Suits a training institute lab: students see every part, and it runs on hardware they already have.
  • Managed (AKS, EKS, GKE): the cloud operates the control plane and its etcd storage; the customer still plans Kubernetes upgrades and manages node pools, networking and add-ons. It suits production when reducing control-plane operations is worth the cloud cost.
  • kubeconfig and contexts: ~/.kube/config lists clusters (API server address and CA certificate), users (credentials) and contexts. A context is a named combination of cluster, user and default namespace. The engineer has a staging and a prod context; kubectl uses the current one, kubectl config use-context prod switches, and --context runs one command against the other. Checking the current context before a delete stops accidents on prod.

Marking (5): three options analysed and matched to the laptop, the lab and production 3 (1 each); kubeconfig and contexts 2.

5 marks · 9 minutes

After deploying a food-delivery app, kubectl get pods shows:

NAME                        READY   STATUS             RESTARTS      AGE
frontend-6b8d7c5f9-p7xqk    0/1     ImagePullBackOff   0             5m
orders-api-58c9d4b7f-r2mzt  0/1     CrashLoopBackOff   6 (55s ago)   10m
redis-7f9c8b6d5-k4wnv       0/1     Pending            0             10m
  1. [3]Analyze the most likely causes of each Pod's status.
  2. [1]Explain how you would confirm each cause and fix it.
  3. [1]Examine which Pod you would fix first, and why.
Model answer and marking
  • ImagePullBackOff (frontend): wrong image name or tag; a private registry without an imagePullSecret; or the registry is unreachable or rate-limiting. Confirm: kubectl describe pod frontend-..., Events say “not found” or “unauthorized”. Fix the image in the manifest and apply, or add a docker-registry Secret and imagePullSecrets.
  • CrashLoopBackOff (orders-api): the container starts and exits: an app error, a missing env var or Secret, can't reach a dependency, or killed for memory (OOMKilled). Confirm: kubectl logs orders-api-... --previous for the crashed run's output; kubectl describe pod for Last State, exit code and reason. Fix the config, connection string or memory limit.
  • Pending (redis): the scheduler can't place it: its CPU or memory requests don't fit on any node, a PVC isn't bound, or a taint or node selector rules out every node. Confirm: kubectl describe pod (FailedScheduling event), kubectl get pvc. Fix: lower the requests, add nodes, or fix the StorageClass.
  • Link: the API is probably crashing because Redis isn't running, so its connection fails on start-up. Fix Redis first, and the API may recover by itself.

Marking (5): causes for each Pod 3 (1 each); how to confirm and fix them 1 (naming describe, logs or events is enough); linking the API crash to the Pending Redis 1.

5 marks · 9 minutes

Analyze the two problems shown below.

$ kubectl describe pod invoices-6c9f8d7b5-m3qtz
Events:
  Warning  FailedScheduling  default-scheduler  0/3 nodes are available:
  1 node(s) had untolerated taint {node-role.kubernetes.io/control-plane: },
  2 Insufficient cpu.

$ kubectl logs cart-api-7d8c9b6f4-xw2lp --previous
Listening on port 3000
Error: connect ECONNREFUSED 127.0.0.1:6379
  1. [2]For the invoices Pod, identify the cause and state the fix.
  2. [2]For the cart-api Pod, identify the cause and state the fix.
  3. [1]Explain why the cluster behaves this way in each case.
Model answer and marking
  • invoices is Pending: the scheduler checked all three nodes. The control plane node has a NoSchedule taint, which keeps ordinary workloads off it so they can't starve the API server and etcd, and this Pod has no matching toleration. The two workers don't have enough unreserved CPU for the Pod's CPU request. The scheduler counts requests, not actual use. Fix: lower the request to what the app really needs (check usage with metrics), free capacity, or add worker nodes (the cluster autoscaler does this automatically). Don't remove the control plane taint.
  • cart-api crashes: it connects to Redis at 127.0.0.1:6379. Inside a Pod, 127.0.0.1 means that same Pod, and Redis runs in a different Pod, so nothing is listening there and the connection is refused. The app exits and the Pod goes into CrashLoopBackOff. It worked on a laptop because both ran on the same machine. Fix: point the app at Redis's Service name, redis or redis.<namespace>.svc.cluster.local, set through a ConfigMap; make sure that Service exists and has endpoints.

Marking (5): invoices Pod: cause 1, fix 1; cart-api Pod: cause 1, fix 1; why the cluster behaves this way (the scheduler counts requests; the restart loop) 1.

The manifest below is for an Express API that listens on port 3000.

apiVersion: apps/v1
kind: Deployment
metadata:
  name: orders
spec:
  replicas: 3
  selector:
    matchLabels:
      app: orders
  template:
    metadata:
      labels:
        app: orders
    spec:
      containers:
      - name: orders
        image: ghcr.io/food/orders:latest
        ports:
        - containerPort: 3000
---
apiVersion: v1
kind: Service
metadata:
  name: orders
spec:
  selector:
    app: order-api
  ports:
  - port: 80
    targetPort: 80
  1. [3]Detect any three errors or bad practices, and state the fix for each.
  2. [2]Analyze the effect of each on the running application.
Model answer and marking
  • Service selector doesn't match: it selects app: order-api, but the Pods are labelled app: orders. The Service has no endpoints, so every call to orders fails (connection refused or timeout) even though all Pods are Running. Fix: selector: { app: orders }.
  • Wrong targetPort: 80, but the app listens on 3000. Even with the right selector, traffic reaches a closed port: connection refused. Fix: targetPort: 3000.
  • Image tag latest: not reproducible. Nodes may run different builds, you can't tell which version is live, and a rollback goes back to “latest” again. Fix: pin a version, for example ghcr.io/food/orders:1.8.2, ideally the tag CI built.
  • Also accept: no readiness probe (traffic reaches Pods before they're ready); no resource requests or limits (poor scheduling, and one Pod can starve others on its node).

5 marks · 9 minutes

The frontend gets “connection refused” when calling the payments API, although both payments Pods are Running.

$ kubectl get svc payments
NAME       TYPE        CLUSTER-IP     EXTERNAL-IP   PORT(S)   AGE
payments   ClusterIP   10.96.88.140   <none>        80/TCP    15m

$ kubectl get endpoints payments
NAME       ENDPOINTS   AGE
payments   <none>      15m

$ kubectl get pods --show-labels
NAME                        READY   STATUS    AGE   LABELS
payments-5b7c8d9f6-4kqrz    1/1     Running   15m   app=payments,pod-template-hash=5b7c8d9f6
payments-5b7c8d9f6-v8nmt    1/1     Running   15m   app=payments,pod-template-hash=5b7c8d9f6

$ kubectl get svc payments -o jsonpath='{.spec.selector}'
{"app":"payments","tier":"backend"}
  1. [2]Analyze the output above and identify the cause.
  2. [1]State the fix.
  3. [2]Explain how the list of endpoints helps debug a Service.
Model answer and marking
  • Cause: a Service selects Pods that have all the labels in its selector. The selector asks for app=payments and tier=backend; the Pods have only app=payments. No Pod matches, so the Service has no endpoints and connections to its ClusterIP are refused.
  • Fix: either remove tier: backend from the Service's selector, or add tier: backend to the Pod template's labels in the Deployment (which rolls out new Pods). Then kubectl get endpoints payments lists two Pod IPs on the target port.
  • How endpoints help: they're the Service's current list of ready Pod IPs and ports. Empty endpoints point to one of two causes: the selector doesn't match any Pod's labels (compare with --show-labels), or the matching Pods aren't Ready (check the readiness probe). If endpoints are listed but calls still fail, look at the targetPort and whether the app really listens there.

Marking (5): correct diagnosis from the output 2; fix 1; how endpoints help debugging 2.

Compare with a model answer

Pending means the Pod exists but the scheduler hasn't found a node for it, so the container has never started and there are no logs to read. I run kubectl describe pod and read the Events at the bottom; the FailedScheduling message says, node by node, why each one was rejected, for example “0/3 nodes are available: 1 node(s) had untolerated taint, 2 Insufficient memory”. Common causes: the Pod requests more CPU or memory than any node has free, so I lower the request or add nodes (or the cluster autoscaler adds them); the only nodes with room have a taint the Pod doesn't tolerate, like the control plane node; or the Pod uses a PersistentVolumeClaim that isn't bound, for example a wrong StorageClass name, which shows in kubectl get pvc. If the Pod doesn't exist at all and the ReplicaSet's events say “exceeded quota”, it's the namespace's ResourceQuota instead.
