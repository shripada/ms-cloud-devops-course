Opening scenario

Checkout is slow, but every Pod is Running

An online shop runs its shop API on Kubernetes. Customers write in: “checkout is sometimes slow”. The team checks the cluster:

kubectl get pods
NAME                        READY   STATUS    RESTARTS
shop-api-7d9f8c6b5-4kx2p    1/1     Running   0
shop-api-7d9f8c6b5-9mq7w    1/1     Running   0
  • Slow for everyone, or 1 request in 20?
  • Since the last release, or always?

Running only means the container is up. It says nothing about how fast or how well it answers.

Ask: how would you find out if checkout is really slow? Take two or three answers. Most will say "look at logs" or "check CPU". Keep CPU in mind; we come back to it.
Opening scenario

What the team wants

  • One screen showing, for the shop API:
    • requests per second
    • percentage of requests that fail (5xx)
    • p95 latency: the time within which 95% of requests finish
  • A Slack message to the on-call engineer when users are affected

Hear about a problem from an alert before customers complain, and prove the fix worked.

That is what observability means here: the system reports how it is doing in numbers you can graph and alert on.

A typical observability setup

This lesson builds the top row without the Collector: Prometheus pulls /metrics from the apps itself.

OpenTelemetry (OTel): an open standard and free tools for producing and sending metrics, logs and traces. The SDK goes inside each app; OTLP is its data format; the Collector receives everything and forwards it to any backend, so you can change backends without changing app code. It stores and shows nothing itself. Common alternatives: Elasticsearch or OpenSearch instead of Loki; Jaeger instead of Tempo; PagerDuty or email next to Slack. Managed versions exist too: Grafana Cloud, Datadog, AWS CloudWatch. Source: https://opentelemetry.io/docs/what-is-opentelemetry/

One failed checkout, seen three ways

The metric says how often. The log says what happened. The trace says where the time went.

Same incident, three views. The metric is one number per moment for all requests together. The log line is written by the app for one event. The trace follows one request through every service it calls; each bar is a "span".

01

How the numbers are collected

Prometheus, /metrics, three kinds of metric

Prometheus: a database of numbers over time

Free, open-source monitoring tool. Started at SoundCloud in 2012; in the CNCF since 2016, the second project after Kubernetes.

  1. Collects numbers from your apps every few seconds
  2. Stores each number with a timestamp
  3. Answers queries in its language, PromQL
  4. Checks alert rules and sends firing alerts on

One time series: http_requests_total{status="500"}

10:00:00   40
10:00:15   41
10:00:30   43

Where do the numbers come from? The app shows them on a web page.

CNCF = Cloud Native Computing Foundation, the body that also looks after Kubernetes. Source: https://prometheus.io/docs/introduction/overview/

The app shows its numbers at /metrics

curl localhost:9898/metrics
# TYPE http_requests_total counter
http_requests_total{status="200"} 1
http_requests_total{status="500"} 1

Metric name
what is counted

Labels in { }
which kind: here, the status code

Value
the number right now

The app keeps these numbers in memory. A client library, such as prom-client for Node.js, does it for you.

Plain text over HTTP. That is the whole format. Source: https://prometheus.io/docs/introduction/overview/

Is /metrics required?

The path: a convention

Prometheus asks for /metrics unless told otherwise.

You can tell Prometheus a different path for any app.

Required: an HTTP endpoint

It must answer a web request with this plain text: name, labels, value.

Prometheus can't read anything else.

Linux and MySQL have no such endpoint, and you can't add one. What then?

Prometheus also accepts OpenMetrics, a standardised version of the same text format. Source: https://prometheus.io/docs/instrumenting/exposition_formats/ and https://prometheus.io/docs/instrumenting/exporters/

An exporter gives the endpoint

ExporterReads fromServes at
node-exporterLinux files /proc, /sys:9100/metrics
mysqld-exporterMySQL, with queries like SHOW GLOBAL STATUS:9104/metrics

On every scrape the exporter reads fresh numbers and answers in the text format. Prometheus only ever talks to the exporter.

Hundreds of exporters exist: PostgreSQL, Redis, nginx, and more. Source: https://prometheus.io/docs/instrumenting/exporters/ and https://github.com/prometheus/node_exporter

Prometheus pulls the numbers

A new Pod is found through the Kubernetes API and pulled too. Nobody edits a list of IPs.

Pull = scrape. Each stored number with its timestamp forms a time series. In the demo a ServiceMonitor tells Prometheus which Service's Pods to scrape, by label.

02

Showing and alerting

Grafana and Alertmanager

Grafana: dashboards for your data

An open-source tool that draws dashboards: screens of graphs and numbers, each built from a query.

Panel
one query, drawn as a graph, number or table

Data source
where it reads: Prometheus, Loki, Tempo, MySQL…

Stores no data
it asks the data source each time it draws

Made by Grafana Labs, first released in 2014. It can also send its own alerts; in this lesson Prometheus and Alertmanager do that. Source: https://grafana.com/docs/grafana/latest/fundamentals/

Alertmanager: from alert to message

An open-source tool that handles the alerts Prometheus sends, and turns them into messages for people.

Prometheus: “is something wrong?”

Checks each alert rule about every 30 s. When one fires, it sends it to Alertmanager.

It knows nothing about Slack or people.

Alertmanager: “who hears, and how?”

Route: urgent → on-call, rest → Slack

Group: ten related alerts → one message

Silence: quiet during maintenance

Remind: repeat, then say when fixed

Being a separate program, all the rules about notifying people sit in one place, shared by every Prometheus. Alertmanager also removes duplicates: teams often run two Prometheus copies for safety, both send the same alert, and only one message goes out. Source: https://prometheus.io/docs/alerting/latest/alertmanager/

Four tools, four jobs

Grafana stores no metrics: it asks Prometheus. Prometheus decides when an alert fires; Alertmanager decides who hears about it.

Source: https://prometheus.io/docs/alerting/latest/alertmanager/

04

Asking questions: PromQL

Rate, error percentage, p95

Demo · step 7

Requests per second

sum(rate(http_requests_total{job="shop-api"}[5m]))
  1. http_requests_total: a counter, keeps growing
  2. rate(...[5m]): how much it grew in the last 5 minutes, per second, for each Pod
  3. sum: add up all the Pods

If a Pod restarts, its counter goes back to 0. rate notices and handles it.

Paste into the Query page, press Execute, then click Graph. Read the query from the inside out.
Demo · step 8

Error percentage: the number users feel

sum(rate(http_requests_total{job="shop-api", status=~"5.."}[5m]))
  /
sum(rate(http_requests_total{job="shop-api"}[5m])) * 100

Top: rate of 5xx requests
=~"5.." means 5 followed by any two characters: 500, 502, 503…

Bottom: rate of all requests
Divide, then × 100

Result: about 9. It matches the prediction: 1 in 11.
Demo · step 9

Why the average hides slow requests

In every 11 requests: 10 take a few milliseconds, 1 takes 1 second.

Average

0.1 s

“Looks fine.” The one slow request is spread across the ten fast ones.

p95

1.7 s

95% of requests finish within this. The slow ones show up.

“Slow for some customers” needs a percentile, and a percentile needs a histogram.

About 9% of requests take 1 second, so the 95% point lands in the 1–2.5 s bucket; histogram_quantile estimates inside it, giving about 1.7 s. Average query: sum(rate(..._sum[5m])) / sum(rate(..._count[5m])).
Demo · step 9

p95 from the histogram

histogram_quantile(0.95,
  sum by (le) (rate(http_request_duration_seconds_bucket{job="shop-api"}[5m])))
  1. Each bucket is a counter: requests that took ≤ that time (le = less than or equal)
  2. rate: how fast each bucket grew
  3. sum by (le): add the Pods together, bucket by bucket
  4. histogram_quantile(0.95, …): find the bucket where the 95% point falls, and estimate inside it

Add up the counts from all Pods first, then work out p95 once.

Source: https://prometheus.io/docs/practices/histograms/

Why add counts, not percentiles?

Pod A

100 requests · p95 = 0.2 s

Pod B

100 requests · p95 = 2 s

p95 for both Pods together? Not (0.2 + 2) ÷ 2: two p95 values don't say how many requests were slow.

BucketPod APod BBoth, added
≤ 0.5 s9880178
≤ 2.5 s100100200

95% of 200 is the 190th request. Only 178 finish within 0.5 s, so p95 lies between 0.5 s and 2.5 s.

Counts can be added because they are just numbers of requests. histogram_quantile then estimates inside the 0.5–2.5 s bucket. This is why sum by (le) comes before histogram_quantile in the query.

06

Alert, route, silence

Demo · step 14 · alerts.yaml

An alert rule has three parts


- alert: ShopApiHighErrorRate
  expr: |
    sum(rate(http_requests_total{job="shop-api", status=~"5.."}[5m]))
      /
    sum(rate(http_requests_total{job="shop-api"}[5m])) > 0.05
  for: 2m
  labels:
    severity: page
  annotations:
    summary: "shop-api: {{ $value | humanizePercentage }} of requests are failing"

Inside a PrometheusRule

Another kind from the Helm chart. Prometheus reads it. Full file on the lesson page.

Name

Shown in Prometheus, Alertmanager and Slack.

1. What is measured

Share of requests failing over 5 minutes: the error % query without × 100.

2. Threshold

More than 0.05, that is 5%.

3. Duration

Must stay above 5% for 2 minutes. One bad moment doesn't wake anyone.

Labels and summary

severity: page marks it urgent, so Alertmanager sends it straight to the on-call engineer. The summary tells the engineer what is wrong.

Demo · step 16

From Alertmanager to Slack and email


route:
  receiver: oncall
  group_by:
    - alertname
    - namespace
  group_wait: 30s
  repeat_interval: 4h
receivers:
  - name: oncall
    slack_configs:
      - api_url_file: /etc/alertmanager/secrets/slack/webhook-url
        channel: "#shop-oncall"
        send_resolved: true
    email_configs:
      - to: oncall@shop.example.com

The lab stops at localhost:9093, with no Slack. A real team adds this.

route: every alert goes to the receiver oncall.

Grouping: same alert, same namespace → one message, not ten.

Timing: wait 30 s to collect related alerts; remind every 4 h while firing.

receivers: Slack and email. send_resolved posts again when fixed.

The webhook URL is a password: keep it in a Kubernetes Secret, never in Git.

api_url_file points at the Secret mounted into the Alertmanager Pod. Email also needs the company's mail server, set once at the top of the file.

Grouping: one message, not ten

One problem, one page. Ten messages at 3 a.m. get muted.

Demo · step 17

Planned maintenance: silence it

Tonight you restart the database. Errors are expected; nobody should get an alert.

# or in the Alertmanager page: New Silence
amtool silence add alertname=ShopApiHighErrorRate \
    --duration=1h --comment="planned DB maintenance"

Prometheus
Still firing. The rule keeps running.

Alertmanager
Marks it suppressed, sends nothing.

After 1 hour the silence ends by itself, so a forgotten silence can't hide problems forever.

Full command runs amtool inside the Alertmanager Pod: kubectl exec -n monitoring alertmanager-monitoring-kube-prometheus-alertmanager-0 -c alertmanager -- amtool --alertmanager.url=http://localhost:9093 silence add ... (lesson step 17).

What to alert on

Symptoms, SLOs, error budgets

Why not alert on CPU above 80%?

CPU 90%, all fast

Every request served quickly.

CPU alert wakes the on-call engineer for nothing.

CPU 5%, all failing

Database down: the API returns 500s instantly.

Users suffer. CPU alert stays quiet.

Alert on what users feel: errors and latency. Use CPU and memory on the dashboard to find the cause.

How many errors are too many?

SLO (service level objective): “99.5% of checkout requests succeed, over 30 days.”

Checkout requests per month10 lakh
Allowed to fail: the error budget (0.5%)5,000
A bad release fails 1% of requestsBudget gone in about 15 days

Budget nearly used up
Slow down releases, fix reliability

Plenty left
Ship faster

Zero errors isn't realistic, and chasing it stops you from ever releasing. A simple classroom alert: success ratio over 1h below 0.995, with for: 5m. The dashboard shows the 30-day success rate and the budget left.

Check yourself

Answer first, then click

Check 1

The Deployment scales from 2 Pods to 6. What must you change in Prometheus?

Nothing. Prometheus watches the Kubernetes API; the ServiceMonitor selects the Service by label, so new Pods are scraped and deleted Pods dropped.
Check 2

Which kind of metric fits “memory the container is using right now”?

A gauge: it goes up and down. A counter only goes up; a histogram counts values into buckets.
Check 3

Users say “some checkouts are slow”, but the average response time looks fine. What do you need?

A histogram of request durations, to calculate p95 or p99. The average spreads a few slow requests across many fast ones.
Check 4

One hour of planned maintenance. You don't want Slack messages for ShopApiHighErrorRate. What do you do?

Create a 1-hour silence in Alertmanager matching that alert. Prometheus keeps checking the rule; Alertmanager sends nothing until the silence ends.
Exit question · 5 minutes

Customers report checkout is slow for some requests. Choose tools to measure it, show it on one screen and alert the on-call engineer in Slack. Explain how the API's Pods are found, how the 5xx percentage over 5 minutes is calculated, and why you alert on that instead of CPU.
