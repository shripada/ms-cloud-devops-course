Opening scenario

Builds stuck in a queue

A food-delivery startup's CI builds wait 30 minutes in a queue before the Diwali sale. The DevOps team uses Terraform to add 8 build and 2 staging servers on AWS. Each needs a deploy user, an /opt/app folder and a settings file.

An engineer sets up each one by hand over SSH.

  • Server 7 got MAX_JOBS=40 instead of 4: a typo
  • Running the setup script again fails: “user already exists”
  • Next month, 5 more servers: do it all again
Ask: Terraform made these servers. Why can't Terraform also set them up? Take two or three answers, then go to the next slide.

Who sets up the inside of a server?

Terraform talks to the cloud's API. It has no way to check or fix a user inside the server on later runs.

Terraform can run a script once when a server is created (a provisioner). HashiCorp calls provisioners a last resort: they don't run again and can't detect a later hand change. Source: https://developer.hashicorp.com/terraform/language/resources/provisioners/syntax

Terraform and Ansible do different jobs

TerraformAnsible
Main jobCreate and delete infrastructure: networks, clusters, serversSet up what is inside existing servers: users, files, packages
Talks toCloud APIsEach server, usually over SSH
How it knows what existsA state fileNo state file: checks each server on every run
OrderRuns first: creates the serverRuns next: sets it up
In container-based teamsCreates the clusterMainly sets up the servers Kubernetes runs on; can also apply Kubernetes objects

Writing the setup of servers as code is called configuration management.

How Ansible works

The pieces and one run

Ansible's vocabulary

WordMeaningFor the startup

Source: https://docs.ansible.com/ansible/latest/getting_started/basic_concepts.html. The docs call the control machine the "control node" and managed hosts "managed nodes".

The pieces together

The managed hosts need only SSH and Python. Nothing from Ansible is installed on them.

What happens in one run

  1. Read the inventory: which hosts
  2. Read the playbook: which tasks, in order
  3. Gather facts: read details about each host, such as its OS and IP address
  4. For each task, on every host: connect over SSH, copy the module, run it
  5. The module checks first: already right → ok, otherwise fix it → changed
  6. Delete the module, go to the next task
  7. Print a recap: how many ok and changed per host
Tasks run in order. Each task runs on all hosts (five at a time by default) before the next task starts.

Agentless

Ansible: push

You run it from one machine when you choose. It connects to the hosts.

Hosts need SSH and Python only

Chef, Puppet: pull

An agent program runs on every host and asks a central server for its setup.

The agent must be installed and kept running everywhere

No agent: a new server is ready for Ansible as soon as you can SSH into it.

The files

Inventory, playbook, variables, secrets

Inventory: the hosts, in groups


[runners]
runner1.example.com
runner2.example.com

[staging]
stage1.example.com

inventory.ini

Host names or IP addresses, one per line.

Group runners

The build servers.

Group staging

A playbook can target one group, or all.

A new build server is one more line under [runners].

Source: https://docs.ansible.com/ansible/latest/inventory_guide/intro_inventory.html

A playbook, piece by piece


- name: Prepare build servers
  hosts: runners
  become: true
  tasks:
    - name: Create the deploy user
      ansible.builtin.user:
        name: deploy
        shell: /bin/bash

    - name: Create the app folder
      ansible.builtin.file:
        path: /opt/app
        state: directory
        owner: deploy

setup.yml

A YAML file. Read it top to bottom.

Play

A name, which hosts (the runners group from the inventory), and become: true: run the tasks as root, through sudo.

tasks

The list of things to do, in order.

A task

A name you will see in the output, and one module.

Module and values

Module user. Values: the user is called deploy, with the bash shell.

ansible.builtin = comes with Ansible. Other prefixes are add-on collections.

Second task

Module file: /opt/app is a folder owned by deploy.

ansible.builtin.user is the module's full name: it ships with Ansible. Source: https://docs.ansible.com/ansible/latest/playbook_guide/playbooks_intro.html

A task says what should be true

Shell script: steps

useradd -s /bin/bash deploy
mkdir /opt/app

Second run:
“user already exists”, “File exists”

Ansible task: the result you want

make sure user deploy exists
make sure /opt/app is a folder

Second run:
checks, finds it already true, does nothing

Idempotent: run it once or ten times, the server ends up the same.

Reading the output: ok or changed

First run, new server

TASK [Create the deploy user]
changed: [runner1]
TASK [Create the app folder]
changed: [runner1]

Second run, nothing touched

TASK [Create the deploy user]
ok: [runner1]
TASK [Create the app folder]
ok: [runner1]

If the playbook and its values didn't change, a changed means someone edited that server by hand.

Variables: one playbook, different values

group_vars/runners.yml


app_env: ci
max_jobs: 4

group_vars/staging.yml


app_env: staging
max_jobs: 1

In a task


content: |
  APP_ENV={{ app_env }}
  MAX_JOBS={{ max_jobs }}

Ansible loads the file with the group's name and fills in each {{ }} for each host.

The value is written once. All runners get the same value, and a mistake is fixed in one place.

Vault: a password that is safe in Git

A group's variables can also be a folder of files: group_vars/runners/. The secret goes in its own file there.

cat group_vars/runners/vault.yml
registry_password: "Gh0st@2026"
ansible-vault encrypt group_vars/runners/vault.yml
New Vault password: ****
cat group_vars/runners/vault.yml
$ANSIBLE_VAULT;1.1;AES256
6231386462316233643764323630363733376332...

Commit the file
AES-256 encrypted. Tasks use {{ registry_password }} as usual. Add no_log: true to such a task so the output doesn't print the password.

Never commit the vault password
Type it with --ask-vault-pass, or CI reads it from its secret store.

A group's variables can be one file (group_vars/runners.yml) or a folder of files (group_vars/runners/). The folder form lets the secret sit in its own encrypted file. Source: https://docs.ansible.com/ansible/latest/vault_guide/index.html

Before the demo

Three stand-in servers

# three containers play the part of three servers
for h in runner1 runner2 stage1; do
  docker run -d --name $h python:3.13-slim sleep infinity

Real servers cost money and need SSH keys. Containers are free, and Ansible reaches them with docker exec instead of SSH.

Demo · setup.yml

Three tasks


- name: Prepare servers
  hosts: all
  tasks:
    - name: Create the deploy user
      ansible.builtin.user:
        name: deploy
        shell: /bin/bash

    - name: Create the app folder
      ansible.builtin.file:
        path: /opt/app
        state: directory
        owner: deploy
        mode: "0755"

    - name: Write the app settings
      ansible.builtin.copy:
        dest: /opt/app/settings.env
        owner: deploy
        content: |
          APP_ENV={{ app_env }}
          MAX_JOBS={{ max_jobs }}

Play

All hosts in the inventory.

user

When run: make sure user deploy exists. Create it only if missing.

file

Make sure the folder exists, owned by deploy, permissions 0755 (in quotes so YAML keeps it as text).

copy

Make sure the file has exactly this content. Values come from the host's group.

Demo · step 6

Change staging only

Set max_jobs: 2 in group_vars/staging.yml, then:

The runners are not touched, though the playbook says hosts: all. Try changes on staging first.

Can Ansible deploy to Kubernetes too?

Yes: the kubernetes.core.k8s module applies a manifest through the cluster's API, like kubectl apply. The lesson page has the full exercise.

For Kubernetes objects aloneChoose Ansible when
kubectl apply and Terraform's Kubernetes provider are also idempotentOne playbook already sets up your servers, and should deploy the app too
By default, Terraform stores values in its state file in plain text, passwords includedThe password should stay encrypted in Git with Vault

Ansible's main job is the inside of servers. For Kubernetes it is one option among several.

Kubernetes · inventory.ini

Each cluster is a host


[clusters]
staging-cluster  kube_context=staging  replicas=2
prod-cluster     kube_context=prod     replicas=5

[clusters:vars]
ansible_connection=local
ansible_python_interpreter={{ ansible_playbook_python }}

Values per cluster

Which kubeconfig context to use, and how many replicas.

local

Run on the control machine itself. No SSH.

The module calls the cluster's Kubernetes API with your kubeconfig, like kubectl. Nothing is installed on the cluster.

Context names come from kubectl config get-contexts; for EKS, aws eks update-kubeconfig adds one. The k8s module needs the kubernetes Python library on the control machine (uv pip install kubernetes); the interpreter line makes Ansible use the venv's Python, where that library is. Source: https://docs.ansible.com/ansible/latest/collections/kubernetes/core/k8s_module.html
Kubernetes · deploy.yml

One playbook, every cluster


- name: Deploy the API
  hosts: clusters
  tasks:
    - name: Apply the Deployment
      kubernetes.core.k8s:
        context: "{{ kube_context }}"
        template: deployment.yml.j2
        state: present

deployment.yml.j2, the Deployment with one value left open


spec:
  replicas: {{ replicas }}

Play

Runs once for each cluster in the inventory.

context

Which cluster to talk to.

template

Fills in {{ replicas }}: 2 for staging, 5 for prod.

state: present

Already matches → ok. Missing or different → create or update → changed. No “already exists” error.

Spot the problems

Another team's playbook for 15 build servers


- hosts: all
  tasks:
    - name: Install Docker
      ansible.builtin.shell: curl -fsSL https://get.docker.com | sh
    - name: Add runner config
      ansible.builtin.shell: echo "concurrent=4" >> /etc/runner/config.toml
    - name: Set registry password
      ansible.builtin.copy:
        dest: /etc/runner/registry.env
        content: "REGISTRY_PASSWORD=Gh0st@2026"

Find at least three problems and say how to fix each. shell runs any shell command.

Give 6 minutes, then take answers.

Problems and fixes

ProblemFix
shell runs every time and always says changed: a hand change can't be spottedA module that describes the result, such as apt with name: docker.io and state: present
echo >> adds another line on every runlineinfile: makes sure the line is there exactly once
Password in plain text in GitVault-encrypted variable: {{ registry_password }}
hosts: all, no groupsInventory groups and --limit to try a few servers first
apt is the package module for Ubuntu/Debian. docker.io is Ubuntu's own Docker package; docker-ce needs Docker's apt repository added first. Also accept copy with the whole file, or template, for the second problem, and no_log: true on the password task.

Check yourself

Answer first, then click

Check 1

Terraform created a server. Why don't we also use Terraform to create the deploy user on it?

Terraform manages things through cloud APIs. It can run a setup script once when the server starts, but it cannot check or fix the user inside the server on later runs. Ansible connects to the server and checks what is inside on every run.
Check 2

What must be on a Linux server before Ansible can manage it?

SSH access, Python, and a user that can use sudo for system changes. No agent, and no Ansible.
Check 3

A second run says changed=0 on every host. What does that tell you?

Everything the playbook manages still matches on every server, so nothing was done. Ansible doesn't look at anything else: a hand change to another file would go unnoticed.
Exit question

Your team sets up 20 build servers by hand over SSH. Explain how Ansible would do it: what files you write, how each server gets its own job limit, and why running it twice is safe.

An inventory lists the servers in groups. A playbook lists tasks; each task uses a module that states a result, such as “user deploy exists”. group_vars files give each group its own max_jobs. Ansible connects over SSH from one machine. Each module checks first and reports ok or changed, so a second run changes nothing.
