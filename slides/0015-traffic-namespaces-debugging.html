01

Gateway API

One entry point, many Services

One load balancer per Service?

Each Service a LoadBalancer

3 Services → 3 load balancers

3 addresses, 3 bills, 3 certificates

One Gateway

1 entry point → routes to many ClusterIP Services

by hostname and path

Only the gateway is exposed. The app Services stay internal.

Three objects

ObjectSays
GatewayClassWhich software runs the gate
GatewayWhat it listens for, e.g. HTTP on port 80
HTTPRouteHost + path → which Service

An apartment's main gate: the security company, the gate, and the visitor register.

GatewayClass = the security company named in the contract. Gateway = the gate. HTTPRoute = the register: "visitors for flat 4B, go to Tower A". The older Ingress API is frozen but not removed; Kubernetes recommends Gateway API for new work.

Who does the work?

The three objects are only a description. Something must read them and pass on each request.

Ours is Envoy Gateway, a controller: it reads the objects.

It starts Envoy Proxy Pods: they take each request and send it to the right Service.

At the main gate: Envoy Proxy is the guard who handles each visitor.

The objects are only configuration

No controller → nothing happens.

HTTP on port 80.

The GatewayClass eg in shop.yaml has controllerName: gateway.envoyproxy.io/gatewayclass-controller. At work a platform team owns the GatewayClass and shared Gateway; app teams own their Deployments, Services and HTTPRoutes.

The HTTPRoute: where and for whom


apiVersion: gateway.networking.k8s.io/v1
kind: HTTPRoute
metadata:
  name: shop
spec:
  parentRefs:
    - name: shop
  hostnames:
    - shop.local

An HTTPRoute

Also named shop.

Attach to

The Gateway shop.

Only for

Requests with Host: shop.local.

Every request carries the site name it asked for, in a Host header. That's how one address serves many sites.

The HTTPRoute: rules


rules:
  - matches:
      - path:
          type: PathPrefix
          value: /api
    backendRefs:
      - name: api
        port: 80
  - matches:
      - path:
          type: PathPrefix
          value: /
    backendRefs:
      - name: web
        port: 80

Match

Path is /api or under it…

/api/orders ✓   /apiary ✗

…send to

the api Service, port 80.

Everything else

goes to web.

The most specific match wins, so /api beats /. Order in the file doesn't matter.

web and api are ordinary Deployments of traefik/whoami:v1.11 with ClusterIP Services, all in shop.yaml.

Sharing a cluster

Namespaces, labels and quotas

Three tools

ToolIs
NamespaceA folder for objects. Names unique inside it
LabelA tag like app=front. Filter with -l
ResourceQuotaA cap on one namespace's total CPU, memory, Pods

Each tower gets its own name boards, and at most 3 parking spots.

Same apartment building: each tower is a namespace; the parking limit is a ResourceQuota.
Try it

A quota for the testing team


apiVersion: v1
kind: ResourceQuota
metadata:
  name: team-quota
  namespace: testing
spec:
  hard:
    pods: "3"
    requests.cpu: "1"
    requests.memory: 1Gi

For one namespace

testing, created in the same file.

The caps

3 Pods, 1 CPU and 1 GiB of requests, in total.

testing.yaml starts with a Namespace object named testing, then ---, then this quota.
Predict

The testing team adds a Deployment with 5 replicas and no resource requests. How many Pods start?

Zero. Once a namespace has a CPU or memory quota, every Pod must say what it requests.
kubectl get events -n testing
failed quota: team-quota: must specify requests.cpu…

Add requests: 3 of 5

Each Pod now requests cpu: 100m, memory: 64Mi. The quota counts them.

The API server refuses Pods 4 and 5. They're never created, so they aren't Pending. Nothing in the default namespace is touched.

kubectl describe quota -n testing shows pods 3/3. The Deployment still wants 5; the ReplicaSet keeps trying; the API server keeps refusing.

Reaching a Service in another namespace

Namespaces keep names apart, not traffic. Any Pod can still call front.testing.

kubectl get pods -A -l app=front looks in all namespaces. Test: kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- wget -qO- http://front.testing.svc.cluster.local Clean up: kubectl delete -f testing.yaml removes the namespace and everything in it.

kubeconfig and contexts

You have a laptop cluster and a work cluster. How does kubectl know which one to talk to?

Check the current context before any delete.

kubectl config get-contexts, kubectl config current-context, kubectl config use-context <name>, kubectl --context <name> get pods.

03

Debugging

Read the status, run one command

It never starts

You seeIt meansCheck with
PendingNo node can take it yetdescribe pod
ImagePullBackOffNode can't download the imagedescribe pod
CreateContainer­ConfigErrorMissing ConfigMap, Secret or keydescribe pod

Not started yet = no logs. Read the Events at the bottom of describe.

Pending causes: requests bigger than any node's free CPU/memory; taints; a PVC that can't be bound. ImagePullBackOff causes: typo in name or tag; private registry without imagePullSecrets.

It starts, but it's broken

You seeIt meansCheck with
CrashLoopBackOffKeeps crashinglogs --previous
OOMKilledOut of memorydescribe pod
Running, no repliesService can't find the Podget pods --show-labels
CrashLoopBackOff causes: app error, missing env var, can't reach the database, liveness probe too strict. OOMKilled: used more memory than its limit; shows in describe under Last State. No replies: compare the Service selector with the Pod labels. Also check targetPort and readiness. kubectl get endpointslices -l kubernetes.io/service-name=<svc> shows whether the Service found any Pods.
Try it

Read a Pending message

A Deployment that requests 64Gi of memory:

0/3 nodes are available:
1 node(s) had untolerated taint
  {node-role.kubernetes.io/control-plane: },
2 Insufficient memory.
  • 1 → the control plane node keeps normal Pods off
  • 2 → neither worker has 64 GiB free
kubectl create deployment big --image=traefik/whoami:v1.11; kubectl set resources deployment big --requests=memory=64Gi; kubectl describe pod -l app=big. Fix: ask for a sensible amount, or add bigger nodes. kubectl delete deployment big. minikube doesn't taint its control-plane node, so there the message is "3 Insufficient memory".

The 127.0.0.1 trap

The API is in CrashLoopBackOff. Its log: connect ECONNREFUSED 127.0.0.1:5432

It worked on the laptop because both ran on one machine. In the cluster, use the Service name.

Set the database host through a ConfigMap: db, or db.shop.svc.cluster.local.

Check yourself

Answer first, then click

Check 1

You apply a Gateway and an HTTPRoute in a fresh cluster. The Gateway never becomes Programmed. Most likely cause?

No Gateway controller is installed, or none matches the GatewayClass. The objects are only configuration. Second most likely: no load balancer, so the Gateway gets no address.
Check 2

A namespace's quota allows 20 Pods and 20 are running. Someone scales a Deployment up by 2. What happens?

The API server refuses the new Pods. They are never created; events show “exceeded quota”.
Check 3

Both API Pods are Running and Ready, but the Service has no endpoints. What do you check first?

The Service's selector against the Pods' labels: kubectl get pods --show-labels.
Check 4

A Pod is in CrashLoopBackOff. Which command most often shows why?

kubectl logs <pod> --previous: the logs of the run that just crashed.
Check 5
frontend-…     0/1   ImagePullBackOff
orders-api-…   0/1   CrashLoopBackOff
redis-…        0/1   Pending

Which Pod do you fix first, and why?

redis, if the API's logs --previous says it can't reach Redis: the API crash is a symptom and may clear by itself. Read redis's Events with describe pod. The frontend image error is unrelated; fix it separately.
