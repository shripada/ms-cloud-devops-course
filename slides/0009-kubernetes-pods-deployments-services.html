Module 2 · Lessons 9–11

Pods, Deployments
& Services

How Kubernetes keeps your app running, gives it one address, and reads it from a YAML file

Press S for this speaker view, T to switch light/dark, Esc for the slide overview. Today: the cluster, Pods, Deployments (lesson 9), Services (lesson 10), manifests and kubectl apply (lesson 11).

Why Docker Compose is not enough

IRCTC, Tatkal booking, 10 a.m.:

  • 50 copies of the booking service, spread across many servers
  • A server dies → its copies must start again somewhere else, in seconds
  • New code ships → old copies are replaced one by one, nobody sees an error page

Compose only does “start these containers on this machine”. Nothing watches them afterwards.

Kubernetes is a container orchestrator: you say what you want running, it keeps it running.

Connect to module 1: Compose ran app + database on one laptop. Ask: what happens if that laptop dies? Nobody restarts anything. K8s = K, 8 letters, s. EKS, AKS, GKE are Kubernetes sold as a service. It appears in almost every Cloud/DevOps job description.
01

The cluster

A group of machines managed together

Inside a cluster

The kubelet on each node starts containers when the control plane tells it to.

Click 1: the other three control plane parts. etcd = records, scheduler = which node, controller manager = the loops (the AC thermostat from lesson 9). Click 2: worker nodes. kubelet is the agent that starts containers. kube-proxy runs once on every node; we meet it again with Services. Click 3: you and kubectl. Every command goes to the API server. The control plane parts themselves run as Pods in kube-system.

Say hello to the cluster

desktop-worker          Ready    <none>
desktop-worker2         Ready    <none>
kubectl get pods -n kube-system -o wide

kube-scheduler-desktop-control-plane              desktop-control-plane

The control plane parts run as Pods too, on the control plane node.

Output trimmed. On minikube the nodes are minikube, minikube-m02, minikube-m03. -n picks a namespace, like a folder for cluster objects. kube-proxy appears once per node.
02

The Pod

The smallest thing Kubernetes runs

A Pod wraps a container

Pods are disposable: a dead Pod is never repaired, a new one replaces it.

Kubernetes never runs a bare container; it always runs a Pod. Usually one container, sometimes a few that must stay together. All containers in a Pod share one IP. Click 1: the Pod dies. Click 2: the replacement has a NEW name and a NEW IP. Remember the new IP; it is why we need Services later.
Try it

A bare Pod has nobody watching it

kubectl run solo --image=nginx
pod/solo created
kubectl delete pod solo
pod "solo" deleted
kubectl get pods
No resources found in default namespace.

Gone for good. Nobody had asked Kubernetes to keep it running.

To keep Pods running, you need something that watches them: a Deployment.

This is the "wrong way" from lesson 9. Ask the room first: will it come back? Then show it doesn't.
03

The Deployment

Write down what you want; a controller keeps it true

Desired state and the control loop

A Deployment holds the desired state; a controller keeps actual = desired.

The controller manager runs this loop. You never say "create a Pod now"; you say "there should be 3" and the loop does the rest. Same idea comes back in lesson 11: the YAML file is the desired state.

Deployment → ReplicaSet → Pods

Each layer owns the one below: delete the Deployment and the rest goes too.

Look at the names: ReplicaSet = web-<hash>, Pod = web-<hash>-<random>. Last click: the label app=web. The ReplicaSet finds "its" Pods by label. Labels come back with Services.
Try it

See the chain of three objects

kubectl create deployment web --image=nginx --replicas=3
kubectl get deployment,replicaset,pods
NAME                            READY   UP-TO-DATE   AVAILABLE
deployment.apps/web             3/3     3            3

NAME                            DESIRED   CURRENT   READY
replicaset.apps/web-6b7f9c4d8   3         3         3

NAME                            READY   STATUS
pod/web-6b7f9c4d8-x2k4q         1/1     Running
pod/web-6b7f9c4d8-7hq9d         1/1     Running
pod/web-6b7f9c4d8-m3vtw         1/1     Running

Add -o wide to see each Pod's IP and the node the scheduler picked.

In lesson 9 students created it with 1 replica and scaled to 3 with kubectl scale; same result. Debug habits from module 1 still work: kubectl logs, kubectl exec, kubectl describe (look at Events at the bottom).

Self-healing: delete a Pod

Desired 3, actual 2 → the ReplicaSet creates 1. The other Pods keep serving.

Run kubectl get pods --watch in a second terminal while you delete. Old Pod: Terminating. New Pod: ContainerCreating, then Running, with a different name. kubectl delete pods -l app=web deletes all three at once; three new ones appear within seconds.

Where do the Pods land?

The scheduler spreads copies, so losing one machine doesn't take down all of them.

Command: kubectl describe node desktop-control-plane | grep -i taints. A taint is like a "staff only" sign; a toleration is the staff ID card. minikube does not taint its control plane node.
04

The Service

One stable address in front of changing Pods

The problem: Pod IPs keep changing

Your backend runs as 3 Pods. Any of them can be replaced at any moment, with a new IP.

Which IP should the frontend call?

Your college office landline: the staff at the desk change every shift, but students always dial the same number, and whoever is on duty picks up.

Landline number = Service · staff on duty = Pods · duty roster = EndpointSlice

A Service is a fixed name and IP in front of whichever Pods are running now.

Link to lesson 5: Compose let containers call backend:3000 by name. Same idea, built for Pods that keep moving.

How a Service finds its Pods

The Service picks Pods by label, never by name. The app=web Pod gets no traffic.

Click 1: the Service and its selector. Click 2: the EndpointSlice, the live list of matching Pod IPs, updated within seconds when a Pod is replaced. Click 3: a client calls http://who. DNS (CoreDNS) turns "who" into the ClusterIP. Full name: who.default.svc.cluster.local.

kube-proxy: the ClusterIP isn't a machine

  • No process listens on 10.96.143.20
  • kube-proxy, on every node, writes network rules into the node's Linux kernel
  • Those rules catch packets sent to the ClusterIP and redirect each one to a Pod from the EndpointSlice
  • That is how one Service shares requests between several Pods
wget -qO- http://who | grep Hostname      # works: TCP port 80 is forwarded
Hostname: who-7d9f8c6b5-2xkqp
ping -c 2 who                           # no reply: ping is not forwarded

Ping failing doesn't mean the Service is broken. Test with the real port.

Run wget a few times: the Hostname changes between Pods. That's kube-proxy sharing requests. The client here is a throwaway Pod: kubectl run tmp --rm -it --image=busybox:1.36 -- sh
Try it

Replace every Pod. What changes?

kubectl get service who
NAME   TYPE        CLUSTER-IP     PORT(S)
who    ClusterIP   10.96.143.20   80/TCP
kubectl get endpointslices -l kubernetes.io/service-name=who
NAME        PORTS   ENDPOINTS
who-x7k2p   80      10.244.1.5,10.244.2.7,10.244.2.8
kubectl delete pods -l app=who
kubectl get service who
who    ClusterIP   10.96.143.20   80/TCP      # same
kubectl get endpointslices -l kubernetes.io/service-name=who
who-x7k2p   80      10.244.1.11,10.244.2.12,10.244.2.13

New Pod IPs, same Service IP. A client calling http://who never notices.

The Service was made with: kubectl expose deployment who --port=80. expose copies the Deployment's selector app=who. ClusterIPs (10.96.x.x) come from a different range than Pod IPs (10.244.x.x).
Debug it

A Service with no Pods behind it

kubectl scale deployment/who --replicas=0
kubectl get endpointslices -l kubernetes.io/service-name=who
NAME        PORTS     ENDPOINTS
who-x7k2p   <unset>   <unset>
kubectl run tmp --rm -it --image=busybox:1.36 -- wget -qO- -T 3 http://who
wget: can't connect to remote host (10.96.143.20): Connection refused

The Service exists and DNS works, but no running, ready Pod matches the selector.

Most common cause at work: a label typo. Compare with kubectl get pods --show-labels.

When a Service “doesn't work”, check its endpoints first.

Bring them back afterwards: kubectl scale deployment/who --replicas=3.

Three types of Service

TypeReachable fromUsed for
ClusterIP (default)Only inside the clusterPod-to-Pod: frontend → backend, backend → database
NodePortA port 30000–32767 on every node's IPRarely used directly; the building block for LoadBalancer
LoadBalancerOutside the cluster, through an external load balancerLetting users in. On AWS, a real AWS load balancer

Each type adds a way in on top of the one before: LoadBalancer → NodePort → Pods.

On the laptop, Docker Desktop plays the load balancer (minikube needs minikube tunnel). kubectl expose deployment who --name=who-lb --type=LoadBalancer --port=8099 --target-port=80

Three ports, three jobs

PORT(S)  8099:31233/TCP      # port:nodePort — targetPort 80 is in the YAML
port = where the Service listens. targetPort = where the container listens. nodePort = opened on every node (30000–32767; Kubernetes picks one unless you set it, for example nodePort: 30090). On Docker Desktop you can't open the nodePort yourself: the nodes live inside its VM.
05

Manifests

The desired state, written in a file and kept in Git

Imperative vs declarative

Imperative

Say what to do:

kubectl scale … --replicas=5
kubectl expose …

Ring the canteen each time: “add one thali”, “cancel one dosa”. Miss a call and nobody knows the real order.

Declarative

Say what should exist:

who.yaml: a Deployment who with 5 replicas

A shared sheet lists the order; the canteen makes whatever it says. The sheet is the manifest, the canteen is the control plane.

Git records what should run and who changed it; the cluster shows what is running.

The 2 a.m. incident: "how many replicas should the backend have, and who changed it last week?" If the answer is only in someone's shell history, nobody knows. Same control loop as lesson 9; now you write the desired state yourself. Terraform (module 3) and Argo CD build on this idea.

Four top-level fields

FieldMeaningExample
apiVersionWhich API group and versionapps/v1, v1
kindThe type of objectDeployment, Service
metadataIts name and labelsname: who
specThe desired state: what you wantreplicas: 3

Read an object back and you also see status: what Kubernetes observes right now.

You write spec. Controllers move the cluster towards it and report in status.

You don't have to write YAML from memory: kubectl create deployment who --image=traefik/whoami --replicas=3 --dry-run=client -o yaml. kubectl explain deployment.spec.replicas reads the cluster's own docs for any field.

Reading who.yaml: the Deployment


apiVersion: apps/v1
kind: Deployment
metadata:
  name: who
  labels:
    app: who
spec:
  replicas: 3
  selector:
    matchLabels:
      app: who
  template:
    metadata:
      labels:
        app: who
    spec:
      containers:
        - name: whoami
          image: traefik/whoami:v1.11
          ports:
            - containerPort: 80

Which API, which object

Deployments live in apps/v1.

The Deployment's own name tag

name: who names it. This label sits on the Deployment itself and selects nothing.

Desired state

Keep 3 Pods running. Inside spec, like everything below it.

Which Pods are mine?

The Deployment manages Pods carrying app: who.

The Pod blueprint

template is copied for every new Pod. Its labels are stamped on each Pod.

The container

containers is a list (- = one item). Fixed tag v1.11, not latest.

containerPort: 80 only documents the port; it doesn't open it.

Three app: who, three jobs

6: tags the Deployment
11: finds the Pods
15: stamps the Pods

11 and 15 must match, or Kubernetes rejects the file.

Read it from the outside in. Indentation shows what belongs to what; spaces only, never tabs. VS Code + the Red Hat YAML extension underlines mistakes.

Reading who.yaml: the Service


---
apiVersion: v1
kind: Service
metadata:
  name: who
spec:
  selector:
    app: who
  ports:
    - port: 80
      targetPort: 80

Two objects, one file

A line with just --- separates YAML documents. This Service goes after the Deployment.

The core API group

Services belong to the core group, written as just v1.

The name is the address

A Pod in the same namespace calls http://who.

Send traffic to…

…Pods labelled app: who: the labels from the Deployment's template.

Two ports

port: what clients call. targetPort: where the app really listens.

No type line → ClusterIP.

If the app listened on 3000, keep port: 80 and set targetPort: 3000. For outside access on this setup: add type: LoadBalancer under spec. A Service selector that matches no Pods is still valid YAML; it just has empty endpoints.

Who uses the label?

The Deployment and the Service each look for the template's label, on their own.

Trace it: template labels → Pods. Deployment selector must match them so it can manage its Pods. Service selector independently looks for the same labels to send traffic.
06

kubectl apply

Hand the file to Kubernetes; it works out the steps

Try it

Created, unchanged, configured

kubectl apply -f who.yaml
deployment.apps/who created
kubectl apply -f who.yaml              # same file again
deployment.apps/who unchanged
# edit who.yaml: replicas: 3 → replicas: 5
kubectl apply -f who.yaml
deployment.apps/who configured

Same file, same result: apply is idempotent, so CI can run it on every push.

Predict first before each run. Compare: kubectl create deployment who … a second time fails with "already exists". -f names the file. Editing the file changes nothing in the cluster until you apply.
Try it

Preview first with kubectl diff

kubectl diff -f who.yaml
   kind: Deployment
-  generation: 1
+  generation: 2
   …
-  replicas: 3
+  replicas: 5

Nothing has changed in the cluster yet. generation goes up by one each time the spec changes.

At work, kubectl diff is what you paste into a pull request for review.

Order: edit file → kubectl diff → kubectl apply. Reviewers see exactly what will change in production.

Drift: the 2 a.m. hand fix

who.yaml (Git)

replicas: 5

Cluster

kubectl scale … --replicas=1

replicas: 1 ← drift

kubectl diff -f who.yaml
-  replicas: 1
+  replicas: 5
kubectl apply -f who.yaml
deployment.apps/who configured        # back to 5

To keep 1 replica, change the file to replicas: 1 and apply it.

Drift = the cluster no longer matches the file. The hand-run kubectl scale changed only the live object. The next apply puts the file's value back.
Break it

Kubernetes checks your manifest

Template label changed to app: whoo:

kubectl apply -f bad.yaml
The Deployment "who" is invalid: … `selector` does not match template `labels`

Field name typo, replicass::

kubectl apply -f bad.yaml
Error from server (BadRequest): … unknown field "spec.replicass"

A rejected Deployment is not partly changed. Read the error for the field name.

Both errors are long; teach students to search them for the field path. Afterwards: rm bad.yaml.
Try it

Two objects in one file

# who.yaml now holds the Deployment, ---, and the Service
kubectl apply -f who.yaml
deployment.apps/who unchanged
service/who created
kubectl delete -f who.yaml
deployment.apps "who" deleted
service "who" deleted
  • Apply handles each object on its own
  • Not one transaction: an earlier valid object may already be changed if a later one fails
  • Removing an object from the file does not delete it from the cluster
kubectl delete -f deletes the objects named in the file. Deletion is always a separate step.

Commands to remember

# look
kubectl get nodes
kubectl get deployment,replicaset,pods
kubectl get pods --show-labels
kubectl describe deployment who
kubectl get endpointslices \
  -l kubernetes.io/service-name=who
# change
kubectl create deployment who \
  --image=traefik/whoami --replicas=3
kubectl expose deployment who --port=80
kubectl diff -f who.yaml
kubectl apply -f who.yaml
kubectl delete -f who.yaml

Imperative commands to explore; a file and kubectl apply for anything you keep.

?

Check yourself

Answer first, then click

Check 1

A Deployment runs 4 Pods. You delete 2 of them. What happens next, and which part of Kubernetes does it?

The ReplicaSet controller sees 2 running against 4 desired and creates 2 new Pods, with new names and usually new IPs. The scheduler places them and the kubelets start them. The other 2 Pods keep serving the whole time.
Check 2

The Service who exists and DNS works, but wget http://who fails and its endpoints show <unset>. What do you check first?

No running, ready Pod matches the Service's selector. Compare the selector (kubectl describe service who) with the Pod labels (kubectl get pods --show-labels): a label typo, or the Deployment scaled to 0.
Check 3

ping who gets no reply, but wget http://who works. Is the Service broken?

No. The ClusterIP is not a machine. kube-proxy's rules forward only the Service's port (80, over TCP). Ping uses a different protocol, so nothing answers it.
Check 4

Your app listens on port 3000. Other Pods should call it as http://api. What are port and targetPort in the Service?

port: 80, because http://api means port 80. targetPort: 3000, where the process really listens. containerPort in the Deployment only documents it.
Check 5

You run kubectl apply -f who.yaml twice without editing the file. What does the second run print, and why does that matter?

deployment.apps/who unchanged. Nothing in the file differs from the cluster. Apply is idempotent, so a CI pipeline can safely run it on every push.
Check 6

A teammate ran kubectl scale deployment/who --replicas=1. The file says 5. What does kubectl diff show, and what does the next apply do?

The diff shows replicas: 1 → replicas: 5; the next apply restores 5. If 1 is really wanted, change the file to replicas: 1 and apply it, so Git stays the record.
