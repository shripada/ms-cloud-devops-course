Data, jobs
& scaling

Keep data when Pods move, run work on a clock, and grow with the traffic

Press S for this speaker view, T to switch light/dark, Esc for the slide overview. Check first: kubectl get storageclass should show one marked (default).

Pods come and go

Kubernetes deletes and recreates Pods all the time, on any node.

  • A database that forgets every order → storage
  • A backup at 2 a.m. → CronJob
  • Placement results: 10× traffic → autoscaling

Fine for a stateless API. A disaster for a database.

01

Storage

Data that outlives the Pod

emptyDir vs PersistentVolumeClaim

emptyDir: a train berth. A PVC: your hostel room. Books still there after the holidays.

Sleeper berth: get off and whatever you left is gone. Hostel room: you go home (Pod deleted) and your books are there when you come back.

Who makes the disk?

ReadWriteOnce: only one node can mount it at a time.

Same YAML on a laptop and on AWS; the StorageClass decides what disk you get.
Try it · wrong way

PostgreSQL on emptyDir

# create table orders, insert (1, 'masala dosa')
kubectl delete pod -l app=db
kubectl exec deploy/db -- psql -U postgres -c "SELECT * FROM orders;"
ERROR:  relation "orders" does not exist

The new Pod got a brand new, empty emptyDir. Every order is gone.

db.yaml: postgres:17.6, password from db-secret.local.yaml (lesson 12 pattern), PGDATA set to a sub-folder, replicas 1, strategy Recreate. Ask first: will the order survive a Pod delete?
Try it · right way

A PersistentVolumeClaim


apiVersion: v1
kind: PersistentVolumeClaim
metadata:
  name: db-data
spec:
  accessModes:
    - ReadWriteOnce
  resources:
    requests:
      storage: 1Gi

One node at a time

What a normal cloud disk allows.

How big

1 GiB. The StorageClass makes it.

Goes at the top of db.yaml, followed by a --- line.

Use the claim in the Pod


containers:
  - name: postgres
    volumeMounts:
      - name: data
        mountPath: /var/lib/postgresql/data
volumes:
  - name: data
    persistentVolumeClaim:
      claimName: db-data

Where

Mount it where PostgreSQL keeps its files.

What

Was emptyDir. Now the claim db-data.

The names match

The mount finds its volume by name.

Try it

The order survives

kubectl get pvc
NAME      STATUS   CAPACITY   ACCESS MODES
db-data   Bound    1Gi        RWO
kubectl delete pod -l app=db
kubectl exec deploy/db -- psql -U postgres -c "SELECT * FROM orders;"
 id |    item
  1 | masala dosa

On a laptop the new Pod lands on the same node. On AWS the disk moves to the new node.

Run kubectl get pod -l app=db -o wide before and after the delete.

Why 1 replica and Recreate?

  • Two PostgreSQL servers on one data folder corrupt it
  • ReadWriteOnce: one node only
  • Rolling update: new Pod starts while the old one holds the disk
  • Recreate stops the old Pod first

More copies? A StatefulSet with replication, or a managed database like Amazon RDS.

Before you delete a PVC

kubectl get pv
NAME          CAPACITY   RECLAIM POLICY   STATUS
pvc-3f9a…     1Gi        Delete           Bound
DeleteDeleting the PVC deletes the disk and the data
RetainThe disk stays, for manual recovery
Clean up later: kubectl delete -f backup.yaml -f db.yaml -f db-secret.local.yaml.
02

Jobs

Work that finishes, and work on a clock

Forever, once, or on a schedule

ObjectRuns a Pod…
Deploymentforever
Jobuntil it finishes successfully
CronJobby creating a Job on a schedule

The schedule

Same format as Linux cron. * means “every”.

Try it

A backup CronJob


spec:
  schedule: "0 2 * * *"
  timeZone: "Asia/Kolkata"
  concurrencyPolicy: Forbid
  jobTemplate:
    spec:
      backoffLimit: 2
      template:
        spec:
          restartPolicy: OnFailure
          containers:
            - name: backup
              image: busybox:1.36

When

02:00 every day, India time. Without timeZone, it's the cluster's clock.

Overlap

Last run still going? Skip the new one.

Retries

2 retries, then the Job is Failed.

On failure

Retry in the same Pod. Never = a new Pod each time.

Three settings

concurrencyPolicy
backoffLimit
restartPolicy

Top of the file: apiVersion: batch/v1, kind: CronJob, metadata name: backup. For the demo the lesson uses schedule "* * * * *" and a command that sleeps 90 s, so runs would overlap. kubectl get jobs -w for three minutes: never two running together.

When the last run is still going

concurrencyPolicyThe new run…
Allow (default)starts anyway: two backups fight over the same files
Forbidis skipped
Replacekills the old run and starts
Break it

A backup that keeps failing

At work, you alert on BackoffLimitExceeded.

Change the command to echo disk full; exit 1 and restartPolicy to Never. kubectl describe job shows BackoffLimitExceeded.
03

Autoscaling

More Pods when the queue grows

The HorizontalPodAutoscaler

Like the canteen manager who opens a second counter when the queue gets long.

The HPA checks about every 15 s. It closes the counter after lunch too: scale-down.

Percent of what?

CPU request: 200m = a fifth of one CPU

Target 50% → aim for 100m per Pod

No request → nothing to divide by → the HPA can't measure.

m = millicores. 1000m = one CPU.

How many Pods?

wanted = current replicas × current CPU ÷ target

4 × 90 ÷ 60 = 6

Rounded up, kept between minReplicas and maxReplicas.

By default, scale-down waits 5 minutes of low CPU, so a short dip doesn't flap.

Try it

The HPA spec


spec:
  scaleTargetRef:
    apiVersion: apps/v1
    kind: Deployment
    name: php-apache
  minReplicas: 1
  maxReplicas: 6
  metrics:
    - type: Resource
      resource:
        name: cpu
        target:
          type: Utilization
          averageUtilization: 50

What to scale

The php-apache Deployment.

Limits

Between 1 and 6 Pods.

Target

Average CPU at 50% of the request.

The Deployment leaves out replicas: the HPA owns it.

Top of the object: apiVersion: autoscaling/v2, kind: HorizontalPodAutoscaler, name: php-apache. hpa.yaml also has the Deployment (requests cpu 200m, limits 500m) and a Service. Image registry.k8s.io/hpa-example from the Kubernetes docs. Needs metrics-server: kubectl top nodes should print numbers.
Try it

Create a rush

# second terminal: a load generator calling http://php-apache
kubectl get hpa php-apache -w
NAME         TARGETS          MINPODS   MAXPODS   REPLICAS
php-apache   cpu: 0%/50%      1         6         1
php-apache   cpu: 250%/50%    1         6         1
php-apache   cpu: 120%/50%    1         6         4
php-apache   cpu: 52%/50%     1         6         5

Stop the load: replicas come down only after about 5 minutes.

Load: kubectl run load --rm -it --image=busybox:1.36 --restart=Never -- sh -c "while sleep 0.01; do wget -qO- http://php-apache; done" Ask first: how many replicas will you get? Numbers vary.
Break it

Remove the CPU request

kubectl get hpa php-apache
TARGETS
cpu: <unknown>/50%
kubectl describe hpa php-apache
… missing request for cpu

No request, no 100% to measure against. The HPA does nothing.

Delete the resources: block (three lines) and apply. Clean up: kubectl delete -f hpa.yaml.

What limits how fast you scale?

  • Checks every 15 s; metrics are a little behind
  • Each new Pod: schedule, pull image, start, pass readiness
  • Full nodes → Pending until a cluster autoscaler adds nodes (minutes)

For a known sale or results day, raise minReplicas before it starts.

Check yourself

Answer first, then click

Check 1

A Pod with an emptyDir volume is deleted. The Deployment makes a new one. What's in the new Pod's volume?

Nothing. It's a fresh, empty folder. An emptyDir lives and dies with its Pod.
Check 2

A daily backup sometimes runs over 24 hours. Never two at once, and never kill one half-way. Which setting?

concurrencyPolicy: Forbid: the new run is skipped while the old one is still going.
Check 3

An HPA shows cpu: <unknown>/70% and never scales. metrics-server works. Most likely cause?

The Pods have no CPU request, so there's nothing to measure the percentage against.
Check 4

An HPA targets 60% CPU. 4 replicas average 90%. About how many replicas will it ask for?

4 × 90 ÷ 60 = 6.
Check 5

Why run PostgreSQL with a PVC, 1 replica and Recreate, not emptyDir and 3 replicas?

emptyDir dies with the Pod; the PVC's disk lives on. Two servers on one data folder corrupt it, and ReadWriteOnce mounts on one node. Recreate stops the old Pod before the new one takes the disk.
