Opening scenario · 10 minutes

How was production built?

A college created its AWS network, EKS cluster, worker nodes, registry and Cloudflare DNS by clicking in two consoles.

  • Test no longer matches production
  • Nobody knows who changed what
  • A second environment means repeating every click

Choose a tool that keeps the setup in Git, previews changes and can remove a copy cleanly.

Infrastructure needs the source-code workflow

Console clicks

The result exists, but the recipe does not.

No useful diff, review or reliable rebuild

Infrastructure as code

The desired setup lives in files beside the application.

Git records the change. CI previews and applies it.

Terraform makes infrastructure changes reviewable and repeatable.

01

Three ideas

Declarative code, providers and state

Declarative code


resource "docker_image" "web" {
  name         = "nginx:1.27-alpine"
  keep_locally = true
}

resource "docker_container" "web" {
  name  = "web-dev"
  image = docker_image.web.image_id
  ports {
    internal = 80
    external = 8081
  }
}

Desired result

Describe what should exist, not a sequence of API calls.

An image

Terraform keeps nginx:1.27-alpine available.

A container

It uses that image and publishes port 8081.

This feels like a Kubernetes manifest. The configuration states the result; Terraform decides the API operations.

Providers connect Terraform to APIs

One configuration can manage resources from several services.

Source: https://developer.hashicorp.com/terraform/language/providers

02

The workflow

Initialize, preview, apply and remove

Four commands

CommandWhat it does
terraform initDownloads providers and prepares the working directory
terraform planShows the proposed difference without changing infrastructure
terraform applyMakes the real resources match the configuration
terraform destroyProposes and removes everything recorded in this state

The plan is the change reviewers inspect before apply.

Source: https://developer.hashicorp.com/terraform/intro/core-workflow

Reading a plan

+ create
~ update in place
- destroy
-/+ replace

-/+ deserves special attention.

A replacement deletes the old resource and creates another one.

For a container, that may be fine. For a database, it may destroy data.

A plan exposes risky changes before any API call changes the resource.

Provider and variables


terraform {

    docker = {
      source  = "kreuzwerker/docker"

    }
  }

  type    = string
  default = "dev"

  type    = number
  default = 8081
}

Environment

Port

Applying again changes nothing

What happens when the code and real container already match?

terraform apply
No changes. Your infrastructure matches the configuration.
Idempotent: running the same configuration once or ten times produces the same result.
A shell script containing docker run would fail on the second run because the container name already exists.

A port change forces replacement

Change the default port from 8081 to 8082, then plan.

terraform plan
-/+ resource "docker_container" "web"
    external = 8081 -> 8082 # forces replacement

Plan: 1 to add, 0 to change, 1 to destroy.

Docker cannot change a running container's published port, so Terraform proposes a new container.

03

State and drift

How Terraform knows what it manages

State maps code to real objects

Plan uses this mapping to read the real object and compare it with the code.

Source: https://developer.hashicorp.com/terraform/language/state
Drift demo · change

A manual fix creates drift

# someone changes the container outside Terraform
docker update --restart=always web-dev
terraform plan
~ resource "docker_container" "web"
    restart = "always" -> "no"
Plan: 0 to add, 1 to change, 0 to destroy.

Drift means the real resource no longer matches the configuration.

Drift demo · delete

A missing object can be recreated

docker rm -f web-dev
terraform plan
+ resource "docker_container" "web"
Plan: 1 to add, 0 to change, 0 to destroy.
terraform apply

Terraform sees that the recorded container is gone and proposes another one.

The AWS equivalent: someone disables S3 versioning in the console. A later plan proposes restoring the configured value.

Local state does not work for a team

On one laptop

Other engineers cannot read the latest mapping.

Two copies become inconsistent.

Remote backend

Store one encrypted state in S3 with restricted access.

CI and authorized engineers share it.

Never commit terraform.tfstate. It can contain secrets in plain text.

S3 backend with locking


terraform {
  backend "s3" {
    bucket       = "shop-terraform-state"
    key          = "prod/terraform.tfstate"
    region       = "ap-south-1"
    encrypt      = true
    use_lockfile = true
  }
}

Remote
One current state for the team

Encrypted
State may include sensitive values

Locked
One plan or apply can hold the state at a time

Source: https://developer.hashicorp.com/terraform/language/backend/s3

A lock prevents overlapping changes

With -lock-timeout=5m, the second command can retry instead of failing immediately.

Environments and CI

Reuse code without mixing state

Two local environments for the demo

terraform workspace new prod
terraform apply -var env=prod -var port=8090
docker ps --format '{{.Names}} {{.Ports}}'
web-prod  0.0.0.0:8090->80/tcp
web-dev   0.0.0.0:8081->80/tcp
terraform workspace list
  default
* prod

A CLI workspace gives the same configuration a separate state. It is useful for this laptop demo.

Production needs stronger isolation

Shared modules

Write the VPC, EKS cluster and node group once.

Inputs include node size and count.

Separate roots and backends

Staging and production call the modules from different root configurations.

Each can have its own state, credentials and access controls.

CLI workspaces share one backend, so they are not strong production isolation.

A change from Git to AWS

The pipeline applies against the latest shared state after review.

The AWS configuration has the same shape


provider "aws" { region = "ap-south-1" }

module "eks" {
  source       = "terraform-aws-modules/eks/aws"
  cluster_name = "shop-${var.environment}"

  eks_managed_node_groups = {
    default = {
      instance_types = [var.instance_type]
      desired_size   = var.node_count
    }
  }
}

resource "aws_ecr_repository" "api" { name = "shop/api" }

output "registry_url" { value = aws_ecr_repository.api.repository_url }

Provider
Talk to AWS in Mumbai

Module
Create EKS resources from reusable code

Resource and output
Create ECR and publish its URL

Read only. A real EKS deployment also supplies VPC and subnet inputs and requires careful module version pinning.

Spot the problems

15-minute team drill

Four risky practices

  1. terraform.tfstate is committed so everyone has a copy
  2. Engineers run apply from their laptops whenever needed
  3. The database password sits in main.tf
  4. Urgent changes happen in the console; code gets updated later

For each item, explain the failure and a safer practice.

Safer team practices

RiskPractice
State leaks secrets and copies divergeEncrypted remote backend, restricted access
Applies overlap or skip reviewLock state; run apply from CI after approval
Password remains in Git historySupply it from a secrets manager or CI secret
Console change creates driftChange code; run scheduled plans to detect drift
Cleanup

Remove both demo environments

terraform destroy -var env=prod -var port=8090
terraform workspace select default
terraform destroy
docker ps -a --filter name=web

In a cloud account, verify failed or retained resources and check billing after destroy.

Check yourself

Answer first, then click

Check 1

What does terraform plan change in the cloud account?

Nothing. It reads the configuration, state and real resources, then prints what apply would do.
Check 2

Two engineers run terraform apply against an S3 backend with locking. What happens?

One command holds the lock. The other gets a lock error, or retries when a lock timeout is configured.
Check 3

Someone turns off versioning on an S3 bucket in the console. Terraform manages the bucket. What does the next plan show?

A change that restores the configured versioning setting. Terraform read the real bucket and found drift.
Check 4

Why can one Terraform configuration manage AWS resources and Cloudflare DNS?

Provider plugins connect the same Terraform language and workflow to each service's API.
Exit question · 5 minutes

Your team creates dev and prod EKS clusters by clicking in the AWS console. Convince them to use Terraform. Explain the path from Git to AWS and how two engineers avoid overwriting each other.

Keep shared modules and environment inputs in Git. CI posts plan on the pull request, then runs apply after approval. Separate encrypted remote states record dev and prod. State locking allows one writer at a time.
