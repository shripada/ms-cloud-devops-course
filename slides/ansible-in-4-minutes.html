Scenario

One firewall rule

You are at your desk. Your manager messages you: “Can you update a firewall rule on one of the servers?”

  • You log in, make the change, test it
  • You reply: “All good, change applied”
  • Manager: “Perfect. Now do it on the other 127 servers.”

One or two servers by hand is fine. As the number grows, it becomes impossible.

Ask: how long would 127 logins take? What are the chances every one is typed the same way?

What Ansible is

An open-source automation tool that manages and sets up servers at scale.

You describe the tasks for each server in simple, readable files called playbooks.

Ansible is built around three things: inventory, playbooks and modules.

The three pieces

Inventory, playbook, module

Inventory: which servers


[webservers]
192.168.1.10
192.168.1.11

The inventory file

A list of servers, in groups.

Group webservers

A name for a set of servers.

Two servers

VMs, cloud instances, anything you can reach over SSH.

Now when you say webservers, Ansible knows you mean these two machines.

Playbook: what to do


- hosts: webservers
  become: yes
  tasks:
    - name: Allow HTTPS
      ufw:
        rule: allow
        port: "443"
        proto: tcp

The playbook

A YAML file. Read it top to bottom.

hosts

Which group to target. Ansible looks up webservers in the inventory.

become

Changing the firewall needs sudo. This says “become root” for the tasks.

tasks

The task list: where the real work happens. Here, just one task.

The task

Accept TCP connections on port 443: open HTTPS in the firewall, using the ufw module.

ufw is the firewall on Ubuntu.

Module: a mini tool that does the job

Ansible has modules for almost everything:

  • users
  • files
  • packages
  • services
  • cloud providers
  • Docker
  • Kubernetes

The ufw module manages the firewall on Ubuntu.

Describe the result, not the command

By hand: the command

sudo ufw allow 443/tcp

You must know and type the exact command, on each machine.

With a module: the goal

rule: allow
port: "443"
proto: tcp

You say what you want. The module works out how to get there.

A few lines of YAML, written once: your first automation as infrastructure as code.

Three features

Agentless, idempotent, check mode

1. Agentless

Nothing to install on the target servers. Ansible connects over SSH, runs the tasks and disconnects.

2. Idempotent

  1. Check the current setup on the server
  2. Compare it with what the playbook asks for
  3. Change it only if something is actually different
Run the same playbook 10 times on the same server: nothing breaks, and the same change is not applied again and again.

3. Check mode

Simulate the changes without actually applying them.

ansible-playbook -i inventory.ini playbook.yml --check

Preview everything before it runs on 128 servers.

Ansible turns manual work into automation that scales.

Check yourself

  1. Which file tells Ansible what webservers means?
  2. Why does the firewall playbook need become: yes?
  3. You run the playbook a second time. Port 443 is already open. What does Ansible do?
  4. What must you install on the 128 servers before Ansible can manage them?
Answers: 1. The inventory. 2. Changing the firewall needs root (sudo). 3. It checks, finds the rule already there, changes nothing. 4. Nothing from Ansible: it only needs SSH access.
