  • No “site down for 10 minutes, we're deploying”
  • Replace old Pods a few at a time
  • Send traffic to a new Pod only when it's ready

A Deployment's rollout does all three, if you set it up right.

Real teams ship many times a day, while users keep clicking.
01

Rolling updates

Old Pods out, new Pods in, a few at a time

A rollout makes a new ReplicaSet

The old ReplicaSet stays at 0 (the last 10 are kept by default). Rollback = scale it back up.

Click 1: you change the image; a new ReplicaSet appears. Click 2: new scales up, old scales down to 0 but is not deleted. revisionHistoryLimit (default 10) sets how many old ReplicaSets are kept.

What starts a rollout?

Pod template changes

image, env, args…

→ new ReplicaSet

Only replicas changes

Same template

→ same ReplicaSet, more or fewer Pods

No template change, no rollout.

This answers lesson 11's stretch question.

Two dials

With replicas: 4:

SettingMeansValue 1 / 0 gives
maxSurge: 1Extra Pods allowed above replicasAt most 5 Pods
maxUnavailable: 0Wanted Pods allowed to be not readyNever fewer than 4 ready

“Ready” means the readiness probe from lesson 12 passed.

One step of the rollout

At most 5 Pods, never fewer than 4 ready. Four rounds and it's done.

Try it

Set the strategy in who.yaml


spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

Plus a readiness probe

on the container, next to ports.

Without it, “ready” just means “started”.

Readiness probe in the lesson: httpGet path / port 80, periodSeconds: 2. Start from image traefik/whoami:v1.10.
Try it

Ship version 1.11

# who.yaml: image v1.10 → v1.11
kubectl apply -f who.yaml
kubectl rollout status deployment/who
deployment "who" successfully rolled out
kubectl get rs -l app=who
NAME             DESIRED   CURRENT   READY
who-7d9f8c6b5    4         4         4       # new
who-5c6b7d8f9    0         0         0       # old, kept

Predict first: at the busiest moment, how many Pods? How many ready?

In the watch: one new Pod appears, turns 1/1, one old Pod Terminating, four times over. A Terminating Pod isn't counted in the 5, so kubectl get pods may briefly show more.
Break it

Ship a broken build

Give the container the argument --no-such-flag: the app crashes on start.

kubectl rollout status deployment/who --timeout=30s
error: timed out waiting for the condition
kubectl get pods -l app=who
who-7d9f8c6b5-…   1/1   Running            # × 4 old
who-6f4d9b7c2-…   0/1   CrashLoopBackOff

Users see nothing wrong: no old Pod goes until a new one is ready.

That's maxUnavailable: 0 plus the readiness probe. With maxUnavailable above 0, or no readiness probe, users would see errors. The args line goes under the container, next to image.
Fix it

Roll back

kubectl rollout undo deployment/who
deployment.apps/who rolled back

But who.yaml still has the bad args. The next apply breaks it again.

rollout undo is the emergency brake. The real fix goes in Git.

kubectl rollout history deployment/who lists the revisions. Real fix: remove the args line, commit, apply. Then kubectl diff -f who.yaml shows nothing.

Recreate: all out, then all in

Use it when old and new can't run together, e.g. a database change v1.10 can't read.

YAML: strategy with just type: Recreate. The rollingUpdate block isn't allowed with Recreate. Show it live with the watch running: all four go Terminating together.
Trap

The kubectl set image shortcut

kubectl set image deployment/who whoami=traefik/whoami:v1.11
kubectl diff -f who.yaml
-  image: traefik/whoami:v1.11
+  image: traefik/whoami:v1.10

Git says v1.10. The cluster runs v1.11. That's drift.

Nobody reading the repo knows what's running.

Put it back with kubectl apply -f who.yaml.

Build once, deploy many

Same image everywhere. Only its settings (lesson 12) change.

02

Release strategies

How users meet the new version

Four ways to release

StrategyUse when
RollingUpdate (default)Most releases. Old and new can run side by side
RecreateOld and new can't run together
Blue-greenYou want an instant switch and an instant way back
CanaryTry a risky change on a few users first
College exam timetable. Rolling: one department at a time moves. Recreate: college closes a day, then everyone starts on the new one. Blue-green: new timetable is ready on a second notice board; the principal switches the arrow. Canary: only final-years try it for a week.

Blue-green: flip the selector

One change moves every user at once. Switching back is the same change.

Green is running and ready the whole time, but gets no users until the switch. Cost: you pay for double the Pods during the release.
Try it

The Service in bluegreen.yaml


apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  selector:
    app: shop
    track: blue
  ports:
    - port: 80

The switch

blue → green, then apply.

Pods are labelled app: shop plus track: blue or track: green.

Test loop: kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- sh -c 'for i in 1 2 3 4 5 6; do wget -qO- http://shop | grep Hostname; done'

Canary: share the Service

To widen the canary, change the replica counts.

Lesson: selector only app: shop, shop-blue 3 replicas, shop-green 1. With 12 requests, about 3 come from green. Tools like Argo Rollouts or a service mesh give exact percentages; the idea is the same.
03

Private images

Letting the nodes pull from a private registry

ImagePullBackOff

kubectl get pods -l app=mine
mine-6d8f9c7b5-q2wxz   0/1   ImagePullBackOff
kubectl describe pod -l app=mine | tail -5
… 401 Unauthorized

The kubelet on the node tried to pull with no login.

Your docker login on the laptop doesn't help the nodes.

mine.yaml uses your GHCR image from lesson 8. If the package is public it just works; make it private to try this.
Fix it · 1

A docker-registry Secret

kubectl create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io \
  --docker-username=YOUR-USERNAME \
  --docker-password=YOUR-TOKEN \
  --dry-run=client -o yaml > ghcr-pull.local.yaml
kubectl apply -f ghcr-pull.local.yaml

Token: a GitHub PAT with only read:packages. Keep the file out of Git.

Add ghcr-pull.local.yaml to .gitignore first.
Fix it · 2

Point the Pod at it


    spec:
      imagePullSecrets:
        - name: ghcr-pull
      containers:
        - name: app
          image: ghcr.io/YOU/IMAGE:TAG

In the Pod template's spec, beside containers.

Apply: the new Pod pulls and runs.

At work, a secrets manager or encrypted-secret controller supplies the credential. Clean up: kubectl delete -f mine.yaml -f ghcr-pull.local.yaml.

Check yourself

Answer first, then click

Check 1

Which change starts a rollout with a new ReplicaSet: replicas: 3 → 6, or image api:1.4 → api:1.5?

The image change. It changes the Pod template. Scaling only changes the count on the same ReplicaSet.
Check 2

Why does a Deployment keep the old ReplicaSet after an update?

So kubectl rollout undo can just scale it back up, with the exact same Pod template.
Check 3

In a blue-green release, what actually moves users to the new version?

Changing the Service's selector to the new Deployment's labels.
Check 4

New Pods show ImagePullBackOff with 401 Unauthorized from ghcr.io. What's the fix?

Create a docker-registry Secret and list it under imagePullSecrets.
Check 5

6 replicas, maxSurge: 2, maxUnavailable: 1. During an update, what's the most Pods, and the fewest ready?

At most 6 + 2 = 8 Pods. At least 6 − 1 = 5 ready.
Check 6

Version 4.0 changes the results table so version 3.x can't read it. Which strategy?

Recreate: every old Pod stops before any new one starts. A rolling update would run 3.x and 4.0 together.
