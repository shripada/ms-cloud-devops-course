Ship a new version while users keep clicking, and get back fast when it's broken

Press S for this speaker view, T to switch light/dark, Esc for the slide overview. Students need a second terminal for kubectl get pods -l app=who -w.

Upgrade IRCTC while Tatkal opens

10 a.m.: Tatkal booking opens and lakhs of users are clicking. The team must ship a new version right now.

Stop all old Pods, then start new ones → every user sees errors. So the upgrade must:

  • Replace old Pods a few at a time
  • Send users to a new Pod only when it's ready
  • Keep a one-command way back

A Deployment's rolling update gives all three, if you set it up right.

Real teams ship many times a day, while users keep clicking.
01

Rolling updates

Old Pods out, new Pods in, a few at a time

A new image makes a new ReplicaSet

Rollback = scale the old ReplicaSet back up.

Click 1: you change the image; a new ReplicaSet appears with 0 Pods. Click 2: new scales up to 4, old scales down to 0 but is not deleted. revisionHistoryLimit (default 10) sets how many old ReplicaSets are kept.

What starts a rollout?

Pod template = the template: block, what every Pod looks like.

Pod template changes

image, env, args…

→ new ReplicaSet

Only replicas changes

Same template

→ same ReplicaSet, more or fewer Pods

No template change, no rollout.

This answers lesson 11's stretch question.

Two settings control each round

With replicas: 4:

SettingPlain meaningResult
maxSurge: 1Up to 1 extra Pod during the updateAt most 5 Pods
maxUnavailable: 0No Pod may be missing or not readyAlways 4 ready

Bigger numbers → faster update, but less spare room if the new version is bad.

“Ready” = the readiness probe from lesson 12 passed.

Each round: add one, wait, remove one

Never more than 5 Pods, never fewer than 4 ready.

Try it

Set the strategy and a probe in who.yaml

Under spec:, next to replicas:


spec:
  replicas: 4
  strategy:
    type: RollingUpdate
    rollingUpdate:
      maxSurge: 1
      maxUnavailable: 0

Under the container, next to ports::


readinessProbe:
  httpGet:
    path: /
    port: 80
  periodSeconds: 2

Without the probe, “ready” just means “started”.

Start from image traefik/whoami:v1.10. Apply, then kubectl get rs -l app=who: one ReplicaSet with 4 Pods.
Try it

Ship version 1.11

Terminal 2 watches: kubectl get pods -l app=who -w

Terminal 1: change the image in who.yaml to v1.11, then kubectl apply -f who.yaml

Predict: at the busiest moment, how many Pods? How many ready?

# terminal 2
who-7d9f8c6b5-k8x2p   0/1   ContainerCreating   # new: the 5th Pod
who-7d9f8c6b5-k8x2p   1/1   Running             # new is ready
who-5c6b7d8f9-q4wzn   1/1   Terminating         # one old goes
… the same, three more times

Busiest moment: 5 Pods, 4 ready.

A Terminating Pod isn't counted in the 5, so kubectl get pods may briefly show more. Afterwards: kubectl get rs -l app=who shows the new ReplicaSet with 4 and the old one with 0.
Break it

Ship a broken build

Give the app a flag it doesn't know, so it crashes on start. Under the container, next to image, then apply:


args:
  - --no-such-flag

kubectl rollout status deployment/who --timeout=30s
error: timed out waiting for the condition
kubectl get pods -l app=who
who-7d9f8c6b5-k8x2p   1/1   Running            # v1.11, still serving
who-7d9f8c6b5-m3v7r   1/1   Running            # v1.11, still serving
who-7d9f8c6b5-p9d2s   1/1   Running            # v1.11, still serving
who-7d9f8c6b5-t5h8w   1/1   Running            # v1.11, still serving
who-6f4d9b7c2-x7n4c   0/1   CrashLoopBackOff   # new, with the bad flag

No old Pod goes until a new one is ready. Users see nothing wrong.

Why: maxUnavailable: 0 plus the readiness probe. With maxUnavailable above 0, or no readiness probe, users would see errors.
Fix it

Roll back

kubectl rollout history deployment/who
REVISION   CHANGE-CAUSE
1          <none>     # v1.10
2          <none>     # v1.11
3          <none>     # v1.11 + bad flag
kubectl rollout undo deployment/who
deployment.apps/who rolled back   # to revision 2

But who.yaml still has the bad args. The next apply breaks it again.

Real fix: delete the args lines → commit → kubectl apply -f who.yaml

rollout undo is the emergency brake. The real fix goes in Git.

After the real fix, kubectl diff -f who.yaml shows nothing.
02

Release strategies

How users meet the new version

Four ways to release

StrategyHowUse when
RollingUpdate (default)Replace Pods a few at a timeMost releases
RecreateStop all old Pods, then start new onesOld and new can't run together
Blue-greenTwo Deployments; switch the Service between themYou want an instant switch and an instant way back
CanaryA few new Pods share the Service with old onesTry a risky change on a few users first
College exam timetable. Rolling: one department at a time moves. Recreate: college closes a day, then everyone starts on the new one. Blue-green: new timetable is ready on a second notice board; the principal switches the arrow. Canary: only final-years try it for a week.

Recreate: all out, then all in

Use it when old and new can't run together, e.g. the new version renames a database column the old one still reads.

Try it: in who.yaml set type: Recreate, delete the rollingUpdate: block, set the image back to v1.10, apply and watch.

The rollingUpdate block isn't allowed with Recreate. With the watch running, all four go Terminating together. Put the strategy back to RollingUpdate afterwards.

Blue-green: flip the Service's selector

One change moves every user at once. Switching back is the same change.

Click 1 flips the selector. Cost: you pay for double the Pods during the release.
Try it

The Service in bluegreen.yaml


apiVersion: v1
kind: Service
metadata:
  name: shop
spec:
  selector:
    app: shop
    track: blue
  ports:
    - port: 80

The switch

blue → green, then apply.

shop-blue Pods: track: blue, v1.10

shop-green Pods: track: green, v1.11

Both also have app: shop.

The two Deployments are in the lesson. Test loop: kubectl run tmp --rm -it --image=busybox:1.36 --restart=Never -- sh -c 'for i in 1 2 3 4 5 6; do wget -qO- http://shop | grep Hostname; done'

Canary: 1 new Pod in 4 gets ~1 in 4 requests

To widen the canary, change the replica counts: 2 + 2 → half the requests.

Lesson: selector only app: shop, shop-blue 3 replicas, shop-green 1. With 12 requests, about 3 come from green. Tools like Argo Rollouts or a service mesh give exact percentages; the idea is the same.
03

Git is what's running

Change the file, not the cluster

Trap

Changing the cluster without Git

kubectl set image deployment/who whoami=traefik/whoami:v1.11
kubectl diff -f who.yaml
-  image: traefik/whoami:v1.11   # what the cluster runs
+  image: traefik/whoami:v1.10   # what who.yaml (Git) says

Git and the cluster disagree. That's drift.

Nobody reading the repo knows what's running. The next apply silently undoes it.

Put it back: kubectl apply -f who.yaml. Change the image in the file instead.

Build once, deploy many

Rebuild for each environment, and production runs an image nobody tested.

Same image everywhere. Only its ConfigMaps and Secrets (lesson 12) change.

04

Private images

Letting the nodes pull from a private registry

ImagePullBackOff: the node has no login

kubectl get pods -l app=mine
mine-6d8f9c7b5-q2wxz   0/1   ImagePullBackOff
kubectl describe pod -l app=mine | tail -5
Warning  Failed  …  failed to pull "ghcr.io/YOU/IMAGE:TAG": 401 Unauthorized

The node tried to download the image without a username or token.

Your docker login on the laptop doesn't help. The cluster needs its own.

mine.yaml uses your GHCR image from lesson 8. If the package is public it just works; make it private to try this.
Fix it · 1

A docker-registry Secret

echo ghcr-pull.local.yaml >> .gitignore
kubectl create secret docker-registry ghcr-pull \
  --docker-server=ghcr.io \
  --docker-username=YOUR-USERNAME \
  --docker-password=YOUR-TOKEN \
  --dry-run=client -o yaml > ghcr-pull.local.yaml
kubectl apply -f ghcr-pull.local.yaml

--dry-run=client -o yaml: don't create it, just write the YAML to a file.

Token: a GitHub token (PAT) with only read:packages. The file stays out of Git.

Fix it · 2

Point the Pod at it


spec:
  template:
    spec:
      imagePullSecrets:
        - name: ghcr-pull
      containers:
        - name: app
          image: ghcr.io/YOU/IMAGE:TAG

In the Pod's spec (the one inside template:), beside containers.

Apply: the new Pod pulls and runs.

At work, a secrets manager or encrypted-secret controller supplies the credential. Clean up: kubectl delete -f mine.yaml -f ghcr-pull.local.yaml.

Check yourself

Answer first, then click

Check 1

Which change starts a rollout with a new ReplicaSet: replicas: 3 → 6, or image api:1.4 → api:1.5?

The image change. It changes the Pod template. Scaling only changes the count on the same ReplicaSet.
Check 2

Why does a Deployment keep the old ReplicaSet after an update?

So kubectl rollout undo can just scale it back up, with the exact same Pod template.
Check 3

In a blue-green release, what actually moves users to the new version?

Changing the Service's selector to the new Deployment's labels.
Check 4

New Pods show ImagePullBackOff with 401 Unauthorized from ghcr.io. What's the fix?

Create a docker-registry Secret and list it under imagePullSecrets.
Check 5

6 replicas, maxSurge: 2, maxUnavailable: 1. During an update, what's the most Pods, and the fewest ready?

At most 6 + 2 = 8 Pods. At least 6 − 1 = 5 ready.
Check 6

Version 4.0 changes a database table so version 3.x can't read it. Which strategy?

Recreate: every old Pod stops before any new one starts. A rolling update would run 3.x and 4.0 together.
