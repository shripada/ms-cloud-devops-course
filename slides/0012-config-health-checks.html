Config &

Keep settings out of your code, and let Kubernetes check if your app is working

Press S for this speaker view, T to switch light/dark, Esc for the slide overview. Two halves today: ConfigMaps and Secrets, then the three probes.

One image, three places

Same image everywhere. Only the settings change.

Three places, and staging and production are two separate clusters. Staging is a copy where the team tries a new version first; production is the one real students use to buy fest tickets. Same two settings in every box, different values. Bake them in and you need three images, and the production password sits inside every copy on Docker Hub.

Running is not the same as ready

Kubernetes only knows that the process is running.

It can't tell if the app is:

  • stuck
  • still loading
  • ready for users

Probes are how you tell it.

Without probes, a rolling update (next lesson) sends users to Pods that can't answer yet.
01

ConfigMaps & Secrets

Settings that live outside the image

ConfigMap or Secret?

ConfigMap

Normal settings anyone on the team may see

LOG_LEVEL
PAYMENT_GATEWAY_URL

Secret

Anything that would hurt if it leaked

DB_PASSWORD
UPI_API_KEY

Both are small key–value objects. A Pod reads them as env vars or files.

Try it

A ConfigMap manifest


apiVersion: v1
kind: ConfigMap
metadata:
  name: app-config
data:
  LOG_LEVEL: info
  PAYMENT_GATEWAY_URL: https://pay.example.com

data

Each line is one key and its value, in plain text.

Safe to keep in Git with your other manifests.

kubectl apply -f app-config.yaml
configmap/app-config created
Try it

A Secret manifest


apiVersion: v1
kind: Secret
metadata:
  name: db-secret
type: Opaque
stringData:
  DB_PASSWORD: Fest2026

stringData

You write plain text. The API server stores it as base64 under data.

Name it db-secret.local.yaml and add it to .gitignore. Never commit it.

printf '%s\n' 'db-secret.local.yaml' >> .gitignore, then kubectl apply -f db-secret.local.yaml.

base64 is not encryption

kubectl get secret db-secret -o yaml
data:
  DB_PASSWORD: RmVzdDIwMjY=
echo RmVzdDIwMjY= | base64 -d
Fest2026

No key. No password. One command.

What protects a Secret: who may read it (RBAC), encryption at rest in etcd (when configured), and keeping it out of Git.

base64 is just a way to write any bytes as plain letters. If you can read the Secret object, you can read the password. The lesson uses kubectl get secret db-secret -o jsonpath='{.data.DB_PASSWORD}' | base64 -d.

Feed the settings into the container


containers:
  - name: app
    image: busybox:1.36
    envFrom:
      - configMapRef:
          name: app-config
    env:
      - name: DB_PASSWORD
        valueFrom:
          secretKeyRef:
            name: db-secret
            key: DB_PASSWORD

The container

Part of the cfg Deployment.

envFrom

Every key in the ConfigMap becomes an env var.

secretKeyRef

Picks one key from the Secret.

The demo app prints LOG_LEVEL, the URL and only the password's length. Never print a secret in logs. kubectl logs deploy/cfg --tail=2 shows LOG_LEVEL=info and password_length=8.
Predict

In app-config.yaml you change LOG_LEVEL: info to debug and apply it. Does the running app print debug?

No. Env vars are copied into the process once, when the container starts.
kubectl rollout restart deployment/cfg
kubectl logs deploy/cfg --tail=1
LOG_LEVEL=debug …
Same as any Linux program: the environment is fixed at start. A ConfigMap mounted as a file does update inside the Pod after a short delay, but the app still has to re-read it. Plan for a restart either way.
Break it

Ask for a key that doesn't exist

In cfg.yaml: key: DB_PASSWORD → key: password

kubectl get pods -l app=cfg
NAME              READY   STATUS
cfg-7c9d5-x1kqp   1/1     Running
cfg-5b8f6-k2mzt   0/1     CreateContainerConfigError
kubectl describe pod cfg-5b8f6-k2mzt
couldn't find key password in Secret default/db-secret

The old Pod keeps running, so users are safe.

Put the key back to DB_PASSWORD, apply, then kubectl delete -f cfg.yaml.
02

Health checks

Three probes the kubelet runs against your container

Three probes

ProbeAsksIf it fails
livenessProbeIs the app stuck?Restart the container
readinessProbeCan it serve users now?No traffic, no restart
startupProbeHas it finished starting?The other two wait
Readiness failure removes the Pod from the Service's endpoints. Startup: if it never passes within its budget, the container is restarted.

The college canteen

  • Liveness: is the cook awake?
    No → replace the cook.
  • Readiness: is food ready to serve?
    No → don't send students to this counter yet.
  • Startup: the dosa batter takes 40 minutes.
    Don't ask “are you awake?” every 5 seconds till then.

In a real app


app.get('/healthz', (req, res) => {
  res.send('ok');
});

app.get('/ready', async (req, res) => {
  try {
    await db.query('SELECT 1');
    res.send('ready');
  } catch {
    res.status(503).send('db down');
  }
});

Liveness: /healthz

Checks only the app itself. Stuck app → no answer → restart.

Readiness: /ready

Checks what it needs to serve, like the database. Fails → no traffic.

The developers write these URLs into the app. The probe just calls them.

A Node.js/Express API, port 3000. The probe YAML is the same as in our demos: httpGet path /healthz, port 3000. Never check the database in liveness: if the DB is down, restarting every Pod fixes nothing. Frameworks give you these: Spring Boot /actuator/health/liveness and /readiness; Kubernetes' own API server has /livez and /readyz. We can't make a real app hang on cue in class, so the next demo fakes the hang with nginx.
Try it

Simulate a hang


apiVersion: v1
kind: Pod
metadata:
  name: liveness
spec:
  containers:
    - name: app
      image: nginx:1.27
      livenessProbe:
        httpGet:
          path: /index.html
          port: 80
        periodSeconds: 3

Name

We chose liveness. Any name works.

App

Plain nginx. /index.html → 200.

Probe

Every 3 s, ask for /index.html.

Same nginx the students already know. index.html stands in for the app's /healthz route from the last slide. kubectl apply -f liveness.yaml, then kubectl get pod liveness: 1/1 Running, 0 restarts.

Break it yourself

kubectl exec liveness -- rm /usr/share/nginx/html/index.html
kubectl get pod liveness -w
NAME       READY   STATUS    RESTARTS
liveness   1/1     Running   0             ← at start
liveness   1/1     Running   1 (2s ago)    ← ~10 s later

Same Pod. -w (--watch) adds a new line each time the Pod changes.

kubectl describe pod liveness
Liveness probe failed: HTTP probe failed with statuscode: 404
Container app failed liveness probe, will be restarted

The process never crashed. The probe found it broken. The restart brought the file back.

-w never rewrites a line: line 1 is the state when you start watching, line 2 is printed when the restart happens. Real output also has an AGE column. No file → nginx answers 404 → after 3 failures (about 9 s) the kubelet restarts the container. A restart makes a fresh container from the image, so index.html is back: that's why restarting is the right fix for a stuck app. RESTARTS stays at 1. Clean up: kubectl delete -f liveness.yaml.

The slow-start trap

App needs 30 s to start. Liveness: start at 5 s, every 5 s, 3 failures allowed.

Restarts forever → CrashLoopBackOff. The app is fine; the probe is wrong.

The lesson's slow.yaml: nginx with "sleep 30" before it starts. Liveness checks at 5, 10 and 15 s all fail, so it gives up at about 15 s. kubectl get pods -l app=slow -w: restarts every ~15–20 s (the kill itself takes a moment), never 1/1.

Fix: a startup probe


startupProbe:
  httpGet:
    path: /
    port: 80
  periodSeconds: 5
  failureThreshold: 12

Budget

12 × 5 = 60 s to start

Liveness and readiness don't run until it passes.

Result: 0/1 for ~30 s, then 1/1, 0 restarts.

The lesson replaces the livenessProbe block with three probes: startup (budget 60 s), readiness on /ready every 5 s, liveness on / every 10 s.

Readiness: out of traffic, not restarted

Readiness fails → no traffic. Liveness fails → restart.

kubectl exec $POD -- rm /usr/share/nginx/html/ready, wait 20 s, then compare kubectl get pods and kubectl describe endpointslices: that Pod's endpoint shows Ready: false. Put the file back and the Pod rejoins. Like a Pod that lost its database connection: don't kill it, just stop sending users.

Check yourself

Answer first, then click

Check 1

A teammate says: “It's safe to commit the Secret YAML to Git, the password is encrypted.” What's wrong?

The value is only base64-encoded. Anyone runs base64 -d and reads it, no key needed.
Check 2

A Pod's readiness probe starts failing. What does Kubernetes do?

Removes it from the Service's endpoints, so it gets no traffic. It does not restart it.
Check 3

You change LOG_LEVEL in a ConfigMap that a Deployment reads with envFrom. What happens to the running Pods?

Nothing, until they restart. Run kubectl rollout restart.
Check 4

An app needs 90 seconds to start, then should be restarted quickly if it hangs. Which probe solves the slow start?

A startup probe with a budget over 90 s, e.g. periodSeconds: 10, failureThreshold: 12. Keep liveness for later hangs.
Check 5

Liveness: start at 10 s, every 5 s, 2 failures allowed. The app needs 45 s to load. What happens?

Checks at 10 s and 15 s both fail, so it's killed at about 15 s, long before 45 s. It restarts forever: CrashLoopBackOff. Add a startup probe.
