Question bank — Module 1: Docker

University-pattern questions. Each one carries 10 marks and has two parts of 5 marks each. Write the answer first, on paper, with a timer. Only then open the model answer.

How to use this. Ten marks is roughly 12 minutes of writing. Part (a) is usually “explain”, part (b) is usually “apply” — a command, a Dockerfile or a debugging decision. In the exam, a labelled diagram or a correct command earns marks that a paragraph does not, so draw and write commands wherever the question allows.

Unit 1 — Containers and images

Q1. (10 marks)

(a) Differentiate between a virtual machine and a container with the help of a diagram. (5 marks)
(b) A container started from the nginx image is running. Explain what exactly is “isolated” about it, and state two commands that prove a container is an ordinary process. (5 marks)

Model answer

(a) Draw two stacks side by side. VM stack: hardware → host OS → hypervisor → guest OS (with its own kernel) per VM → app. Container stack: hardware → host OS with a single kernel → container runtime → container (app + its libraries) with no guest OS. Points to state: a VM virtualises hardware and boots a full OS with its own kernel; a container virtualises the operating system and shares the host kernel. Consequences: containers start in milliseconds versus minutes, use megabytes instead of gigabytes, and give weaker isolation than a VM because a kernel bug is shared by all containers.

(b) The process is isolated using Linux kernel features: namespaces give it a private view of process IDs, mount points (its own filesystem from the image), network interfaces, hostname and users; cgroups limit how much CPU and memory it may consume. It is not a separate machine — the process is visible from the host. Commands: docker top web lists the container's processes, and docker ps/ps -ef on the host shows the same nginx process. docker logs web simply reads the process's stdout/stderr, which is also evidence it is a plain process.

Q2. (10 marks)

(a) “An image is a class and a container is an object.” Justify this statement, and explain why an image is called immutable. (5 marks)
(b) Write the commands to run two containers from the same nginx image on host ports 8081 and 8082, list them, and remove both along with their names. (5 marks)

Model answer

(a) An image is a read-only template, like a class definition; a container is a running instance created from it, like an object, with its own writable layer, own process and own state. One image can produce many containers, just as one class can produce many objects. An image is immutable because once built, its layers are fixed and identified by a content digest (SHA-256). Any change — installing a package, editing a file — does not modify the image; it produces a new layer and therefore a new image. What a running container writes goes into a thin writable layer on top, which is discarded when the container is removed.

(b)

docker run -d -p 8081:80 --name a nginx
docker run -d -p 8082:80 --name b nginx
docker ps
docker rm -f a b

Note -p HOST:CONTAINER: both containers still listen on port 80 internally; only the host port differs, which is why there is no clash. docker rm -f stops and removes in one step; docker stop a b && docker rm a b is equally acceptable.

Unit 2 — Layers and registries

Q3. (10 marks)

(a) Explain the layered architecture of a Docker image and the role of the union filesystem. (5 marks)
(b) Two images, app:v1 and app:v2, are built from the same base image. Explain, with reference to layers, why pulling the second one is much faster. (5 marks)

Model answer

(a) An image is a stack of read-only layers, each layer being the set of filesystem changes produced by one build instruction. A union (overlay) filesystem merges these layers into a single directory tree that the container sees. Files in an upper layer hide files of the same path in a lower layer. When a container runs, a thin writable layer is added on top; modifying an existing file copies it up into that layer first (copy-on-write), leaving the image untouched. Each layer has a content-addressable digest, so identical layers are stored once and shared by every image that uses them.

(b) Pulling downloads layers, not whole images. Since both images share the same base layers and those are already present locally from the first pull, Docker sees the digests already exist and skips them — the output shows “Already exists” for those layers. Only the layers unique to v2 (typically the application layer) are transferred. This is also why ordering instructions so that rarely-changing steps come first is valuable: shared, cached layers reduce both pull time and disk usage.

Q4. (10 marks)

(a) What is a registry? Distinguish between a repository, a tag and an image digest. (5 marks)
(b) Your team deploys using myapp:latest, and the production server is running different code from the test server. Explain the cause and give a corrected tagging practice with commands. (5 marks)

Model answer

(a) A registry is a server that stores and distributes images (Docker Hub, GitHub Container Registry, a private Harbor). A repository is one named collection of related images inside a registry, e.g. library/nginx or shripada/myapp. A tag is a mutable human label on one version within a repository, e.g. nginx:1.27; the default tag is latest. A digest (sha256:…) is the immutable content hash of a specific image; a tag can be moved to point at a new digest, a digest always identifies exactly one image.

(b) Cause: latest is only a label, not a version. It was moved to a newer image after the test server pulled, so the two servers resolved latest to different digests at different times. Correct practice — tag every build with an immutable version and deploy that:

docker build -t myapp:1.4.2 .
docker tag myapp:1.4.2 shripada/myapp:1.4.2
docker push shripada/myapp:1.4.2
docker pull shripada/myapp@sha256:<digest>   # strictest: pin by digest

Keep latest as a convenience pointer only, never as the deployment reference.

Unit 3 — Dockerfiles

Q5. (10 marks)

(a) Explain the purpose of the instructions FROM, WORKDIR, COPY, RUN, EXPOSE and CMD. (5 marks)
(b) Differentiate between RUN and CMD, and between CMD and ENTRYPOINT, with one example each. (5 marks)

Model answer

(a) FROM selects the base image and starts a build stage. WORKDIR sets the working directory for the instructions that follow and for the running container, creating it if needed. COPY copies files from the build context into the image. RUN executes a command at build time and commits the result as a new layer. EXPOSE documents the port the application listens on — it does not publish it; -p at run time does that. CMD gives the default command executed when a container starts.

(b) RUN happens once, at build time, and its effect is baked into a layer (RUN npm ci). CMD happens at run time, every time a container starts (CMD ["node","server.js"]), and it is replaced by any command the user appends to docker run. ENTRYPOINT also runs at start-up but is not replaced by user arguments; those arguments are appended to it. So ENTRYPOINT ["ping"] with CMD ["localhost"] makes the image behave like the ping program: docker run img google.com runs ping google.com. Use ENTRYPOINT when the image is one tool, CMD when you want an overridable default.

Q6. (10 marks)

(a) Explain build cache and layer ordering. Why is COPY package.json written before COPY . .? (5 marks)
(b) Write a multi-stage Dockerfile for a Node.js application and state two benefits of the multi-stage approach. (5 marks)

Model answer

(a) During a build, Docker checks each instruction against its cache. If the instruction and the files it depends on are unchanged, the cached layer is reused; the first instruction that changes invalidates that layer and every layer after it. Application source changes on almost every build, while dependencies change rarely. Copying only the manifest first, installing dependencies, and copying the source afterwards means an ordinary code edit reuses the cached dependency-install layer, turning a multi-minute build into a few seconds. Writing COPY . . first would invalidate the install layer on every edit.

(b)

FROM node:22-alpine AS build
WORKDIR /app
COPY package*.json ./
RUN npm ci
COPY . .
RUN npm run build

FROM node:22-alpine
WORKDIR /app
ENV NODE_ENV=production
COPY package*.json ./
RUN npm ci --omit=dev
COPY --from=build /app/dist ./dist
EXPOSE 3000
CMD ["node","dist/server.js"]

Benefits: (i) the final image contains only runtime files — no compilers, dev dependencies or source — so it is far smaller and faster to pull; (ii) the attack surface shrinks, since build tools that an attacker could use are absent. A third acceptable point: build and runtime environments are defined in one file, with no external build script.

Mixed / viva practice

Q7. (10 marks)

(a) A container exits immediately after docker run. List the steps you would follow to diagnose it, naming the command used at each step. (5 marks)
(b) Justify: “docker stop is not the same as docker rm, and removing a container does not remove its image.” (5 marks)

Model answer

(a) 1. docker ps -a — confirm it exited and read the exit code. 2. docker logs <name> — read stdout/stderr, which usually names the error. 3. docker inspect <name> — check the command actually executed, environment variables and mounts. 4. Re-run interactively with a shell to explore the image: docker run -it --entrypoint sh <image>. 5. Verify the main process runs in the foreground — a container lives only as long as its PID 1, so a daemon started in background mode makes the container exit at once. Typical causes: wrong CMD path, missing config or environment variable, or a process that daemonises itself.

(b) docker stop sends SIGTERM (then SIGKILL after a grace period) to PID 1; the container stops but continues to exist with its writable layer and configuration, visible in docker ps -a and restartable with docker start. docker rm deletes that stopped container and its writable layer permanently. The image is a separate, read-only object stored independently and shared by all containers made from it, so removing a container leaves the image in docker images; it is deleted only by docker rmi.

Marks split shown here is the usual pattern: roughly 2 marks for the definition, 2 for the explanation or example, 1 for the diagram, command or a correctly justified conclusion.
